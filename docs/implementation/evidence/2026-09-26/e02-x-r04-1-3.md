## X-R04-1 per-dialect verdicts: SQL cancel

| Dialect | Verdict | Observed behavior |
|---|---|---|
| PostgreSQL (live) | NEGATIVE — no server-side effect | `cancel()` mid-`pg_sleep` flips the client `cancelled` flag only. Second connection confirms the backend stays `active` after the call; the awaited query runs to full completion (`ok`, elapsed >= sleep). Same on a `reserve()`d connection. |
| MySQL (live) | NEGATIVE — no server-side effect | `cancel()` mid-`SLEEP` flips the client flag only. `SHOW PROCESSLIST` from a second connection still shows the thread in `Execute / User sleep` after the call; the query completes normally. No server `KILL` is issued (no 1317). |
| SQLite (in-memory) | NEGATIVE — structurally uninterruptible | Execution is synchronous: a timer due 50ms into a ~500ms scan fires only after the query settles (`cancelled` still false at settle; rows exact). Cancel cannot interleave. The file adapter shares this engine. |

All three dialects share two further behaviors (pinned by legs):

- Cancel before execution leaves the await unsettled (2s race on
  PG/MySQL, 1s on SQLite; a 30s+ scratch wait also never settled).
  E04 must never cancel a query that has not started executing.
- The client `active` flag reads `false` while a query is demonstrably
  executing server-side; it is not an execution oracle.

Consequence: NO caller deadline/cancel operand maps to `Query.cancel()`
on any dialect. SQL takes the cancel-absent branch: the request
boundary still returns at budget expiry while the native operation
stays owned until settlement, reporting the honest unknown-write
outcome with supervisor escalation (E04/E09 per the experiment table).
Aborting a queued `reserve({signal})` rejects the reservation with the
signal reason while running queries complete normally — it is
reservation control, not query cancellation, and maps to no
query-cancel operand either.

## X-R04-3 verdict: ingress disconnect projection

POSITIVE — pinned `Bun.serve` projects peer disconnect as
`Request.signal` abort, tested separately from SQL cancel:

- The serve-side `Request` exposes `signal: AbortSignal`, un-aborted
  on arrival (surface leg).
- Buffered handler: client abort trips the handler's signal promptly
  (~400ms wall, matching the abort; leg bound 2500ms) while the
  handler itself is NOT terminated and runs to full completion.
- Streaming handler: client abort fires the `ReadableStream`
  `cancel()` callback and trips the request signal together.

Exact native meaning E04 may map: disconnect observation only. The
signal reports the disconnect; it stops no work by itself. Any
response to it (budget expiry, boundary return) is E04 policy built on
the E01 budget/ownership layers, not native termination.
