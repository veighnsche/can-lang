## Cancel branch verdict (X-R15-1): NEGATIVE

The `end(Error)` preservation candidate is dead. `end(Error)`
issues byte-identical wire traffic to bare `end()` on both the
single-PUT and multipart paths — no `AbortMultipartUpload` is ever
issued, the key materializes, and the call resolves (never rejects)
with the byte count. The pinned-types remark ("Writer will
automatically abort multipart upload on error") describes Bun's
behavior when its own part operations fail (observed in F3: abort on
`delete()` after part failure), not the `end(error)` parameter,
which is ignored. E08 must take the destructive rename:
`cancel_upload` goes, explicitly-named `discard_upload` carries the
destructive/unknown contract.

## Cleanup-await failure injection (one leg per await)

- F1 (complete-mpu → 500, cancel): cancel resolves; client
  retries the completion 1+3 (each on a fresh connection) with NO
  abort attempt; key absent; orphan 1 holding parts `[1: 5242880,
  2: 1048576]` (ListParts 200). Failed completion strands real
  bytes.
- F2 (delete-object → 500, cancel): cancel resolves; key REMAINS
  with the replacement bytes — the transient completion becomes
  permanent. Exact ops `[PUT put-object, DELETE delete-object
  fault500]`.
- F3 (upload-part → 500): `uploadWrite` → `s3::service_error
  {code: InternalError, operation: upload_write}` after 4 part
  attempts; cancel resolves; key absent; orphan 0. Mechanism
  (bisected): `end()` after a failed flush returns `0`
  synchronously with zero wire traffic; `file.delete()` aborts the
  tracked MPU first and then deletes the key; ~3 further
  background aborts fire within 1 s, then silence through 6 s
  (bounded burst, not a loop).
- F4 (complete-mpu → 500, abort-mpu → 500): the abort-fault rule
  NEVER triggers (0 abort attempts — the client does not try);
  orphan 1 holding parts `[1: 5242880, 2: 1048576]`; out-of-band
  abort + empty re-list (the re-list, not the 204, is the proof).
- F5 (put-object → 500, small cancel): 4 PUT attempts; cancel
  resolves; key absent.
- F6 (`end(Error)` with PUT → 500): rejects `S3Error /
  InternalError` after 4 attempts; key absent. A failed `end`
  surfaces; only a successful one silently publishes.
- F7 (upload-part → 500, abort-mpu → 500): the delete-coupled
  abort faults, the key delete still lands, orphan 1 = EMPTY shell
  (ListParts 200, zero parts — the MPU record with no bytes).

Observed native retry policy (all S3-protocol): error RESPONSES are
retried 1+3 on fresh connections (PUT, part, complete);
`delete()` is single-shot; a dropped (reset) connection is NOT
retried for create (H2) but IS retried for complete (H3) —
recorded as observed asymmetry, mechanism unknown.

## Deadline branch verdict (X-R15-3): NEGATIVE

No bounded implementation exists for hung writer/flush/end. Hung
awaits never settle client-side (no timeout, no abort API, no
release call); `end(Error)` waits on the same hung state; and
abandoning a writer pins the event loop from creation while
stranding MPU state server-side. A raced write_stream can return
user-visibly at its deadline, but only by abandoning an un-ended
sink — the pin plus the orphan make that unbounded in every sense
that matters. E08 keeps the honestly-documented between-awaits
bound; the W5 S3 legs are BLOCKED pending explicit user scope
return (per disposition F-R15-03/04, the O2 branch fails W5).

Per-await observations:

- H1 (hung `source.read`, 100 ms deadline, 3 s watchdog):
  WATCHDOG; zero wire ops (lazy sink — the hang is pre-first-byte).
  Current code hangs past its deadline: F-R15-03 live. Bounding a
  hung read is a Can-reader concern (pre-wire; no sink, hence no
  S3 pin cost), not an S3-native concern — E08 may apply the
  cancel-absent shape there, but it does not salvage a bounded
  write_stream deadline while writer/flush/end stay unboundable.
- H2 (hung create → hung flush): flush WATCHDOG (3 s),
  `end(Error)`-during-hung-flush WATCHDOG (5 s). No client-side
  abort exists. Recovery (drop + healthy service): both reject
  `S3Error / ConnectionClosed` with NO retry; no key, no orphan
  (the creation never reached the service).
- H3 (hung complete → hung `end()`): WATCHDOG; parts uploaded
  fine. Recovery: the client retries the completion on a fresh
  connection and `end()` resolves `6291456`; key completes at full
  size. ONE full-run observation listed a leftover MPU for the key
  afterwards; six follow-up reproductions (1 single + 5 loop, all
  with ListParts probing) show zero orphans. Ghost-vs-real is
  undetermined (the vacuous abort-204 cannot decide it); H3 pins
  the qualified zero-orphan shape and fails loudly on recurrence.
  AWS-real confirmation flagged.
- H4 (hung HEAD → hung `stat()`): WATCHDOG; recovery resolves.
  Post-end stat is an ordinary hung fetch with no sink involved.
- H5 (abandoned hung sinks, child processes): hung-flush,
  hung-end, hung-stat, and end-during-hung-flush (in-child race:
  WATCHDOG) all print their work lines then stay alive to SIGKILL.
  Abandonment never settles anything.
- Pin-after-settle (scratch child probes): a REJECTED `end()`
  releases the loop (exited 0); a resolved-after-retry `end()`
  releases it too (exited once the leftover race timer fired).
  Only the unsettled/un-ended writer pins.
