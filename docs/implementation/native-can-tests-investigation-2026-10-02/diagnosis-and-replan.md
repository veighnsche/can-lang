# Native Can testing: diagnosis and proposed replan

Investigated 2 October 2026. Initial Can HEAD `b1a9a9a8`; both repositories initially clean. This document records findings and proposed policy changes. No source, acceptance gate, retirement rule or caller was changed. No broad build, performance measurement, live service or browser campaign ran.

The principal failure is scope: the 143-task programme inventories **Can's own tests**, while the requested endpoint is **Manolea's tests**. It produced substantial infrastructure and static source, but **zero Manolea test files have been replaced**. The assertion bloat is real and largely generated by repeated authored observations and provenance tables. Executable replacement remains unfinished.

## 7. Real engineering and the completion bottleneck

Live recomputation: **143 unique tasks = 47 complete / 46 active / 40 planned / 10 blocked**. The task sources agree. Summary fields disagree: [tasks.json:9964](/Users/vince/Projects/can-lang/docs/implementation/native-can-tests-plan-2026-09-30/tasks.json:9964) retains older counts, while [validation.json:13](/Users/vince/Projects/can-lang/docs/implementation/native-can-tests-plan-2026-09-30/validation.json:13) is one promotion behind.

Under the present contract the narrow serial chain is:

`P13 strict host enforcement → P14 actual independently built N owner → P23 live runner → affected qualification → semantic M acceptance → Z01 aggregate acceptance → Z02 retirement → Z03/Z04 callers/bootstrap → Z05 matrix → Z06 review`.

- P13 genuinely lacks a kernel memory backstop and strict envelope-bound temporary storage: [profile.go:51](/Users/vince/Projects/can-lang/tools/native-test-owner/host/profile.go:51). Ledger admission cannot claim those enforcement properties.
- P14's ACK helper is not the actual owner: [P14 evidence:118](/Users/vince/Projects/can-lang/docs/implementation/native-can-tests-plan-2026-09-30/evidence/P14.json:118).
- P23 is actual missing execution, not an administrative signature. It gates 196 rows directly plus 71 conditionally if retained; **267/292 rows potentially depend on it**. Twelve I parents are active and unpromoted, with P14 required.
- Browser mechanisms gate 38 rows. The live longest residual unit chain is `K07→K08→K09→K10→K11→I06→QB0→QB1base→QB2→M21→Z05→Z06`, 12 unfinished vertices. Host/P23 dependencies still join it.
- [lane-plan:132](/Users/vince/Projects/can-lang/docs/implementation/native-can-tests-plan-2026-09-30/lane-plan.md:132) deliberately preserves the aggregate Z01→Z02 barrier. This delays per-file retirement even when a file's own proof could be complete. The 14-node/63-hour/422.25-hour planning estimates are stale and hypothetical.

Process costs can be reduced. Real memory/storage enforcement, independently observed browser behavior, reliable native adapters and a live runner require engineering. Completing the unrelated Can-suite programme is an additional product scope decision.

## 9. Critical path and a bounded wall-time budget

The proposed path is **one real Manolea vertical case → only required native capabilities → parallel probe families → family qualification → per-file caller switch/retirement → final manifest reconciliation**. A general Can-suite retirement project is no longer a prerequisite. P23 should deliver useful execution early. Any revision to the old strict host acceptance contract requires an explicit decision; otherwise its block remains.

Parallel source lanes: (A) auth/services/mail, (B) storage/images/context/MCP, (C) browser/delivery/preview. Shared compiler/runtime edits have one owner. Serialize resource-intensive builds and live campaigns on this Mac; continue unrelated authoring during bounded checks. Use native JavaScript/Bun operations rather than rebuilding them in Can.

The following is a **40-hour planning envelope**, not a measured ETA or guarantee. Count actual wall-time implementation separately from verification, reviews, documentation and waiting. Avoid summing concurrent agent-hours as wall time. Overlap implementation with checks only when an agent is actually implementing. Do not relabel proof-writing as implementation.

| Phase | Wall-time envelope | Implementation allocation | All overhead allocation | Acceptance of phase |
| --- | ---: | ---: | ---: | --- |
| Live vertical case, required runner/profile/adapters | 12 h | 10 h | 2 h | A real Manolea operation, independent result, seeded wrong result, missing-check refusal and cleanup |
| Three file-based port lanes with incremental live integration | 20 h | 16 h | 4 h | Every baseline obligation has an executable Can path; browser assets remain faithful |
| Remaining fixes, caller changes and per-file retirement | 8 h | 6.4 h | 1.6 h | Qualified file dispositions, working active callers and no host verdict policy |
| Total | **40 h** | **32.4 h / 81%** | **7.6 h / 19%** | Actual Manolea replacement |

Each allocation meets the requested 80% implementation target. It is a budget to manage, not fabricated observed performance. If the final phase becomes pure verification, report the changed ratio; do not manufacture code to improve the statistic. Use one compact time record per run/phase. At two-hour checkpoints, diagnose overhead above 20% and batch/defer the named source of overhead before dispatching more identical rows.

There is material schedule uncertainty. Initial cross-file inspection suggests **48–112 total coding/review attention-hours**, including **16–40 hours of runner/profile/capability work**, before host unblock or new findings. Parallel execution can reduce calendar time, but the shared runner/profile can exceed its 12-hour envelope. Start with a **four-hour vertical-case feasibility checkpoint** inside phase one: either show a working subject path and the remaining capability gap, or report the exact blocking mechanism and revised critical path. This does not stop ready authorized work or impose a cap on task completion. **A sub-48-hour finish cannot honestly be promised now.**

Commit policy: land each coherent implementation increment as soon as locally checked, then continue immediately. No wait for a family, broad gate or review sign-off. Use explicit owned paths and serialize Git mutations. Pending qualification is recorded separately from source correctness; it must never hold all finished implementation uncommitted. Require a commit or an explicit current blocker at every handoff. Keep receipts compact and reference the implementation commit.
