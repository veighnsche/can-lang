# Can implementation task list, dependency ordered

24 September 2026. This is the result of the [design preparation](can-design-preparation-2026-09-24.md). It is a **plan**, not a claim that any production change below has shipped. Can is for AI coding agents; correctness, stable contracts and observable product behavior lead, while total tokens per successful agent task is a secondary measured outcome. There are no external users or compatibility requirements. The [disposition ledger](preparation/design-disposition-ledger.md) covers every DI-01–DI-23 item; only accepted mechanisms and qualification work appear as build tasks. The [integrated action contract](preparation/integrated-action-contract.md), [product acceptance matrix](preparation/product-acceptance-matrix.md), and linked topic packets define exact semantics.

## How to execute this graph

`Depends on` is a hard prerequisite for integration or qualification, not necessarily for beginning an isolated branch or test fixture. Each task lists a suitable GPT-6 model and Codex reasoning effort: Astra for difficult contract integration and Sol for implementation. These are assignments, not proof of optimal cost. A task may be split among workers while its lead owns the stated definition of done. After T01, **T02/T03/T06/T07/T18/T19** can run in parallel. T03 unlocks **T04/T05/T08**; T05 and T06 unlock T10, while T03/T05/T06/T07 unlock T21. T10 unlocks **T11/T12/T13**; T21 unlocks T22. T09 integrates the core before T16, while the invoice and browser lanes continue on their own stated prerequisites. Do not merge two workers' compiler or catalogue edits blindly; integrate against one locked revision and rerun affected checks. The [model rationale](can-preparation-model-allocation-2026-09-24.md) applies to delegated work.

For every compiler/catalogue change, add positive, negative and diagnostic-span tests plus regenerated generated TypeScript/goldens as applicable. For every task that edits authored `runtime/` or `tools/runtime/` TypeScript, run `bun run lint:fix:runtime`, `bun run format:runtime`, `bun run check:runtime` and relevant tests; use `bun run lint:runtime --format=agent` for compact diagnostics. Do not hand-edit generated `runtime/catalogue.ts` or pinned vendor files. For observable product tasks, tests must inspect native HTTP/browser/database results, not just a Can assertion or Jev advice. Record actual model/version, compiler revision, environment and failures in each qualification report.

## Deliberately outside this implementation graph

DI-03 finite error-set parameters, DI-08 capture-binding syntax, DI-14a mutation `RETURNING`, DI-17 new native AI wrapper/batch/callable forms, DI-18 static escape/consumed-fault additions, DI-19 unrestricted SDK imports, DI-20 bulk immutable collections, DI-22 named-field constructors and DI-23 multiline grammar remain deferred pending the [ledger's specific reopening evidence](preparation/design-disposition-ledger.md). DI-21 billing/calendar is a later policy-explicit library/example, not a blocker for the demonstrated invoice/webhook/grid gates. DI-10 declarative markup and typed DOM-target scopes remain unselected; existing safe builders and concrete accessibility repairs are in T15/T22/T24. Current SQL statement checks and runtime row validation are described honestly; versioned schema proof is not silently added. Agent comparisons may validate the selected design or trigger a revised design decision, but implementation workers do not invent these mechanisms to make a test pass.
