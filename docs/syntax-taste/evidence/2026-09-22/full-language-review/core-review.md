# Core types, control flow, callables and coordination review

Read-only evidence memo, 2026-09-22. Paths below are relative to `/Users/vince/Projects/can-lang`; line numbers were checked in the current working tree. No implementation changes or test executions. Recommendations are design candidates for the coordinator's consultations, not approved changes. Consulted AGENTS.md, all three review inputs, technical/coordination specifications, callable/coordination implementation notes, checker code and admitted fixtures.

## 1. P1 — Error-set aliases cannot satisfy the confirmed normalization requirement

**Current/evidence.** `docs/implementation/design-revisions.md:19–46` requires language-owned wrappers at fetch and judge, explicitly excludes individual noul/choice/score wrappers, requires inherited handling plus additions/overrides and last-wrapper-wins precedence. R8's `errorset transport` only abbreviates declarations; its own explanation says callers still handle every leaf (`docs/syntax-taste/redundancy-review-2026-09-22.md:469–489`). Thus it fails the requirement even if aesthetically useful elsewhere. `emits [=draft]` equally forwards the original seven failures.

**Better alternative.** Treat the wrapper as a checked normalization policy whose externally visible bound contains its normalized transport error plus any explicitly retained application/AI errors. Its diagnostic detail should be typed and permit selective recovery. Inheritance should resolve handlers by exact failure identity, retaining omitted handlers and replacing a conflicting inherited handler with the last derived definition before checking the resulting outward bound. Start with one base unless multiple-base order is explicitly specified. Do not silently normalize application errors or the additional AI errors; those remain an open policy question. An error-set alias can be independently considered for genuinely shared domain contracts, but cannot be the normalization mechanism.

**Tradeoff/tests.** A wrapper policy adds declaration/checking work but removes repeated handling at the actual boundary. Acceptance: eight-call fetch fixture drops seven-way declarations/arms; a caller recovers from one typed transport detail; derived override wins while another base handler remains inherited; question declarations gain no wrapper layer. Errors precede final `ok` in all examples. Reduced nesting is explicitly not an acceptance criterion (`design-revisions.md:27–29,48–60`).

## 2. P1 — Fix generic error discrimination before erasing aggregate types

**Current/evidence.** Distinct `all_failed<a_failure>` and `all_failed<b_failure>` are genuine distinct error types, but completion patterns are forced to bare names. `compiler/internal/check/completion_matches.go:113–136` rejects type arguments, and `compiler/internal/check/errors.go:180–185` rejects the resulting ambiguity. The composition fixture's identical-leaf variants then need two normalization wrappers and array conversions (`compiler/testdata/current/coordination/aggregate-composition.can:4–68`). `compiler/internal/check/coordination_test.go:34–49` separately tests the bare-arm ambiguity and prohibited array covariance. These are two constraints, not one unavoidable consequence of nominal typing.

**Better alternative.** Evaluate exact specialized domain patterns, e.g. proposed `all_failed<a_failure> => ...` and `all_failed<b_failure> => ...`, using exact nominal specialization for dispatch. A bare name can remain admissible only where its matched bound uniquely determines a specialization. This permits consuming heterogeneous aggregates without first rebuilding their payloads. When one normalized aggregate is actually required downstream, retain explicit elementwise conversion; a named scalar widening function used with existing `.map` should replace the fixture's recursive array conversion. Generic `.map`/callback support must be verified before calling a particular compact rewrite admitted.

**Tradeoff/tests.** A small pattern extension preserves typed details and invariance, but requires decision changes to Q5/Q6 and exact-specialization exhaustiveness/dispatch tests. Test two specializations, duplicate exact arm, missing specialization, still-ambiguous bare arm, preserved error IDs, original payloads and native snapshot identity, and no array covariance. Plain first-success `race` would still have its one aggregate arm; do not casually confuse its implicit aggregate with an ordinary call returning an existing aggregate.

**Refutation.** R7's distribution-owned closed `failure_data` cannot cover arbitrary authored errors and their specializations. Replacing typed payloads with strings would lose the existing contract. R7 B's `variant race_outcome<success> / success / failure_data[]` is invalid under `technical-spec.md:125–129`: arrays cannot be variant leaves, and arbitrary success can be primitive or void. Record envelopes could repair syntax, but they do not solve an extensible typed failure set. Also, “every race needs a bespoke variant” (`redundancy-review...:401`) is false: ignored payloads need no named type (`coordination-spec.md:317–324`, implementation `coordination.md:11`).

## 3. P1 — Expose the existing standard-failure snapshot consistently

**Current/evidence.** Ordinary `[_]` binds only `str` (`compiler/internal/check/completion_matches.go:105–111`), while aggregates expose the read-only `standard_failure` kind, occurrence ID and message (`docs/syntax-taste/coordination-spec.md:253–274`). The inconsistency identified by F2 is real. These standard failures are deliberately outside `emits`, not undeclared domain errors (`technical-spec.md:245`).

**Better alternative.** Make the bound catch form receive `standard_failure`, reusing the same opaque snapshot and projections. This enables kind-specific logging/recovery without parsing diagnostic prose. Preserve the current automatic propagation and handler ownership rules. No raw native cause or public snapshot constructor is needed.

**Tradeoff/tests.** A uniform structured projection is a modest API change; it does not create checked exception freedom or promise recoverability from fatal termination. Tests should show equal occurrence identity through ordinary handling/aggregate observation, canonical kind/message, rejection of construction/update, and a handler's failure escaping rather than being redispatched. Converting standard failures into blanket `emits` entries is a substantially different proposal without supporting evidence here.

## 4. P2 — Coordination's different arm placements express different ownership

**Current/evidence.** Q4 distinguishes per-participant `T` from whole-operation fallback `T[]` (`coordination-spec.md:150–173`); Q5 gives first-success race no participant error arms (`:205–219`). Checker enforces these distinctions (`compiler/internal/check/coordination.go:90–110,137–150,189–202`). The semantics map to four different native Promise operations.

**Better alternative.** Keep the selected four modes and document each with an explicit participant outcome versus aggregate outcome table. Any layout simplification must preserve those regions. A promising narrowly scoped usability check is that diagnostics say whether an arm recovers one element or the whole result. Apply the confirmed failures-before-final-success ordering wherever success/error arms coexist, without changing which region owns an arm.

**Refutation/tradeoff.** R4's nested per-entry errors plus shared fallback does not delete the semantic table. In `Promise.all`, recovering one rejected participant before native selection changes behavior to a different operation; recovery after selection still needs a whole fallback array. In `Promise.any`, turning an early participant error into a local success can make it win. Adding per-entry post-selection handlers may be possible, but requires new provenance and typing rules and is not merely a layout cleanup. Test existing Q12 order, prepare-before-launch, no handler redispatch, and thenable shielding for any rewrite.

## 5. P2 — Exact-name capture hides dependencies; receiver elimination is an overcorrection

**Current/evidence.** `callable combine` captures `prefix` and `suffix` without visible arguments (`compiler/testdata/current/callables/captures.can:15–23,41,50`). The checker resolves these declaration names in the creation environment and requires exact type (`compiler/internal/check/callables.go:119–135`). This is coherent but a declaration parameter rename changes clients' capture requirements.

**Better alternative.** Evaluate an explicit capture-binding clause at reference creation, e.g. illustrative `callable combine with (prefix = left, suffix = right)`, restricted to declared `near` inputs. It makes dependencies visible and decouples local names from parameter names while retaining remaining positional invocation arguments. Captures should still evaluate once, left-to-right, and remain immutable aliases. Syntax is a candidate, not presently admitted.

**Refutation/tradeoff/tests.** R10's receiver-as-first-near proposal also changes method ownership and lookup: methods currently belong to the nominal receiver's defining package and cannot extend foreign records (`technical-spec.md:117`). Those constraints must not disappear by accident. Removing `near` in favor of receiver records instead forces artificial records for multi-value captures. Explicit binding adds source tokens; measure ordinary creation sites before choosing it over tooling. Test differently named locals, missing/extra capture keys, capture evaluation once, receiver evaluation once, independent closure identity, callback error-bound widening and resource captures.

## 6. P2 — Callable type grouping is a small, separable readability improvement

**Current/evidence.** `callable int (int) emits [][] actions` is real admitted syntax (`compiler/testdata/current/callables/captures.can:80`), precisely defined by Q5 (`coordination-spec.md:191–202`). This is a readability issue, not parser ambiguity or type unsoundness.

**Better alternative.** Consider requiring grouping when an array suffix encloses a callable: proposed `(callable int (int) emits [])[] actions`. This separates a callback returning an array from an array of callbacks and retains explicit empty error bounds. A general type-alias facility would solve repeated long signatures too but is a larger feature than this example warrants.

**Tradeoff/tests.** Adds parentheses and a type grammar production. Check callable returning `int[]`, callable array, nested callable, nonempty errors, parser/formatter roundtrip, and exact compatibility. Do not conflate this with R2's choice-arm unification: arms carry static descriptions and registration names and disallow capture (`ai-io-spec.md:293–297`); ordinary callable values alone cannot preserve that metadata through storage without a new contract.

## 7. P2 — General higher-order reuse has a real, deliberately bounded ceiling

**Current/evidence.** `technical-spec.md:137` grants compiler-known catalogue callbacks finite error-bound specialization but requires user-defined higher-order functions to declare a fixed bound. Thus authors cannot express a general callback combinator preserving an arbitrary caller's finite domain-error set, even though built-in `.map` can. Named error-set aliases abbreviate a fixed bound but do not make it polymorphic.

**Better alternative.** First document this limitation explicitly in the user generic model. If authored traversal/retry/composition helpers are a goal, evaluate one explicit finite error-bound parameter, appearing in both callback and outward `emits` contracts, with equality/subset constraints only. This must be a distinct decision from transport normalization and from ordinary data generics. Current data type variables must not masquerade as error sets.

**Decidable candidate rules.** At specialization, each bound variable denotes a finite set of exact nominal error specializations. An actual callback bound must be a subset of its expected bound; union deduplicates by exact type identity; subtracting handled errors is set difference only after checking complete, exact handling of those types. Any errors produced by a handler are then unioned into the escaping set. Reject unresolved variables, recursive/infinite set expansion, and nonfinite bounds. Infer bound variables only from explicitly typed callback arguments and expected signatures, not arbitrary body-effect inference. `standard_failure` remains outside these sets. Named aliases expand finite sets but introduce no variable; normalization consumes particular failures and emits a different public error, which is a behavioral contract change. A signature may therefore express a finite union/subtraction contract without weakening exhaustiveness or exposing a dynamic catch-all.

**Tradeoff/tests.** Adds an effect-polymorphism feature and signature checking complexity; priority is lower until a concrete authored helper proves the need. Test empty and multiple finite bounds, idempotent unions, exact-specialization containment, subtraction only for fully handled failures, handler-introduced errors, substitution through callbacks, forbidden undeclared escapes, and independent data-type specialization. Do not claim this is a compiler defect: the limitation is explicitly selected. Do not remove mandatory public error contracts to obtain it.

## 8. P3 — Correct the review's control-flow and inference claims before redesign

**Evidence/refutation.** F3's examples do not prove chain is neglected or unsuitable: current fixtures use it for sequential encode/decode (`compiler/testdata/current/native/questions.can:137–141`, `codec/roundtrip.can:13–17`). `compiler/internal/check/completion_matches.go:26–58` supports prior-success bindings and collects step errors; ordinary call/chain matches are deliberately terminal (`:18–19`). A nesting redesign remains separate from the confirmed wrapper work. F3's halting-fold need is plausible, but its expressiveness-floor claim is too strong: same-specialization recursion is permitted (`technical-spec.md:133`). A `fold_until` could improve traversal ergonomics/performance; no evidence here proves it necessary for expressibility.

F7's proposed rule that existing values never change admitted type is inaccurate: narrower variants can be assigned to wider named variants (`technical-spec.md:131`, `compiler/internal/types/compatibility.go:23–36`). Generic inference solves equality constraints; it does not search arbitrary instantiations (`technical-spec.md:127`). Prefer precise prose: nominal record/generic invariance, explicit numeric conversions, named-variant inclusion, contextual literal typing, finite equality inference and callable error-subset compatibility.

**Tests/decision scope.** Before changing chain, rewrite one ordinary multi-call example under current grammar and measure recovery/context needs separately from indentation. For inference documentation, cite positive leaf/variant/callable-bound examples and negative array covariance/numeric widening cases. No test change is needed merely to correct misleading review prose. Empty `race with error` truly remains pending (`coordination-spec.md:438–455`), so test deadlines are worth a separate harness review; changing native race semantics to reject emptiness would contradict the current native-mapping contract.
