## §1: keep raw error payload leaves, but make the phase and cause work explicit

The draft's `http::failure_detail` variant listing the seven existing errors (`full-language-review-2026-09-22.md:30-44`) fits current Can semantics: error values are ordinary immutable data and finite variants admit nominal error leaves (`technical-spec.md:125-131`); the runtime validates error leaves by nominal record identity (`runtime/domain.ts:66-68,100-119`). Seven new detail records would duplicate seven already defined field shapes and require separate catalogue entries/conversions. Reusing existing payload types therefore remains the better working recommendation. The split vote (2/3 for reuse, with the third favoring new records) should be recorded as a close representation choice, not consensus on the leaf type.

The important implementation constraint is phase provenance, not the seven names. `runtime/transport/http.ts:13-25` constructs HTTP failures; `runtime/transport/named.ts:20-45` constructs codec/body-limit failures during native encoding and decoding. `runtime/ai/typesafe.ts:19-39` constructs judge request/answer codec failures. In generated judges, question preparation precedes `$canAI.ask`, and authored question handlers/continuation run after it (`compiler/internal/emit/judge.go:235-295`). A whole-judge catch keyed only by nominal error would incorrectly convert `codec::invalid_data` emitted by authored code. Normalize the specific adapter completion before handlers run; do not infer phase solely from `DomainFailure.typeIdentity` or source span. Preserve the original `DomainFailure` token as the new outer occurrence's private cause; `domain.create` already accepts a cause argument (`runtime/domain.ts:18-25,125-130`). The terminal reporter currently prints the outer occurrence and origin but does not traverse domain causes (`runtime/entry.ts:19-29`), so the draft should say the original is retained for internal diagnostics, without implying the current report displays a cause chain.

Concrete tests: for each reachable raw error, assert the outer ID, exact inner leaf identity/fields, and private cause object identity; test envelope fetch never produces intrinsic status error; test native decoder `codec::invalid_data` converts but a question handler or continuation emitting the same nominal error passes through unchanged; test standard failures and AI errors pass through; test one POST and no retry. The existing adapter phases and immutable status-header snapshot need to stay intact (`runtime/transport/fetch.ts:13-44`; `docs/syntax-taste/ai-io-spec.md:154-160`). Uncertainty: the new public type/checker lowering and terminal diagnostic treatment have not been prototyped; neither Jev preference establishes those details.

## §5: keep the snapshot recommendation as a small, optional consistency change

The split vote does not overturn the source asymmetry. Ordinary `[_]` is bound to `str` in `compiler/internal/check/completion_matches.go:105-112`, and generated matching calls `$canStandardMessage` (`compiler/internal/emit/regions.go:480-497`). The opaque `standard_failure` already exists with stable `kind`, `message`, and `occurrence_id` projections (`runtime/failure.ts:6-16,54-57,91-102`; `compiler/internal/check/expressions.go:259-267`). Runtime dispatch already passes the occurrence to a standard handler and never redispatches a handler-produced failure (`runtime/completion.ts:95-111`). This makes `[_] as standard_failure failure` a narrow frontend/emitter change, with no new runtime failure class or change to automatic propagation. The draft §5 (`full-language-review-2026-09-22.md:132-150`) can stand, but should not imply that `kind` becomes an enum: it is a `str` projection, and native causes remain private.

Tests: compile and run a typed `[_]` arm selecting on `failure.kind`, check `message` and `occurrence_id` equal the original snapshot, verify unbound `[_]` still works, verify cause is inaccessible and the snapshot cannot be constructed/updated, and verify a new handler failure escapes. Uncertainty: no ordinary-catch use case yet demonstrates that the extra projection is worth changing established source syntax; the one string vote supports treating this as lower priority than normalization rather than as settled by 2/3.

## §8: revise the argument, keep both calling-convention prototypes open

The draft's phrase “grouped-state ABI” (`full-language-review-2026-09-22.md:179-183`) is imprecise. The current **source call convention** has a final group, checked by `compiler/internal/check/arguments.go:41-67`; the native signature and emitted TypeScript arguments are already flat (`compiler/internal/check/native_program.go:47-86`; `compiler/internal/emit/judge.go:218-234`; `compiler/internal/emit/llm.go:10-29`). Callable references are blocked by an explicit kind gate permitting only `fn` and `fetch` (`compiler/internal/check/callables.go:11-29`), consistent with the spec's lack of a selected reference contract (`docs/syntax-taste/ai-io-spec.md:95-99`). State field names and serialization are independently compiler-owned (`compiler/internal/check/judge.go:10-33`; `compiler/internal/emit/judge.go:223-234`).

Two votes favor extending callable contracts to represent grouped state, one favors the draft's explicit per-parameter markers. The draft can keep flat markers as a **prototype**, since they directly permit ordinary positional callback calls without accidentally serializing unmarked inputs; however, it should not dismiss group-aware callable types as mere special-case spread. Preserving the user's selected grouped spelling is a real benefit. Conversely, a grouped callable type alone might not interoperate with existing flat callback slots such as `.map`: it needs a defined adaptation from one callback item to the grouped state invocation. Recommend revising §8 to compare both prototypes under one acceptance test instead of claiming the flat design is preferred: can `callable draft` be passed to `.map` and invoked with the correct state object, including zero fields and mixed `given`/`state`, without handwritten forwarding functions or unintended disclosure? Preserve exact field keys, finite error bounds and one judge batch. Reject implicit last-record state in either design. If grouped callables require every higher-order API to gain a second callback family, flat markers likely win ergonomically; if a checked adapter preserves ordinary callback types and grouped source calls, retaining the selected spelling may be cheaper. Current code does not establish which is true.
