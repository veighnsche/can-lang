# Platform, testing, and tooling review (read only)

Scope: independently checked `AGENTS.md`, the two 2026-09-22 review inputs, `design-revisions.md`, P1–P15, the companion C/Q/A specs, current compiler/runtime sources, and the implementation READMEs. This is advice for the coordinator's decision packet, not an approved redesign. No Jev call or implementation edit was made here. Priorities reflect correctness and usefulness for the current **implemented** compiler (all fifty tasks are marked complete in `docs/implementation/coverage.md:1-7`), not the old milestone order.

1. **P0 — Bound assertion execution without changing production race semantics.** `race with error` on an empty spread deliberately maps to pending `Promise.race([])` (`docs/syntax-taste/coordination-spec.md:434-455`); a transaction owner can also remain pending (`docs/syntax-taste/platform-testing-spec.md:989-999`). Every `fn` assertion is mandatory, but `runtime/assert/runner.ts:75-127` awaits each root and the suite serially with no deadline. One empty race in an assertion therefore prevents a report indefinitely. Add a runner or process-supervisor deadline configured outside Can, report the root plus pending frame paths and phases already exposed by `barrierState` (`runtime/assert/barrier.ts:119-122`), and fail the suite. Keep the production empty-race mapping intact: `Promise.race([])` is the selected native contract, so changing its result to a domain error would violate native reuse. A deadline must explicitly say whether it just terminates the assertion process (safe, no cleanup claim) or tries to cancel owned work (new semantics); choose the former first. Test with an actual emitted Can assertion containing an empty race, plus a pending nested fixture, rather than only a runtime unit timer (`runtime/test/coordination.test.ts:214-220`). This is more urgent than F1's extension-policy discussion.

2. **P1 — Narrow the native-testing gap to authored request construction.** F2 is right that native `judge`, `llm`, `fetch`, and question declarations lack mandatory source `asserts` (`docs/syntax-taste/ai-io-spec.md:91-103`), while the current test model distinguishes supplied consumer completions from raw provider and Bun evidence (`docs/syntax-taste/platform-testing-spec.md:312-353`). The review overstates that all native behavior is untested: P4 already requires raw requests/responses through real adapters, and the catalogue has per-operation conformance (`docs/syntax-taste/platform-testing-spec.md:72-83`). The remaining question is whether an author's interpolated prompt, options, metadata, and branch thresholds receive regression coverage when edited. A narrowly scoped prepared-request fixture or snapshot assertion for each reached native declaration would cover that deterministic surface; live model output must stay outside mandatory assertions. Test one real authored question where a changed `asks` expression changes serialized request bytes but a supplied completion still passes. Do not simply require ordinary `asserts` on each question: questions run only within a judge (`ai-io-spec.md:95-97`), and that grammar cannot express a stand-alone invocation.

3. **P1 — Make resource escape diagnostics transitive if making them static.** F4 correctly identifies P6's runtime-only safety promise (`docs/syntax-taste/platform-testing-spec.md:437-450`), but its proposed simple syntactic must-not-escape rule is too small. Can records and arrays may contain resource values (`docs/syntax-taste/technical-spec.md:129`), and callables retain captured values (`:135`). `sql::with_transaction<T>` currently rejects `void` and checks the `decision<T>` shape, with no recursive resource-free test on `T` (`compiler/internal/check/transaction.go:73-105`); a direct source-level rule would miss `record holder { sql::transaction tx }`, `holder[]`, or a captured callable returned through `T`. Runtime ownership remains essential for late callbacks and concurrent leases (`platform-testing-spec.md:427-460`; `runtime/owner.ts:48-63`). Define a recursive "contains scoped handle" predicate for result types, field construction, closure capture, and stored values, and test accepted in-scope use plus rejected direct/indirect escape. Treat it as earlier feedback, not a substitute for runtime checks. The current checker comment says scope machinery rejects every escape (`compiler/internal/check/transaction.go:36-40`), while the generic result admission in the same file does not show such a check; verify with a compiling fixture before claiming an exploitable compiler defect.

4. **P1 — Keep the closed platform boundary unless a concrete missing capability proves it wrong.** F1's option (b), project-authored declarative bindings to arbitrary named native APIs (`docs/syntax-taste/design-review-2026-09-22.md:42-62`), conflicts with the approved distribution-only boundary (`docs/syntax-taste/decisions.md:2240-2274`) and P2's requirement that every catalogue operation have a Can contract, Bun recipe, assertion substitution, and target conformance (`docs/syntax-taste/platform-testing-spec.md:59-89`). A signature manifest cannot establish native API behavior, mutation, exceptions, resource lifetime, or safe test substitution. Example: direct binding to `Bun.file` might look typed but needs path confinement, byte budgets, copy/ownership, and error mapping; direct `Headers` access needs the normalized `set-cookie` contract at P1:29-39. The closed HTML tag list (`platform-testing-spec.md:648-659`) is a separate domain whitelist, not evidence that arbitrary Bun extension is needed. Document catalogue request/release criteria and test candidate gaps against one closed user program. If a narrowly bounded extension survives that test, specify its adapter semantics and conformance obligations first; do not describe an arbitrary native binding as mere configuration. The current 144-operation inventory is already gated (`docs/implementation/coverage.md:5-7`), so F1 does not gate the P0 harness fix.

5. **P2 — Preserve typed application failures when simplifying `all_failed`.** R7 suggestion A proposes one distribution-closed `failure_data` variant (`docs/syntax-taste/redundancy-review-2026-09-22.md:391-455`). This cannot represent project-defined domain errors from arbitrary race participants: Q6 specifically admits project error and variant leaves in `all_failed<F>` and checks their finite aggregate (`docs/syntax-taste/coordination-spec.md:228-326`). Either the closed variant loses the original error identity/payload or grows an untyped catchall, both contrary to contract-first typing. R7 suggestion B, a value result, could be examined, but it forces explicit conversion at every caller and changes completion handling; no evidence shows that it reduces real code. Target the observed conversion scaffolding (`docs/implementation/design-revisions.md:74-81`) by testing an explicit, checker-known widening operation for compatible named failure variants, leaving race's `Promise.any` and ordered aggregate adapter intact. First compare a two-race composition fixture's source size and preserved selective recovery before replacing Q6 wholesale.

6. **P2 — Retain call-site fixture binding; remove repeated content with checked reuse.** R9's assertion-level proposal uses `model::recent_count#0` (`docs/syntax-taste/redundancy-review-2026-09-22.md:528-545`). P3 defines `#0` as preorder ordinal in the typed syntax tree, stable under formatting only (`platform-testing-spec.md:199-215`). Adding an earlier call silently retargets that fixture, and a helper with repeated/recursive invocations still needs occurrence paths and FIFO queue ownership (`:221-246`). The proposal's optional removal of expected-argument checking would discard a useful mismatch detector (`:248-278`). Prefer named fixture templates or data sharing that are expanded and typechecked at the lexical `when` site, retaining argument comparison and full root identity. Demonstrate on the four duplicated SQL rows in `examples/native-ai/src/model/model.can`, then mutate the query arguments and ensure the fixture fails rather than silently matching an unrelated call.

7. **P2 — Repair tooling claims and improve the actual editor bottleneck.** F9 says the current language has no formatter (`docs/syntax-taste/design-review-2026-09-22.md:161-175`), but `canlc parse --render FILE.can` invokes `syntax.Format` (`compiler/current_parse.go:16-47`), and parser/render tests exist (`compiler/current_parse_test.go:27-47`). The real limitation is that rendering omits comments and writes to stdout (`compiler/internal/syntax/README.md:3-15`), so it is not a safe write-back formatter or LSP formatting action. Diagnostics already exist via LSP (`compiler/lsp.go:261-304`), but resolve/check errors are anchored on the file's first line instead of the source token (`compiler/internal/driver/diagnostics.go:16-20,64-72,134-165`), and the editor publishes parse/resolve/check only (`editors/vscode/README.md:26-37`). The next tooling task should retain comments/trivia in canonical formatting and add source spans to the highest-frequency semantic errors; then add limited code actions for missing arms/emits and fixture argument mismatches. This is a precise follow-up to F9, not a missing-formatter greenfield project.

8. **P2 — Reconsider authored numeric error IDs as a separate contract, not a JSON complaint.** C9 explicitly says the semantic identity of an error is package/declaration plus concrete generic arguments, not the numeric ID (`docs/syntax-taste/technical-spec.md:236-245`). The source nevertheless requires an author-chosen global integer (`docs/syntax-taste/decisions.md:1619-1640`), an exactly matching active/retired JSON registry (`platform-testing-spec.md:122-173`), lock snapshots, and whole-graph uniqueness checks (`compiler/internal/project/graph.go:314-333,366-391`; `graph_test.go:232-249`). That duplicates identity in source and configuration, creates merge/collision work across dependencies, and can reject a correct nominally unique program. The numeric ID does serve a specified purpose: stable numbers in error reports (`decisions.md:1635-1640`), so do not remove it as if it were unused. Ask which report consumer genuinely needs a human-maintained number stable across package/name changes. With zero external users and no compatibility constraint, a cleaner candidate is package-qualified error identity as the authority, with compiler-generated deterministic diagnostic codes if numeric telemetry is wanted; keep an explicit numeric alias only where a concrete external protocol demands it. Test rename, dependency merge, retirement, and generic specialization under either choice. This deserves its own design decision; F8's claim that these files are "JSON Schema validated" is inaccurate: P2 defines exact compiler validation, and SQL descriptors go through PostgreSQL parse/scan (`compiler/internal/sql/descriptors.go:36-156`). Moving SQL descriptors into Can would not make database schemas statically proven (`platform-testing-spec.md:1000-1019`).

F6's proposed raw Can-versus-TypeScript token ratio (`docs/syntax-taste/design-review-2026-09-22.md:127-137`) should also be interpreted cautiously: Can includes bounds and executable assertions that a short TS comparison may omit. Compare equivalent TS types, tests, fixtures, and adapters across realistic edits, recording edit count, diagnostics, and tokens before choosing syntax relief.

**Order:** fix assertion liveness/reporting; prove the scoped-handle escape boundary and native request coverage with concrete fixtures; decide whether any platform gap warrants catalogue expansion; then simplify fixture/error composition and improve editor spans/formatting. No compatibility work is justified (`AGENTS.md:1-3`); all changes should preserve native JS/Bun operations with only contract and immutability adapters (`AGENTS.md:3`).
