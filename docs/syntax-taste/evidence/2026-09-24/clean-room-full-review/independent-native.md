# Independent native/completion design review (24 September 2026)

Scope: current compiler/runtime, the live examples for native AI, streams, sockets, files and processes, and normative C4–C9/Q/A contracts. I did not inspect earlier reviews, consultations, verdicts, or disposition files. This is a static design review; the miniature examples below identify consequences of current contracts, not new conformance-test results. Priorities describe importance for a general frontend/backend SaaS language, not implementation urgency alone. No compatibility requirement applies.

## Confirmed semantic issues

### 1. [P1] A transaction callback can return a closed transaction handle as successful data

`with_transaction<T>` checks only that `T` is not `void`; it builds `decision<T>` and returns `T` ([compiler/internal/check/transaction.go:55–82, 90–140](/Users/vince/Projects/can-lang/compiler/internal/check/transaction.go#L55)). General Can records and arrays may contain resources ([technical-spec.md:129–143](/Users/vince/Projects/can-lang/docs/syntax-taste/technical-spec.md#L129)). The callback receives `sql::transaction`, and its result is passed through after `withScope` returns ([runtime/platform/sql/transaction.ts:199–229](/Users/vince/Projects/can-lang/runtime/platform/sql/transaction.ts#L199)); `withScope` drains/closes scoped resources before returning its successful completion ([runtime/owner.ts:462–484](/Users/vince/Projects/can-lang/runtime/owner.ts#L462)). A callback with `T = record escaped { sql::transaction handle }` can therefore construct `sql::commit<escaped>(escaped(tx))`. The caller receives an apparently successful nominal value holding a token that fails with `resource_state` on use. The same applies to arrays or nested records containing the handle.

Counterevidence: the owner checks scope and refuses actual use after close, so this is not unsafe resource reuse ([runtime/owner.ts:153–170](/Users/vince/Projects/can-lang/runtime/owner.ts#L153)). `near`/participant capture analysis already traverses resource-bearing data ([compiler/internal/ir/resources.go:5–44](/Users/vince/Projects/can-lang/compiler/internal/ir/resources.go#L5)). Recommendation: reject `T` when it transitively contains `sql::transaction` or a callable capturing one. The narrow alternative is a runtime-only contract that admits dead handles as data, but it makes a success type misleading. This need not become a language-wide affine type system.

### 2. [P2] A first-success race suppresses an already observed standard fault without a diagnostic

In `race`/`Promise.any`, earlier failed participants are recorded in `rejected`; when success arrives, `firstSuccess` includes every preceding failed index, and `publish` marks those indices selected ([runtime/coordination.ts:61–82](/Users/vince/Projects/can-lang/runtime/coordination.ts#L61)). The owner emits a standard-failure diagnostic only for a failed result *outside* `selected` ([runtime/owner.ts:399–403](/Users/vince/Projects/can-lang/runtime/owner.ts#L399)). Thus `race` between a participant throwing a `native_exception` promptly and another succeeding later returns success with no caller error and no late-failure diagnostic. The normative text explicitly says earlier standard failures never reappear, while only *late* standard failures get diagnostics ([coordination-spec.md:371–381, 455–461](/Users/vince/Projects/can-lang/docs/syntax-taste/coordination-spec.md#L371)).

Counterevidence: the result correctly follows native `Promise.any`; failed domain alternatives are expected losers, and every promise is observed. Recommendation: preserve native first-success selection and success completion, but report every losing *standard* failure regardless of whether it settled before or after the winner. Alternatively make suppression an explicit race policy. The current timing-dependent visibility of a native/programming fault is a poor observability contract for a service.

## Deliberate scope choices with high operational cost

### 3. [P1] Successful early settlement may still prevent clean shutdown forever

The owner retains all launched participants and resource leases until settlement ([runtime/owner.ts:373–450](/Users/vince/Projects/can-lang/runtime/owner.ts#L373)); root drain waits until every group and callback disappears ([runtime/owner.ts:526–567](/Users/vince/Projects/can-lang/runtime/owner.ts#L526)). The selected contract has no loser cancellation: even after `race` returns a usable success or `concurrent` returns a selected failure, a never-settling participant can hold the root open indefinitely ([coordination-spec.md:447–497](/Users/vince/Projects/can-lang/docs/syntax-taste/coordination-spec.md#L447)). A resource close deadline bounds that close caller's wait but does not revoke a live lease. Example: race a prompt but successful cache request against a stuck user-authored callback, then finish CLI `main`; the program cannot exit cleanly. The same owner can block server shutdown.

Counterevidence: this is honest and safe with respect to resource lifetime; fetch has its own abort/deadline, and external supervision can kill a stuck process. Recommendation: keep native Promise selection but define an explicit structured *group lifetime* option for cancellable catalogue calls, with no rollback claim, plus a bounded shutdown disposition for uncancellable work. The alternative is to retain the current indefinite drain and make every production boundary carry a host-level termination policy. This is a policy decision, not a runtime defect.

### 4. [P1] An empty dynamic `race with error` is an uncatchable permanent wait

The checker accepts a spread of any array of nullary callables; it has no nonempty proof ([compiler/internal/check/coordination.go:46–61](/Users/vince/Projects/can-lang/compiler/internal/check/coordination.go#L46)). Lowering snapshots the array and pushes zero participants if it is empty ([compiler/internal/emit/coordination.go:53–62](/Users/vince/Projects/can-lang/compiler/internal/emit/coordination.go#L53)). `settle("race", [])` awaits native `Promise.race([])` ([runtime/coordination.ts:89–97](/Users/vince/Projects/can-lang/runtime/coordination.ts#L89)); the contract explicitly chooses permanent pending and gives no handler arm a chance to run ([coordination-spec.md:423–445](/Users/vince/Projects/can-lang/docs/syntax-taste/coordination-spec.md#L423)). For a SaaS request, an empty candidate set can pin a request/task until external termination.

Counterevidence: this exactly matches native JS, and `race`/`Promise.any` gives `all_failed([])` rather than hanging. Recommendation: either require a nonempty collection witness for runtime spreads into `race with error`, or classify empty expansion as an explicit domain outcome before invoking native `Promise.race` for nonempty inputs. A weaker alternative is to keep this behavior and require a visible source guard at every dynamic spread. Native reuse does not require silently accepting an unusable empty aggregate.

### 5. [P2] Native recovery is asymmetric between judgment/fetch and generation

`wrap` accepts only fetch, judge, or another wrapper as a base ([compiler/internal/resolve/native.go:75–88](/Users/vince/Projects/can-lang/compiler/internal/resolve/native.go#L75)). Its two-table policy can distinguish native infrastructure failures from authored failures of the same error kind, invoke a target once, and recover or forward exactly once ([ai-io-spec.md:236–269](/Users/vince/Projects/can-lang/docs/syntax-taste/ai-io-spec.md#L236)). LLM is an equally native network operation, but its extensive intrinsic error set must be authored explicitly and conversions can only be made in ordinary callers ([ai-io-spec.md:73–90](/Users/vince/Projects/can-lang/docs/syntax-taste/ai-io-spec.md#L73)). A function wrapping `llm` can catch `codec::invalid_data`, but cannot tell whether it came from authored `asks` computation or native response decoding. Fetch/judge policy has exactly that distinction.

Counterevidence: an ordinary named function can adapt an LLM outcome, and unknown standard faults remain outside both policy tables. Recommendation: either extend the existing provenance-aware `wrap` root to LLM, preserving its grouped-state signature, or explicitly make `wrap` a fetch/judge-specific abstraction and provide an equally precise generation policy surface. Avoid making LLM callers infer origin from an error name; the runtime already retains the origin fact privately.

### 6. [P2] AI batches are validation-atomic but not effect-atomic, while generated records hide the partial-work boundary

Judge lowering evaluates registration/preparation expressions sequentially, returns on the first failed preparation, sends one request, and then runs selected handlers sequentially with early return on failure ([compiler/internal/emit/judge.go:244–294](/Users/vince/Projects/can-lang/compiler/internal/emit/judge.go#L244)). The AI adapter validates all answers before any handler ([runtime/ai/typesafe.ts:98–137](/Users/vince/Projects/can-lang/runtime/ai/typesafe.ts#L98)). Generated-record question runners likewise call field handlers in order and construct the record only after all succeed ([compiler/internal/emit/judge.go:163–177](/Users/vince/Projects/can-lang/compiler/internal/emit/judge.go#L163)). Those handlers and descriptor expressions are ordinary executable Can code and may call effectful `emits []` functions; the spec acknowledges that earlier authored effects are not rolled back ([ai-io-spec.md:163, 181](/Users/vince/Projects/can-lang/docs/syntax-taste/ai-io-spec.md#L163)). Example: field A handler writes an audit row, field B handler fails; no output record exists, yet the audit row exists. Repeating the judge may repeat it.

Counterevidence: answer validation *is* whole-batch, and the no-partial-result rule is consistent. Recommendation: state the exact commit boundary in generated-record and judge-facing documentation and make effectful handler use visibly deliberate. A stronger alternative is a separate prepare/map phase constrained to total computation followed by explicit effect application, but that would need an effect discipline not otherwise selected. Do not describe the current batch as transactional.

## Ergonomic composition constraints; needs product validation

### 7. [P2] Grouped AI state does not compose with the callable/coordination algebra

Grouped state is mandatory at every judge/LLM call, yet neither can be referenced as an ordinary callable because the callable type cannot express the group ([ai-io-spec.md:181–187](/Users/vince/Projects/can-lang/docs/syntax-taste/ai-io-spec.md#L181); [compiler/internal/check/callables.go:13–32](/Users/vince/Projects/can-lang/compiler/internal/check/callables.go#L13)). Coordination spread accepts only arrays of nullary callables ([compiler/internal/check/coordination.go:46–61](/Users/vince/Projects/can-lang/compiler/internal/check/coordination.go#L46)). A dynamic array of `(account state) -> judge` tasks therefore requires one named ordinary wrapper for the judge and another capture setup for each state value; `examples/native-ai/src/oracles/oracles.can` shows `review_bundle` and `draft_account` wrappers that forward every error arm ([lines 83–121](/Users/vince/Projects/can-lang/examples/native-ai/src/oracles/oracles.can#L83)). This is a real expressiveness/verbosity boundary, not a correctness failure.

Counterevidence: direct judge/LLM calls and ordinary named wrappers work, preserve explicit public errors, and avoid anonymous source functions. Recommendation: validate dynamic AI fan-out as a real SaaS use case before adding syntax. If needed, admit a named grouped-state partial application that yields a nullary callable while retaining the original error bound and assertion identity. Keeping only named wrappers is coherent if such fan-out is rare; it should be recognized as an intentional tax rather than a generic coordination capability.

The positive composition evidence matters: protected completion boxes prevent thenable data from being assimilated by JS Promises ([runtime/completion.ts:13–49, 83–121](/Users/vince/Projects/can-lang/runtime/completion.ts#L13)); the four modes actually invoke `Promise.all`, `allSettled`, `any`, and `race` ([runtime/coordination.ts:84–111](/Users/vince/Projects/can-lang/runtime/coordination.ts#L84)); native-origin policy keys use private provenance rather than error names ([runtime/failure.ts:19–59](/Users/vince/Projects/can-lang/runtime/failure.ts#L19)); and recursive capture scanning protects resources inside nominal records and arrays ([runtime/owner.ts:181–224](/Users/vince/Projects/can-lang/runtime/owner.ts#L181)). The findings above concern the contracts at the edges of those mechanisms.

Unproven need: I did not establish that real applications require dynamic batches of judge/LLM callables, general-purpose cancellation of arbitrary Can functions, or effect purity for AI handlers. Those are product-design choices to validate with representative SaaS workflows. Findings 1, 2 and 4 follow directly from current compiler/runtime paths; findings 3, 5 and 6 identify documented policy consequences. No source edit or live provider call was made.
