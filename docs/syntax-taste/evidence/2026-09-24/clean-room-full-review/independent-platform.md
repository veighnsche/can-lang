# Clean-room platform boundary review (24 September 2026)

Scope: current source and examples only. I did not inspect prior reviews or consultations. This is a language-design assessment for authoring an ordinary front-and-back SaaS product, not an implementation plan or a claim that every application feature belongs in the language. The baseline of nominal immutable records, named functions, explicit public errors, attached assertions, native AI forms, and grouped state is coherent. Strong existing boundaries include opaque `html::safe` rendering, compiler-derived JSON/form schemas, bounded SQL row decoding, static route mount checks, local dependency locks, and Bun-backed platform operations.

## 1. [P0, language/tooling boundary] SQL descriptors verify query shape, not database schema or result correspondence

Evidence: descriptor checking verifies the manifest's parameter record fields and that row fields are SQL-compatible at [`compiler/internal/check/sql_descriptors.go:47`](/Users/vince/Projects/can-lang/compiler/internal/check/sql_descriptors.go:47); it then checks statement syntax/cardinality/parameter sites at [line 84](/Users/vince/Projects/can-lang/compiler/internal/check/sql_descriptors.go:84). There is no schema snapshot in the parsed project manifest fields at [`compiler/internal/project/manifest.go:91`](/Users/vince/Projects/can-lang/compiler/internal/project/manifest.go:91). More decisively, a positive compiler test accepts `SELECT id FROM accounts LIMIT $1` with a four-field `wide_row(id, display_name, note, raw)` at [`compiler/internal/check/sql_test.go:20`](/Users/vince/Projects/can-lang/compiler/internal/check/sql_test.go:20) and [line 84](/Users/vince/Projects/can-lang/compiler/internal/check/sql_test.go:84). Thus current checking does not validate selected aliases/count against the row record, regardless of whether the database table exists. Runtime decodes rows and returns `sql::schema_mismatch` on incompatible data at [`runtime/platform/sql/pool.ts:205`](/Users/vince/Projects/can-lang/runtime/platform/sql/pool.ts:205).

Concrete scenario: a migration renames `display_name` to `name` or changes nullable status. Can source and manifest can continue to compile, and an account page fails only after the deployed query runs. The present runtime validation is a valuable containment guarantee, but does not satisfy compile-time schema safety. Decide whether the promise is a checked query against a versioned schema snapshot (migrations/introspection as build input) or an intentionally runtime-validated prepared query. If the latter, document that guarantee clearly and invest in migration-driven integration checks; avoid presenting syntax-checked SQL as static database type safety. This spans language/tooling: migration execution and deployment orchestration need not become Can syntax.

## 2. [P1, package contract] Independent dependencies can collide in both package names and error IDs

Evidence: the graph rejects the same package name from any two directories, even when nominal IDs otherwise include dependency keys, at [`compiler/internal/project/graph.go:264`](/Users/vince/Projects/can-lang/compiler/internal/project/graph.go:264) and [line 273](/Users/vince/Projects/can-lang/compiler/internal/project/graph.go:273). Each project stores explicit application error IDs in its registry at [`compiler/internal/project/lock.go:13`](/Users/vince/Projects/can-lang/compiler/internal/project/lock.go:13), and graph validation rejects an active or retired ID claimed by any other dependency at [`compiler/internal/project/graph.go:375`](/Users/vince/Projects/can-lang/compiler/internal/project/graph.go:375). Source declarations, registries, and dependency lock snapshots must agree at [`compiler/internal/project/graph.go:323`](/Users/vince/Projects/can-lang/compiler/internal/project/graph.go:323) and [line 345](/Users/vince/Projects/can-lang/compiler/internal/project/graph.go:345).

Concrete scenario: two independently authored Can dependencies each export a `models` package or each allocate application error ID `1000000`; an application cannot consume both without changing one dependency's source and lock/registry snapshots. This is a composability problem before a package registry is built. Preserve nominal identity and explicit errors, but make imports resolve through dependency-qualified aliases and scope error IDs by module identity (or allocate collision-free IDs at link/build time). The counterargument is that a globally unique namespace and numeric IDs simplify generated runtime dispatch; this simplicity puts coordination costs on every author of independently reusable packages. Editor support is present—[`compiler/lsp.go:70`](/Users/vince/Projects/can-lang/compiler/lsp.go:70) and [`editors/vscode/README.md:1`](/Users/vince/Projects/can-lang/editors/vscode/README.md:1) describe live diagnostics and go-to-definition—so this is a package contract concern, not absence of basic tooling.

## 3. [P1, language] Parameterized resource paths are outside the router contract

Evidence: the checker requires a literal route and named callback at [`compiler/internal/check/http.go:304`](/Users/vince/Projects/can-lang/compiler/internal/check/http.go:304), explicitly rejects path segments beginning `:` at [line 346](/Users/vince/Projects/can-lang/compiler/internal/check/http.go:346), and runtime dispatch performs exact path lookup at [`runtime/platform/router.ts:57`](/Users/vince/Projects/can-lang/runtime/platform/router.ts:57). Existing examples mount `/accounts/search` and `/dashboard/summary` as static paths at [`examples/account-search/src/web/web.can:103`](/Users/vince/Projects/can-lang/examples/account-search/src/web/web.can:103).

Concrete scenario: an edit page at `/accounts/7`, tenant routes at `/org/acme/projects/12`, or webhook path token cannot be mounted as one typed route. An ID can be carried in a query string with the same HTTP method, so CRUD is still implementable; the gap is for integrations, navigable resource URLs, and products that require IDs in path segments. Add typed path parameters with explicit parse/error behavior and retain static ambiguity checks; alternatively admit a constrained dynamic segment pattern and expose validated raw captures to the callback. The current exact routing gives simple collision and traversal guarantees, but those can be preserved with a deterministic precedence model. This is a language/platform contract gap when resource paths are required, not a claim that all SaaS APIs are blocked.

## 4. [P1, language] Form, route and HTML names are three independent string contracts

Evidence: the form record fields are declared at [`examples/form-validation/src/records/records.can:5`](/Users/vince/Projects/can-lang/examples/form-validation/src/records/records.can:5), while render code spells `name`, `tags`, `note`, result ID and `/signup/validate` independently at [`examples/form-validation/src/render/render.can:46`](/Users/vince/Projects/can-lang/examples/form-validation/src/render/render.can:46). The route spells `/signup/validate` again at [`examples/form-validation/src/web/web.can:48`](/Users/vince/Projects/can-lang/examples/form-validation/src/web/web.can:48). Runtime form decoding rejects unknown fields and enforces presence at [`runtime/platform/form.ts:60`](/Users/vince/Projects/can-lang/runtime/platform/form.ts:60); htmx target IDs are validated as strings at [`runtime/platform/html.ts:176`](/Users/vince/Projects/can-lang/runtime/platform/html.ts:176), but are not linked to document IDs.

Concrete scenario: renaming `signup_results` in one place silently breaks fragment updates; renaming `tags` in the record creates a runtime invalid request when the browser submits the old field. The typed decoder and HTML escaping are strong, but do not connect the authoring contract. Add first-class typed route references and form field/target references that lower to existing strings and native HTML; or use a compiler checked template/component layer over the existing opaque tokens. A library of constants reduces duplication but cannot statically prove that a field or target exists in a rendered page. This is a language ergonomics and correctness issue at the full-stack boundary.

## 5. [P1, language] HTML safety is sound, while routine page construction makes structural errors dominate author code

Evidence: the 82-line signup renderer spends [`examples/form-validation/src/render/render.can:43`](/Users/vince/Projects/can-lang/examples/form-validation/src/render/render.can:43) through [line 78](/Users/vince/Projects/can-lang/examples/form-validation/src/render/render.can:78) constructing tags/attributes/nodes one call at a time, then lists three public construction errors. The accounts page is similar at [`examples/account-search/src/render/render.can:53`](/Users/vince/Projects/can-lang/examples/account-search/src/render/render.can:53). `html::element` checks applicability, child constraints, duplicate attributes and nested forms at runtime at [`runtime/platform/html.ts:245`](/Users/vince/Projects/can-lang/runtime/platform/html.ts:245).

Concrete scenario: adding a labeled input or a navigation bar entails dozens of named temporaries and failure branches, which scales poorly across a product UI. Preserve opaque safe fragments and native `Bun.escapeHTML` lowering, but consider a checked declarative HTML form or component syntax whose literal tag/attribute structure can be rejected at compile time, leaving only dynamic URL/condition errors. An ordinary Can helper library can package common widgets and should be tried first, yet it cannot remove call-by-call construction and runtime errors for otherwise static structure. This is a language surface choice, not a request for a browser framework.

## 6. [P1, language/library boundary] Form projection is too shallow for common typed input while JSON has a separate richer schema

Evidence: [`compiler/internal/types/form_schema.go:18`](/Users/vince/Projects/can-lang/compiler/internal/types/form_schema.go:18) accepts only a record of `str`, `str[]`, or `option::value<str>`; [`runtime/platform/form.ts:64`](/Users/vince/Projects/can-lang/runtime/platform/form.ts:64) directly projects those shapes, with no scalar parse or nested projection. The form example models `tags` and `note`, showing useful repeated/optional semantics at [`examples/form-validation/src/records/records.can:5`](/Users/vince/Projects/can-lang/examples/form-validation/src/records/records.can:5).

Concrete scenario: a signup form with an integer seat count, checkbox, date, or repeated rows must decode as strings and perform manual validation/construction elsewhere; the inferred form record no longer describes the validated application value. Keep the wire form deliberately shallow if desired, but then provide a composable typed parse/validation layer with field paths and accumulated errors, rather than expanding the form codec into arbitrary nested JSON conventions. The counterargument is that HTML forms are string-oriented and business validation belongs in functions; that is valid, but the language needs a scalable bridge from wire strings to nominal application records. This is a boundary design issue, not evidence that every input type should decode implicitly.

## 7. [P1, platform architecture] The closed native catalogue makes ecosystem growth a compiler/runtime change

Evidence: the catalogue explicitly has one authored `catalogue.json` and no project-supplied registration API at [`compiler/internal/catalogue/README.md:1`](/Users/vince/Projects/can-lang/compiler/internal/catalogue/README.md:1). The manifest admits only dependencies/assets/SQL beside its mandatory fields at [`compiler/internal/project/manifest.go:91`](/Users/vince/Projects/can-lang/compiler/internal/project/manifest.go:91); dependencies resolve to confined local directories at [`compiler/internal/project/graph.go:150`](/Users/vince/Projects/can-lang/compiler/internal/project/graph.go:150). Package names are globally unique at [line 273](/Users/vince/Projects/can-lang/compiler/internal/project/graph.go:273).

Concrete scenario: integrating a billing SDK, queue client, observability exporter, or specialized identity provider requires either hand-built HTTP in Can or adding its API, error types, adapter and lowering to the compiler-owned inventory. Ordinary Can packages can share business logic, and local lock snapshots are reproducible. Yet a broad Bun ecosystem is not reachable through a supported typed foreign boundary. Keep core catalogue sealed, but define a narrow audited native-module adapter format or foreign function interface with explicit type/error/immutability conversions and assertion rules. A package registry/download command is separate tooling and need not come first. The counterargument is that a sealed catalogue is easier to secure and reason about; make an extension seam narrow and capability-limited rather than opening arbitrary JS execution in Can source.

## 8. [P2, language] SQL mutation contracts exclude returned rows and force avoidable read-after-write paths

Evidence: `CheckCardinality` requires row-returning descriptors to be `SELECT` with a top-level bound `LIMIT` and requires `execute` to be a mutation without `RETURNING` at [`compiler/internal/sql/cardinality.go:24`](/Users/vince/Projects/can-lang/compiler/internal/sql/cardinality.go:24). The SQLite example performs `rename_note` and then `fetch_note` as separate operations at [`examples/sqlite/src/main.can:28`](/Users/vince/Projects/can-lang/examples/sqlite/src/main.can:28) and [line 79](/Users/vince/Projects/can-lang/examples/sqlite/src/main.can:79).

Concrete scenario: create an account and obtain generated ID/default fields, or update a record and render the canonical saved value. PostgreSQL/SQLite can return these in one native mutation; Can requires another query, introducing extra round trips and potential races unless explicitly wrapped in a transaction. Admit a bounded mutation-returning descriptor for supporting dialects and reuse the existing row codec/cardinality contract, or consciously keep a portable lowest-common-denominator SQL subset and recommend transaction-wrapped reads. This is a language SQL contract restriction, not a request for an ORM.

## Cross-cutting design direction

The best next move is to make one end-to-end resource edit easy and statically connected: route with a typed ID, decode a form, perform a schema-checked bounded update that returns the saved row, and render a safe fragment through a concise checked HTML surface. Keep server/session/CSRF/crypto primitives as library facilities (cookies and CSRF already exist at [`examples/cookies/src/main.can:32`](/Users/vince/Projects/can-lang/examples/cookies/src/main.can:32)); deployment, hosted package discovery and migration running are tooling concerns. The static safety claim should always distinguish checked Can contracts and statement shape from live database state and browser DOM behavior.

## Scope fit for frontend SaaS

The selected browser boundary is explicit: Can runs on Bun and sends server-rendered HTML/JSON, while a pinned HTMX client submits forms and swaps fragments; no Can code or credentials compile for the browser ([`technical-spec.md:420`](/Users/vince/Projects/can-lang/docs/syntax-taste/technical-spec.md:420)). This is implemented through `htmx::runtime_head()` and polling in the dashboard ([`examples/dashboard/src/render/render.can:44`](/Users/vince/Projects/can-lang/examples/dashboard/src/render/render.can:44)), a pinned HTMX script in [`runtime/platform/html.ts:399`](/Users/vince/Projects/can-lang/runtime/platform/html.ts:399), and compiler asset rejection of `.js`, `.ts`, `.html`, `.svg`, and `.wasm` at [`compiler/internal/project/assets.go:45`](/Users/vince/Projects/can-lang/compiler/internal/project/assets.go:45). The HTML checker rejects authored `html::script` at [`compiler/internal/check/html_test.go:8`](/Users/vince/Projects/can-lang/compiler/internal/check/html_test.go:8). This fits CRUD, forms, account search, server-backed dashboards, content pages, and progressive updates. It does not by itself serve rich offline editing, local optimistic state, canvas-intensive UI, or custom browser WebSocket clients; server WebSocket support does not create a browser language target. Therefore “recommended for all SaaS frontend and backend” overstates the selected product scope. This is a scope/positioning mismatch, not an implementation defect or an automatic reason to reopen the no-browser baseline. A future separate browser target or explicit external client integration would be a strategic choice.
