# Core reconciliation — mechanism challenges at 961f921

This follows the independent source review in `/tmp/can-upgrade-core-961f921.md`. The coordinator supplied three fresh classifier recommendations; I treated their disagreements as prompts for counterargument investigation, not votes or evidence that a mechanism works. No production source edits or new test helpers. Additional current-code inspection covered `check/specialize.go`, `types/symbolic.go`, `runtime/assert/context.ts`, `runtime/assert/identity.ts`, `emit/regions.go`, owner representation gates, and owner schema restrictions.

## 1. Generic composition: the need survives; a naïve symbolic-call mechanism does not

**Observed need:** a generic wrapper calling a generic identity helper passes privately and fails when exported. Moving a fragment into another generic helper can change admissibility without adding any representation-dependent operation. This is a real reuse/refactor cost. It is not proof of unsoundness or proof that Can cannot express the application behavior: an explicit callable argument can express the same operation.

**Strongest counterargument to symbolic calls:** current private generics are templates, not universally checked parametric definitions. The compiler cannot safely substitute symbolic arguments into any callee's signature and assume its body is valid for every type. `compiler/internal/check/specialize.go:89–104` explicitly describes this reason for rejection. A helper with `value + value` may have an apparently general signature and successful integer assertions, yet fail for a caller's future instantiation. Blindly trusting its signature would undo the exported-generic guarantee that unsupported operations fail at the declaration.

There are further implementation obligations:

* A callee's validation cannot depend on source-file order. Public-only validation is insufficient if an exported function can call a private template.
* Mutually recursive generic helpers require a validation graph or staged obligation discharge, not recursive validation that runs forever or assumes success prematurely.
* Symbolic applications must not enter concrete-emission specialization caches. `types.SpecializationKey` intentionally rejects opaque parameters; concrete specialization discovery has a 4,096-instance bound (`specialize.go:105–120`). Calls that grow type arguments around a recursive cycle need a finite policy.
* Existing concrete specialization checks still matter for nominal/variant admissibility that symbolic evidence cannot prove universally. The comment at `types/symbolic.go:15–17` explicitly distinguishes definite symbolic duplicates from overlap that may occur only after substitution.

**Why callback-only is a respectable alternative:** it makes required behavior explicit, retains the existing callable/error contracts, and avoids a new symbolic call graph. It is particularly good for operations such as equality, ordering or codec behavior that actually require a capability. Passing an identity-like helper as a required argument solely because a library author extracted it is a less convincing API burden. It shifts implementation organization into every consumer's signature and call site. That cost should be measured with realistic library code, not dismissed as impossible programming.

**Calibrated recommendation:** retain declaration-checked opaque generics and explicit dictionaries for representation operations. Prototype symbolic application only to callees carrying successfully discharged parametric validation obligations. Start with acyclic helper composition; either validate private helpers reached from exported bodies under the same regime, or initially require a clearly visible eligibility marker. Do not make `provides` the long-term semantic selector merely to simplify this implementation. The exact eligibility syntax remains open.

**Acceptance experiment:** three representative helpers (identity wrapper, nested array transform through two generic helpers, and dictionary-based comparison helper) should keep public signatures and behavior after helper extraction. Test cross-package calls, declaration reordering, private helper reachability, and a deliberately broken helper adding `+`; that edit must fail at the helper declaration even when current callers happen to use integers. Include a rejected growing recursive type-argument cycle and prove no symbolic identities leak into emitted modules. Compare authored size and API changes against callback-only versions. This would establish benefit and preserve the actual guarantee before selecting a general mechanism.

## 2. Iteration: documentation is necessary; tail lowering is not automatically the smallest semantic change

**Observed need:** the emitted countdown returns a standard `native_exception` at 10,000 iterations on pinned Bun 1.4.2. Array folds already provide a stack-safe route for an existing finite collection. The remaining need is a usable way to express state-driven repetition whose number of steps is not known as an input array: pagination, state machines, convergence and repeated polling.

**Strongest counterargument to self-tail lowering:** a Can invocation is observable to its verification machinery even when its success value is forwarded. `runtime/assert/context.ts:282–300` creates a child invocation/frame, suspends the parent, starts the child, then finishes/resumes in `finally`. `runtime/assert/identity.ts:53–69` copies the complete parent path and appends a segment. Fixture allocation and callable identity depend on those paths. Replacing a recursive relay with a plain loop would change assertion identities, repeated fixture ordering, diagnostics and potentially coordination scheduling. Preserving every recursive logical frame while eliminating only native stack use may retain substantial memory/time growth; current copied path representation itself has quadratic total segment copying for deep recursion. Thus a numeric countdown passing with no assertion context is a necessary but weak acceptance check.

`emit/regions.go:388–390` also routes each call through context and completion boundaries. Lowering must preserve source-order argument preparation, failure origin/occurrence, caught standard failures, and callable capture behavior across iterations. A `while` rewrite is not merely textual replacement of the relay keyword.

**Why documenting bounds is reasonable:** no runtime can promise unlimited recursion, and the gallery mostly labels recursive examples as small-input teaching examples. A clear statement that `relay` forwards completion rather than guaranteeing tail-call elimination corrects an immediate expectation mismatch. Existing array operations solve many real workloads. For a deliberately bounded application subset, that may be enough today.

**Why documentation alone is insufficient for the broader goal:** native stack depth is not a stable application contract, and arrays are not a natural representation of an open-ended state loop. Documentation does not provide an efficient implementation strategy for those ordinary backend patterns. This is a capability/ergonomics judgment, not a claim that lack of a `while` keyword is intrinsically unacceptable.

**Calibrated recommendation:** require a demonstrated stack-safe state-iteration path before claiming unrestricted application suitability. Keep the mechanism undecided until a narrow comparison. An explicit iteration construct or catalogue primitive may be semantically cleaner because it can define repeated sites within one iteration region, rather than pretending a changing recursive invocation tree is unchanged. Self-tail lowering remains attractive if the existing source/fixture contracts can be preserved economically. Do not promise general recursion optimization based on a successful direct-self prototype.

**Acceptance experiment:** implement only a local proof of concept for direct-self relay and one explicit iterative-state equivalent. Compare a 100k-step pure loop, a paginated callback loop with named errors, an argument that faults before the next step, per-iteration captures, repeated fixtures under a real assertion context, and concurrent unrelated roots. Measure memory/path growth as well as native stack depth. Choose the smaller semantics that preserves the intended fixture contract and offers a comprehensible authored API. Publish bounds now regardless of which experiment wins. No precise keyword is required to establish this need.

## 3. Generic errors: transparent effects are useful, but finite effect-row syntax is not yet justified

**Observed asymmetry:** built-in array operations derive errors from their callback (`check/array.go:305`); authored contracts use finite written error bounds. An author cannot currently write the same transparent generic callback wrapper for arbitrary existing error sets. That is a library abstraction limitation. It does not imply application-specific error handling is impossible or that all wrappers require effects polymorphism.

**Strongest counterargument to adding finite error rows:** it adds a new kind of generic parameter and constraints across callables, higher-order functions, completion matching, concrete specialization identity, exported symbolic checking, catalogue operations, and diagnostics. Rules for row union, overlap, inference, aliases and escaping errors must be specified. A feature introduced for `apply` can quickly become a much larger checker change. The current finite named-error model is easy to audit; preserving that clarity has real value.

**Result-as-data alternative:** generic records can carry success/failure payloads, and a named result variant can be matched explicitly. A callback can return such data under `emits []`, allowing reuse without an effect parameter. This uses existing immutable data and matching facilities. It is especially appropriate where collecting multiple failures, retaining partial outcomes, or carrying a domain status is the intended application behavior.

It is not a drop-in replacement for transparent effects: failure-as-data is an `ok` completion, so builtin short-circuiting/aggregation/relay behavior does not treat it as a domain failure. Adapters must decide when to turn result data into a domain completion. Unrelated errors may be deliberately normalized into a library-owned error, changing identity/payload provenance at a documented boundary. That can be good API design, but is a semantic choice. Standard failures remain a distinct concern; an empty domain bound does not make a callback total.

**Calibrated recommendation:** do not commit to effect-row syntax from this review. First demonstrate realistic library needs using current concrete bounds and result data. Where these approaches preserve intended semantics at reasonable cost, use them. Keep transparent callback-effect preservation as a requirements item if retry, transaction-like traversal or instrumentation wrappers otherwise require repeated enumerations and adapters. Effect rows become justified when that cost is demonstrated, not merely because builtins possess internal derived behavior.

**Acceptance experiment:** implement three authored library examples using existing constructs: a result-collecting validator, a retry wrapper that retries one known error and preserves other caller failures, and a traversal that stops on its first arbitrary callback error. Use two unrelated caller domains. Record where result data is natural, where domain identity must change, and how many explicit adapters/error enumerations are required. Only then prototype the narrowest finite bound parameter needed to eliminate demonstrated duplication. Its acceptance gate must preserve exact error identity, declaration checking and useful diagnostics, with no hidden implicit widening. Result-data syntax and effect-row syntax are not mutually exclusive architectural choices.

## 4. Owner equality: a medium abstraction-evolution issue, not an invariant-enforcement failure

The owner-record mechanism still validly enforces package-controlled construction and representation access. Foreign constructor, field/update/destructure and codec bypasses are rejected; owner factory functions can establish invariants. Representation-derived equality does not let a foreign caller manufacture an invalid value or mutate a valid one. Do not downgrade the verified abstraction boundary to “broken” because it offers weaker representation independence than a full abstract-type discipline.

The separate issue is observable evolution: equality eligibility traverses record fields (`types/inhabitation.go:118–159`) without an owner abstraction exception, and allowed equality compares representation. Adding an internal cache or changing a canonical representation can change equality; adding a callable/opaque field may make consumer equality stop compiling. Two values that an owner considers semantically equivalent may compare differently. This concern becomes material for reusable domain packages; it is less urgent for simple single-field validated wrappers.

A narrow future experiment is owner-provided equality plus a deliberate decision about foreign automatic equality: keep it explicitly as representation equality, or require an exported comparison operation for owner values. Test representation refactors without changing factories/accessors or intended public equivalence. No evidence here requires changing invariant enforcement, codec blocking or ordinary record equality.

## Outcome

The evidence supports needs with different confidence: safe generic helper composition and stack-safe state repetition are directly motivated by repros; transparent error abstraction and owner-selected equality are design opportunities requiring use-case validation. The original proposed mechanisms are experiments, not prerequisites with settled syntax. Callback-only contracts, bounded-recursion documentation and result data are legitimate alternatives whose semantic and maintenance costs should be tested in the same small examples. Classifier preferences do not settle these engineering obligations.
