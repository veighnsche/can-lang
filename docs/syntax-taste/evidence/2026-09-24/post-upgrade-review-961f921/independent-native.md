# Independent native/backend audit — HEAD 961f921 (2026-09-24)

Scope: current Can examples, compiler/check/emit code, runtime and targeted tests. I did not read prior review verdicts, recommendation material, Jev evidence, ledgers, or sibling reports. No production files changed. My native/backend assessment is **credible for bounded services and carefully designed SaaS slices, but not yet a broad default recommendation for full-stack SaaS**. The issues below concern a concrete hang, bulk collection cost, and operational/product contracts. The language can already implement meaningful authenticated transactional workflows; it is not merely a syntax sketch.

## What works, with current evidence

* `examples/native-ai/src/oracles/oracles.can:14-81` declares a statically configured Responses LLM and TypeSafe SystemOne classifier; `judge` batches three registered questions over typed shared state and turns validated answers into a score. Dynamic Choice options are derived from an immutable `map` (`examples/native-ai/src/model/model.can:19-27`) and `llm` outputs are checked against a record schema (`compiler/internal/check/native_bodies.go:218-239`). `compiler/internal/emit/judge.go:223-294` prepares all descriptors, makes one request, validates all answers, then runs handlers and continuation in order. This separation prevents partial handler effects from malformed batched answers. `runtime/ai/questions.ts:80-116,216-301` validates option counts, unique keys, probability distributions and selected keys. `runtime/transport/normalize.ts:5-33` wraps only the originating native infrastructure failure, while authored validation failures retain identity.
* The generated runtime delegates to Bun/JS primitives in substantive paths: `runtime/collections/array.ts:46-200` uses `Array.fromAsync`, `reduce`, `filter`, `toSorted`, `concat`, `toReversed`; `runtime/collections/map.ts:38-94` and `set.ts:31-56` use native Map/Set; `runtime/coordination.ts:84-96` uses Promise all/allSettled/any/race; `runtime/platform/process/spawn.ts:143-155` uses `Bun.spawn`; `runtime/platform/server.ts:246-289` uses `Bun.serve`; `runtime/platform/crypto/password.ts` uses Bun.password. The adapters preserve Can's typed completion, immutability, origin and ownership contracts.
* A realistic SaaS flow is expressible now. Invoice session and tenant membership are checked inside a transaction (`examples/invoice/src/model/model.can:400-474`); the JSON route overwrites an untrusted body token from the cookie (`examples/invoice/src/web/web.can:435-480`). The webhook receiver bounds the raw body, checks its HMAC, decodes a typed envelope and writes ledger plus outbox in one transaction (`examples/webhook/src/web/web.can:138-179`, `examples/webhook/src/model/model.can:62-112`). `sql::commit_unknown` is reconciled by a follow-up lookup (`examples/webhook/src/web/web.can:70-101,124-136`), with runtime classification only after a commit decision (`runtime/platform/sql/transaction.ts:193-258`). The files/process/stream/WebSocket examples all model bounded native resources and typed failures (`examples/files/src/main.can`, `examples/process/src/main.can`, `examples/stream/src/main.can`, `examples/websocket/src/main.can`). Auth and security can be expressed with typed cookie/CSRF primitives (`examples/cookies/src/main.can:20-147`), password hashing, HMAC and Ed25519 (`examples/crypto/src/main.can:19-67`). This is evidence of capability, not a claim that every example is production-hardened.

## Priority 1 — Empty dynamic first-completion race can hang indefinitely

`compiler/internal/syntax/coordination.go:47-75` allows a single spread participant; the array can be empty at runtime. The checker only requires a participant *entry* (`compiler/internal/check/coordination.go:11-14,46-60`). `runtime/coordination.ts:95-96` sends first-completion `race with error` to `Promise.race(promises)`, and `Promise.race([])` never settles. The existing runtime test names this behavior (`runtime/test/coordination.test.ts:520-535`); my direct Bun probe of `settle("race", [])` remained pending beyond 50 ms. By contrast first-success `race` over an empty spread yields `all_failed` (`runtime/coordination.ts:98-107`; `compiler/testdata/current/coordination/main.can:90-100`). Thus two closely related Can forms have materially different empty behavior.

SaaS case: a request races dynamically chosen replica calls; a tenant has no replicas after filtering. The HTTP handler never completes. Strongest counterargument: faithful native Promise semantics make a pending empty race coherent, and callers can check length first. That is real, so call this an admitted semantics/product hazard, not a miscompiled Promise. Minimal experiment: a temporary Can function taking `callable int () emits [][]` and invoking `match call race with error ...operations`; assert the empty case under a short external deadline, then compare either a compiler/runtime `empty` completion arm or a rejected empty spread with an explicit guard. Whichever design is selected should give a typed, testable path; do not silently fabricate a winner.

## Priority 1 — Sequential immutable Map/Set updates scale quadratically

`collections::insert`/`replace`/`remove` clone the entire native Map each time (`runtime/collections/map.ts:47-79`); `collections::add` clones the full Set (`runtime/collections/set.ts:40-44`). The catalogue surface has only empty and point updates, no bulk constructor/transform (`std/catalogue/README.md:326-337`); `examples/gallery/src/24-map-word-frequencies.can:6-29` folds point updates to count words. For a 40,000-key histogram or authorization membership set, repeated copies dominate the native lookup. My local Bun microprobe of `createSet` plus sequential `add` took about 150 ms/617 ms/2,859 ms for 10k/20k/40k unique bigint keys, consistent with O(n²) work. These are indicative local timings, not a benchmark suite.

Strongest counterargument: copying is the simple, correct adapter for immutable values, and small maps work well. Also persistent structural-sharing collections would violate the repo preference for native operations. Minimal experiment: add a bounded *bulk* `from_entries`/`from_values` primitive implemented with one native Map/Set pass plus immutable opaque ownership, and benchmark it against the current fold at 10k/20k/40k. Keep point-update semantics unchanged unless evidence shows an additional need. This is an API design gap, not an observed correctness defect.

## Priority 2 — Early race selection does not bound request or command latency

The runtime chooses the first winner promptly (`runtime/coordination.ts:64-96`), but ownership retains every loser and the root drains all groups (`runtime/owner.ts:389-449,526-590`). HTTP dispatch wraps every request in a child scope that drains before returning (`runtime/platform/server.ts:219-244`). A quick winner therefore cannot make a request finish while a loser remains pending. My probe selected an immediate first-success winner at ~5 ms but `runOwnedRoot` returned at ~85 ms because the loser slept 80 ms. `examples/dashboard/src/model/model.can:33-48` uses a two-read race for its count; in a live route the slower read still affects response lifetime. `server_stop` has a caller deadline but does not cancel the owned work (`runtime/platform/server.ts:424-455`, `runtime/owner.ts:324-355`), so shutdown also needs an external bound if a handler never settles.

Strongest counterargument: draining protects resource lifetimes, prevents unobserved effects, and retains late diagnostics; cancelling JS promises is not automatic. This is a deliberate ownership tradeoff, not a compiler bug. Minimal experiment: a real HTTP route racing a fast and a delayed replica, measure response time and scope diagnostics; then trial an opt-in cooperative cancel token carried to supported native operations while preserving loser cleanup. At minimum, document race as first-*result* selection with scope draining, rather than a latency hedge.

## Priority 2 — Static outbound connections restrict tenant-specific integrations

A `connection` requires a literal endpoint and timeout (`compiler/internal/check/native.go:9-47`, `compiler/internal/check/connections.go:54-92,153-161`); dynamic request paths are confined to that endpoint's origin (`runtime/transport/request.ts:74-92`). This is a useful origin safety boundary and fixed provider integrations are expressible. It makes a SaaS feature such as user-configured webhook destinations or tenant-specific regional APIs awkward: a finite set of connection declarations or an external carrier is needed. The webhook example in fact delegates delivery to an operator carrier (`examples/webhook/README.md:77-88`), although the README's broader statement that Can has no HTTP client is stale beside current `fetch` declarations. The current source does not demonstrate an arbitrary URL outbound request. Strongest counterargument: unrestricted dynamic URLs would introduce SSRF and secret routing hazards; static origins make declarations auditable. Minimal experiment: implement two tenant destinations using only current fetch declarations, then prototype a typed outbound client accepting a per-tenant URL under an explicit allowlist/origin policy and compare its security and assertion contracts. This is a capability boundary, not a defect.

## Priority 2 — Source-level resource cleanup remains repetitive

The owner prevents handle misuse and drains native work, but Can authors must explicitly repeat close paths when they need to preserve a primary domain failure or report close failure. `examples/stream/src/main.can:23-63` has separate reader-close branches for read failure, cancel, size limit and normal EOF. `examples/native-ai/src/app/main.can:41-73` closes a SQL pool on each major outcome. `runtime/owner.ts:301-355,555-565` tracks close failure/cleanup diagnostics, but its automatic scope close is not an authored policy for choosing between primary and cleanup errors. A SaaS import pipeline combining file reader, DB pool, outbound call and child process magnifies this branching. Strongest counterargument: explicit arms make every failure decision visible and the owner already provides a safe fallback. Minimal experiment: implement that same stream pump with a small scoped cleanup construct lowered to JS `try/finally`/native close operations, preserve the exact primary-error precedence, and compare source size plus failure coverage. This is an ergonomics/expressibility proposal, not evidence of a missing cleanup runtime.

## Concrete security and operational limits of the demonstrated webhook

The provider ingress signs before decoding and keeps malformed/oversize inputs from touching the store (`examples/webhook/src/web/web.can:154-179`). The outbox carrier routes, however, directly expose pending events and accept settlement acknowledgements (`examples/webhook/src/web/web.can:181-204,284-306,317-334`) without a route-level credential check. The example binds `127.0.0.1` (`examples/webhook/src/web/web.can:349-359`); behind a proxy it requires an explicitly trusted carrier channel or an added auth guard. `examples/invoice` and `examples/cookies` show that such a guard is source-expressible. The HMAC compares lowercase hex as ordinary string equality (`examples/webhook/src/model/model.can:29-46`); the webhook README itself states this is not constant-time (`examples/webhook/README.md:90-99`). A native constant-time verification primitive would improve expressibility, but I would not call the current language unable to authenticate webhooks. Also the schema is external SQL migration (`examples/webhook/schema.sql:1-24`), and pending rows are listed rather than atomically claimed (`examples/webhook/can.project.json`, `examples/webhook/src/web/web.can:181-204`), so a multi-carrier deployment relies on downstream idempotency. These are explicit slice/deployment boundaries; avoid presenting them as compiler defects.

## AI declaration observations

`judge` batches state and question descriptors, but registration arguments cannot depend on earlier answers in that same batch: they are all checked/prepared before response dispatch (`compiler/internal/check/native_bodies.go:137-213`; `compiler/internal/emit/judge.go:235-281`). A dependent SaaS triage flow needs sequential judges, which is supported by ordinary Can calls. Dynamic options are admitted structurally but runtime validation requires 2–255 options (`runtime/ai/questions.ts:88-104`); `examples/native-ai/src/model/model.can:23-25` explicitly permits an empty plan, so `oracles::pick` can produce `ai::invalid_question` if invoked with it (`examples/native-ai/src/oracles/oracles.can:43-51`). That is a typed, recoverable domain outcome, not a compiler bug; the sample CLI currently forwards it. The sample's successful fixture only uses two options. For a user-facing SaaS classifier, guard zero/one options before the remote call and decide whether to skip, default or request a revised plan.
