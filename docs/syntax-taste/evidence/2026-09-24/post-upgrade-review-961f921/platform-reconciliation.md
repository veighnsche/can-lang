## Browser packaging: strongest qualification and updated diagnosis

The strongest counterargument is that Can explicitly targets TypeScript: emitting intermediate modules rather than a final JS bundle is legitimate, and a maintained bundler/plugin layer can be a complete solution. The current grid actually executes emitted Can, and its shims are intentionally narrow, rather than pretending an unrelated JS demo proves the target. Therefore “browser support nonexistent” and “must redesign the language before it can run in browsers” would both be wrong. The recommendation is to make one supported packaging/runtime contract, not necessarily to emit final JS directly from canlc.

What still makes this material is that `browser.ts` calls diagnostics configuration that synchronously reads files; the current test plugin supplies semantic replacements for fs/util/crypto/AsyncLocalStorage, with assumptions tied to this example. Simply documenting `bun build --target browser` is insufficient. A promoted plugin could satisfy the requirement, but would need target-wide semantics and tests rather than “this grid never enters an owner context.”

Coordinator's newly executed audit probes make the diagnosis more precise. I read `browser-audit-results.json` and rechecked `compiler/internal/browser/browser.go:591-639`: Runtime artifacts are skipped, and authored emitted text is searched by substring for `process.`, `Bun.`, `require(` and `node:`. Literal `"Bun."` and `"node: introduction"` fail while equivalent concatenation passes. This is an additional correctness/expressiveness bug: harmless content (including a docs site explaining Bun) can fail based on spelling, while the check omits the actual runtime closure. It is not evidence that concatenation permits arbitrary native execution; the IR capability checks remain. Replace textual token heuristics with structured import/capability checks, and audit or validate the browser runtime dependency closure separately. Do not substitute a looser substring rule and declare the problem solved.

Acceptance should distinguish (1) semantic capability rejection, (2) harmless source data accepted regardless of spelling, and (3) deployable runtime closure. These need separate tests.

## Actions: strongest counterargument and current import capability

The strongest counterargument is that useful server applications already work through ordinary typed HTTP callbacks. Explicit adapters are often desirable: authentication, authorization, raw webhook bodies and per-route status handling are application decisions. A language should not force every route into a giant framework or silently make client wire data a trusted actor. Also, resource dependency injection may be implementable by passing a checked closure at mount, without a new request-context language feature.

Thus the narrow recommendation is: keep low-level callbacks, but ensure the opt-in typed action abstraction can consume one contract and bind a live handler with non-wire dependencies. The current mismatch matters because the showcased client reads a declared captured path that the current server does not serve; the origin rewrite is executable evidence, not a preference for a different API style.

Imported action lookup already exists: `compiler/internal/check/action_fetch.go:198-228` resolves `package::action` through file imports to the canonical action identity; `compiler/internal/check/form.go:293-337` does the corresponding form lookup. Sharing types/actions across packages is not categorically impossible.

However, a handler-free imported action *contract* cannot currently be declared. `compiler/internal/syntax/native.go:351-431` requires `handles`; `check/actions.go:286-334` resolves a concrete non-generic function with exactly captures plus body and an empty error bound. Form serving carries the declared handler binding (`check/form.go:335`). Browser checking includes other emitted functions and server-backed declarations (`browser/browser.go:106-145,166-190`), so importing the real server implementation brings the very server capabilities the client must reject. A shared action whose handler is a real pure transformation can work without a stub; that does not solve the authenticated SQL save/load case. A pure stub packaged once would avoid duplicated source, but remains a pretend implementation and cannot be rebound to the real server function through the currently checked form action mount.

A minimal evolution would make transport declaration independent of implementation, then accept an exact checked handler/closure at server mount. That can be an incremental action API change, not a new general effect system. Require auth/tenant/pool as explicit non-wire binding inputs, and keep codec, finite status case and domain-error checks intact.

## Catalogue expansion versus reviewed typed adapter seam

Jev's split does not establish the better long-term design. The alternatives solve different scales of problem.

Minimal catalogue expansion is the lower-risk immediate choice for common, predictable needs: event `checked` and modifier/composition state, explicit supported default prevention, and typed persistent storage with absence/quota/unavailable/malformed-data outcomes. These are core browser operations, fit existing contracts and avoid creating an extension ecosystem before its boundaries are understood. Merely adding event names is insufficient when their required payload/control semantics are missing. Prefer native browser operations with only contract/immutability adapters, as AGENTS.md requests.

A reviewed host-adapter seam becomes attractive when the next legitimate integration (specialized editor, browser capability, provider SDK) repeatedly forces compiler-owned catalogue work. It carries significant obligations: declared target availability, non-forgeable opaque values, finite domain failures versus standard failures, native exception mapping, resource ownership/disposal, wire restrictions, assertion substitution provenance, and immutable outputs. An arbitrary JS/TS import or eval with an asserted signature would not preserve the current safety constraints. It is premature to design a universal public FFI just to add local persistence.

One useful bounded experiment: implement the *same* persistent invoice draft feature in two isolated prototypes. Prototype A uses a small compiler-owned `browser storage` contract; B uses one build-pinned, explicitly reviewed external adapter implementing exactly that contract (no arbitrary module imports from Can). Persist raw invalid quantity text, key/version metadata and edit intent; restore after reload; handle corrupt data, unavailable storage, quota failure and schema-version mismatch. Test that an adapter cannot introduce server-only APIs into browser output, forge owner/opaque tokens or return mutable data; distinguish real storage tests from supplied boundary fixtures. Compare compiler special cases, adapter review burden and application code. Promote the seam only if it meaningfully reduces repeated host-integration work while passing identical contract tests. Otherwise ship the minimal catalogue feature and retain evidence for a later decision.

The architectural recommendation can therefore remain “allow a safe path for legitimate host integration” while the next implementation step is a small native catalogue expansion. Broad frontend recommendation should wait for the demonstrated use cases, not for one particular extension mechanism.
