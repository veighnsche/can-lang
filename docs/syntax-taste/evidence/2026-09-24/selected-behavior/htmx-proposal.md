# S01: declaration-scoped HTMX error swaps

Proposal and local evidence, 24 September 2026. This is design evidence, not a runtime change or production qualification.

**Post-audit integration:** the [selected behavior packet](../../../post-upgrade-selected-behavior-2026-09-24.md#required-compile-rejection-and-execution-matrix) extends the guard below. The pinned asset exposes all pending `detail.tasks` at `htmx:before:swap`; declared 200/422/409/403/503 responses are admitted only when that list contains one main task for the original connected target. OOB/partial tasks in an otherwise admitted response are rejected as a whole. Missing targets both before request and during flight produce an observable sanitized client failure. The original disposable probe here covers only blocked unrelated 500 OOB content.

## Selected policy

Emit `noSwap: [204, 304, "4xx", "5xx"]` in the single page-level `htmx-config`. On the element generated by `action::post` for an HTML action, emit one exact `hx-status:<code>` attribute per declared error case whose policy is `swap inner`, with value `{"swap":"innerHTML"}`. For the selected invoice action these are `hx-status:422`, `hx-status:409`, `hx-status:403`, and `hx-status:503`; the checked binding also emits its usual `hx-target` and `hx-swap="innerHTML"`. Keep 200 under the ordinary successful swap path. Derive this finite set only from the checked action case table, not from caller strings or all actions on the page. JSON actions emit no HTMX attributes. Use the existing HTML attribute token/escaping path so no raw markup escape is introduced. An action that does not declare a status emits no exception for it; its 4xx/5xx responses retain the page-level no-swap rule.

Add a controlled `htmx:before:swap` guard for failure responses when the resolved context has `swap === "none"`: cancel that event. This is needed because `noSwap` suppresses the main task but the pinned asset still executes out-of-band tasks from the response body. The guard cancels the whole swap after the asset has resolved the exact-status exception, so declared cases continue and unrelated failures cannot mutate an OOB target. Keep the guard in an owned adapter asset loaded after htmx; do not expose arbitrary author event code.

The pinned [htmx 4.0.0 asset](../../../../../distribution/assets/htmx-4.0.0.min.js) is minified on one line. At byte offset 35475, `#fe(t)` tests the exact status first, then the `40x`/`50x` family, then `4xx`/`5xx`; for each candidate it tests `config.noSwap` *before* reading `hx-status:<candidate>`. Thus an exact `403` in `noSwap` would defeat a local `hx-status:403`, whereas a broad `4xx` entry lets the exact source-element attribute win first. Its `#E`/`#P` attribute reader (offsets 4344/3683) accepts `hx-status:403` and `data-hx-status:403`; `#fe` merges the JSON attribute object into the request context. At offset 9621 the response pipeline applies `#fe` before `swap`; `#De` at 20732 uses that context's swap and target. The asset's default `noSwap` is only `[204,304]` (offset 2402), so Can must supply the broad failure policy explicitly.

Current [runtime policy](../../../../../runtime/platform/html.ts#L402-L411) instead enumerates every 4xx/5xx except 422. The existing [account-search browser probe](../../../preparation/htmx-503-probe.md) observed a real 503 HTML fragment delivered over HTTP but absent from its target. The [integrated action contract](../../../preparation/integrated-action-contract.md#request-operation-and-response-policy) requires real 200/422/409/403/503 statuses with visible `inner` feedback on the admitted target, while unexpected infrastructure statuses remain separate outcomes. The [action design](../../../preparation/action-contract-design.md#checked-action-source-candidate) explicitly rejects a conflicting page-global status policy and requires an observable missing-target outcome.

## Disposable browser check

I loaded this checkout's pinned asset in installed Chromium through local Playwright with a loopback-only intercepted page and responses. The page had the proposed `noSwap` value, three source elements with exact `hx-status` attributes, and two unrelated elements without them. Observed target `innerHTML` after actual htmx requests:

| Source and HTTP response | Target after request |
| --- | --- |
| Declared 503 | `<p>new 503</p>` |
| Unrelated 503 | `old unrelated` |
| Declared 403 | `<p>new 403</p>` |
| Declared 409 | `<p>new 409</p>` |
| Unrelated 422 | `old 422` |
| Unrelated 500 with `hx-swap-oob` fragment, without guard | OOB target changed to `new oob` |
| Same unrelated 500, with `htmx:before:swap` guard | OOB target remained `old oob` |

The disposable script is `/tmp/can-htmx-status-scope.mjs` and was not added to the repository. The first browser launch was blocked by the filesystem/process sandbox; the same script succeeded with approved escalation. This check proves the pinned asset can perform the proposed scoped rule in Chromium and that the guard blocks the tested OOB case. It does **not** prove Can's future compiler emits it, that the full action mount returns the declared bodies, or that focus, announcements, late responses and missing targets satisfy the product contract.

## Adapter bounds and acceptance tests

- Compile an HTML action with 200/422/409/403/503 `swap inner`; inspect the generated element for exact status attributes and the admitted target. Exercise each over real HTTP in Chromium, check actual status, content type and body, and compare the target DOM after the request. In particular a 503 must replace stale 422 feedback. Rendered hostile text must remain escaped.
- On the same page, submit unrelated HTMX sources that return 403, 409, 422, 503 and 500; their targets must remain unchanged. A declared source receiving an undeclared 500 must also leave its target unchanged. This tests declaration scope and unexpected outcomes, not just the numeric response class.
- The pinned asset reads `HX-Retarget` and `HX-Reswap` before `#fe` (around byte offset 9621). Generated action adapters should own or reject these response headers so a declared case cannot redirect a swap outside the admitted target. Test that a response cannot move feedback into an unrelated node. `swap()` builds out-of-band tasks before its main swap (around offset 19911); the browser probe confirmed an unrelated 500 can mutate an OOB target without the guard. Keep an OOB regression case for every blocked failure class.
- Test a target omitted initially and removed while the request is in flight: no unrelated node may change, and the client must report an observable missing-target failure. Test delayed responses in reverse order and the chosen submission/revision policy. Check retained draft values, focus and announcement behavior separately; the status rule does not establish them.
- Switching all 4xx/5xx to broad no-swap also changes generic HTMX 422 behavior. Migrate any intentional non-action 422 swaps to a checked local policy, or explicitly revise those examples and tests. Do not retain a global 422 exception if the requirement is that unrelated 4xx responses never swap.
