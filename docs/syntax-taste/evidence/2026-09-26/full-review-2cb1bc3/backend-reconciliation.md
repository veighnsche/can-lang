# Source reconciliation: operation deadlines versus request/scope policy

Reviewed current HEAD 2cb1bc35435ab5075d51f9f945adfb0e1f9dfe64. This supplements `/tmp/can-review-20260926-backend.md`; no repository edits or additional tests. Source/tests are the evidence, and the saved deterministic race-drain probe from the first review remains relevant. The coordinator reports three fresh Jev consultations split between `operation_deadlines` and `scope_policy`. I have not used the classifier scores as correctness evidence.

## Decision

Prioritize truthful **operation-level interruption/settlement contracts**, especially SQL and S3, while specifying the **request-budget/shutdown policy** they must eventually satisfy. A scope timeout that merely races a promise does not solve this repository's core issue: its owned losers remain live until they settle. Conversely, giving every call an independent timeout does not give a composed request one deadline or handle disconnect/SIGTERM. The alternatives are complementary layers, not mutually exclusive finished designs.

A broad SaaS recommendation should accept a concrete operational model: graceful termination attempts native interruption and reports incomplete disposal/commit uncertainty; an external supervisor supplies the hard process kill bound. The runtime already explicitly tests that model for nonsettling work. Do not promise a universal in-process hard deadline for arbitrary native work, and do not require a whole ownership/effect type system to establish these contracts.

## Why operation deadlines alone are insufficient

1. Three serial 5-second native calls can legitimately consume roughly 15 seconds; their individual limits do not enforce one 5-second request budget. A declared connection timeout is a per-operation cap, not a caller's remaining budget.
2. A timer-raced operation can return timeout while late native work keeps the request scope draining. HTTP handler scope completion precedes response return (`runtime/platform/server.ts:284-293`); owner drain waits for groups/callbacks and leases (`runtime/owner-core.ts:612-649`). The first review's saved race-drain probe demonstrates this exact selection-versus-lifetime distinction.
3. A client disconnect or shutdown should stop new unrelated work and propagate interruption to cooperative adapters. Local operation timers neither establish that ingress signal nor deny the next step within an still-running handler.
4. SQL writes require ambiguity semantics. Cancelling a client wait after a commit decision cannot become rollback proof. The existing commit_unknown behavior (`runtime/platform/sql/transaction.ts:234-252`) must be preserved and extended consistently.
5. Stop/close deadlines are already waiting deadlines. Simply adding more Promise.race calls can multiply timeout errors while preserving the same underlying stuck ownership, rather than produce safe disposal.

Operation-level contracts can still be the first implementation step: make each adapter declare and test whether timeout means native abort requested, execution known stopped, completion unknown, or only the caller stopped waiting. SQL needs dialect-specific capabilities; S3 needs an honest, stronger contract or a documented restriction. Then an ingress lifetime policy can pass `min(operation cap, remaining request budget)` and one interruption signal, track disposal, and route unresolved work to the external supervisor contract. This layering fits AGENTS.md's instruction to retain native operations plus contract adapters.

## Why scope policy alone is insufficient

The owner system currently protects resources by retaining losers and draining them. Adding a scope deadline without adapter interruption would only cause its primary body to stop waiting; the same drain can still block the response/process. A scope policy needs explicit adapter hooks and honest uncertainty outcomes. It should not force-close a borrowed SQL handle, discard an outstanding Promise or label a remotely committed write cancelled. The current tests intentionally preserve loser captures (`runtime/test/coordination.test.ts:537-581`) and require supervisor termination for a nonsettling HTTP handler (`runtime/test/server.test.ts:664-708`). Those semantics are counterevidence against treating scope timeouts as a quick substitute for operation work.

## Concrete newly identified S3 contract mismatch

`compiler/internal/catalogue/catalogue.json:12398-12403` describes cancel_upload as releasing without completion, never materializing/deleting the key (same generated wording at `std/catalogue/README.md:541`). Actual `runtime/platform/s3.ts:204-223` says the native writer has no abort, calls sink.end, then deletes the key, and explicitly acknowledges removing a pre-existing same-name key after writing begins. Both awaits are best-effort; failures are suppressed. `retire` marks the upload cancelled before cleanup (`:226-231`). The live tests recognize end-then-delete (`runtime/test/s3.test.ts:153-156`), but the shown cases check new-key absence, not preservation of an old object. This is a specific contract defect with potential data loss, not a general criticism of native adaptation.

Similarly, the S3 deadline test uses a 500 ms pull with a 50 ms deadline and only checks eventual timeout and limited pulls (`runtime/test/s3.test.ts:688-719`); it does not assert bounded latency and does not exercise a permanently hung pull. A truthful recommendation must flag these limits. No external service mutation or additional test was needed to establish the contradictory source behavior.

## Silent 500: counterevidence and remaining gap

The server default boundary converts failed Completion to fixed 500 and catches thrown exceptions silently (`runtime/platform/server.ts:300-313,341`). This is a default reporting gap, not inability to recover or log manually.

Authors can wrap handler work in a normal function, `match call` it, catch the standard arm `[_] as standard_failure failure`, inspect `failure.kind/message/occurrence_id`, log a carefully selected string with `log::write_error`, and return an ordinary response. Maintained standard-catch syntax appears in `compiler/testdata/current/arrays/contracts.can:106-112,171-176`; logging calls/declared errors appear in `compiler/testdata/current/cli/utilities.can:13-20,48-52`. SQL query failures expose operation/code (`runtime/platform/sql/errors.ts:54-58`), and the Postgres adapter preserves SQLSTATE in code (`runtime/platform/sql/postgres.ts:32-41`). Native declaration wrappers additionally handle declared native/emitted policy obligations (`compiler/internal/check/wrap.go:397-430`), although those are not automatically installed around every HTTP handler.

Main diagnostics and late-owner diagnostics already exist (`runtime/entry.ts:20-55,87-97`), and standard occurrence identity is preserved by Completion invocation. Thus an application can log all anticipated failure sites now. It cannot rely on a default safe server boundary reporter to catch an unexpected fault in the logging wrapper, response adaptation, dispatch or scope drain. Manually logging raw failure.message also lacks the central redaction guarantees of entry diagnostics. The recommendation is a small automatic, redacted request-boundary reporter with correlation and a documented manual policy, not a blanket new logging subsystem.

## Acceptance criteria to decide the next design

- Verify operation return bound, native termination/abort request, late settlement, and disposal independently for a stalled fetch, SQL query, stream pull, child process and S3 upload. Include a cancellation callback that itself hangs.
- Verify one request budget across serial calls and races; a chosen fallback must not conceal an indefinitely retained loser.
- Disconnect the client and send SIGTERM with active handlers. Define immediate admission behavior, cooperative interruption, grace-report timing and supervisor hard-kill timing. Test signal-driven shutdown separately from explicit server_stop.
- Exercise writes around commit/finish ambiguity; preserve commit_unknown and existing objects during rejected/cancelled uploads according to the final stated contract.
- Inject an unexpected request fault inside and outside an authored logging wrapper; require exactly one redacted diagnostic with correlation, plus a safe 500 response.

The Jev split is therefore understandable: operation_deadlines chooses the most immediate unsafe adapter gap, while scope_policy chooses the composition rule needed for the final application guarantee. The source supports doing the former first under a written specification of the latter, rather than using classifier preference as evidence that one layer removes the other.
