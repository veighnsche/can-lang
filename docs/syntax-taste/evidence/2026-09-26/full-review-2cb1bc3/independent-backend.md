## Judgment

The backend is a credible constrained application platform, not a mere syntax demo. The strongest argument for recommending it is the combination of checked native boundaries, immutable typed data, explicit failure handling, and unusually honest commit uncertainty. The invoice and webhook examples show meaningful SaaS business semantics. I would still qualify the recommendation to a Bun service with controlled endpoints, scalar relational storage, externally managed schema and worker infrastructure. The evidence does not yet justify recommending Can as the default language for an arbitrary operational SaaS application.

The main missing design work is making bounded execution, resource lifetime, diagnostic visibility and worker composition usable together. These can be resolved by a small number of native capability contracts and authored composition rules. They do not require copying Bun's whole API or adding backwards compatibility.

## What is already good

- **Native SQL rather than an invented database engine.** Queries enter Bun.SQL through checked template strings and bound parameters (`runtime/platform/sql/pool.ts:1-9`, `:104-120`). Dialect-specific classification is isolated and unknown failures remain faults rather than being laundered into ordinary SQL errors (`runtime/platform/sql/postgres.ts:19-42`). The compiler resolves parameter/row types against the declaration's owning project and preserves record field order (`compiler/internal/check/sql.go:34-40`). Cardinality and row limits are explicit (`compiler/internal/sql/cardinality.go:24-49`). This is stronger than stringly typed SQL hidden behind a generic JSON result.
- **Transaction decisions and uncertainty have distinct meanings.** A total callback returns nominal `commit<T>` or `rollback<T>`; the result must be data and the callback's declared domain error bound is empty (`compiler/internal/check/transaction.go:55-59`, `:127-138`). Runtime transaction handles are private and scoped, queries use the pool's shared codecs, and scope drain precedes commit (`runtime/platform/sql/transaction.ts:199-228`). A failure after the commit decision becomes `commit_unknown`, without automatic retry (`:234-252`). The outcome is conservative even for a foreign throw after commit; tests explicitly require it (`runtime/test/transaction.test.ts:648`). This is a defensible contract for paid actions.
- **Useful ownership exists even though it is not an authored type system.** Opaque handles and captured callables are conservatively retained (`compiler/internal/ir/resources.go:5-8`, `:18-41`); resource operations validate a private owner context. HTTP dispatch revokes request capabilities only after the request scope drains (`runtime/platform/server.ts:284-293`). Runtime tests cover transaction handle escape, nested entry, primary failure preservation and drain-before-commit (`runtime/test/transaction.test.ts:384`, `:531`, `:562`, `:677`). This is real runtime discipline, not just documentation.
- **HTTP boundaries have clear protective contracts.** Requests become copied immutable snapshots (`runtime/platform/http.ts:147-180`), buffered ingress counts bytes incrementally and cancels an incomplete read (`:183-210`). Outbound requests use native fetch, manual redirects, omitted browser credentials, a deadline signal and bounded body decoding (`runtime/transport/fetch.ts:43-98`); responses expose immutable typed data rather than a native Response (`:24-25`). Fixed-origin checks (`runtime/transport/request.ts:88-92`) are useful guardrails for declared integrations.
- **SaaS application rules are actually represented.** The invoice uses tenant/session authorization, optimistic revisions, a same-transaction replay ledger, and rechecks authorization before reconciling an unknown commit (`examples/invoice/src/model/model.can:1218`, `:1590-1643`, `:1712-1826`). Webhook receive records ledger and outbox atomically (`examples/webhook/src/model/model.can:62-112`) and rereads an uncertain result outside the transaction (`examples/webhook/src/web/web.can:66-104`). Live tests kill/restart the service and exercise the external-success-before-ack window (`tests/integration/webhook_test.go:474-533`). These are unusually valuable application tests.
- **AI primitives are typed and replayable.** `llm`, `judge`, dynamic choices and probabilities compose as ordinary checked results (`examples/native-ai/src/oracles/oracles.can:33-81`). Raw provider fixtures drive adapter decoding (`:37-39`, `:75-77`), rather than merely replacing the typed result. Generated requests carry exact encoded state and structured response schema; request settings explicitly disable provider storage, streaming and background mode (`runtime/ai/responses.ts:81-101`). Refusal, truncation, malformed responses and provider nonterminal states are distinguished (`:125-173`). The question runtime separately validates questions and answers (`runtime/ai/typesafe.ts:59-85`).
- **Native collection semantics are implemented carefully.** Arrays retain native traversal and reduce while boxing callback results to avoid Promise assimilation of data-valued `then` properties (`runtime/collections/array.ts:66-77`, `:140-150`). Coordination selects using Promise.all/allSettled/any/race with protected exact failure carriers (`runtime/coordination.ts:109-160`). Those adapters preserve meaningful Can contracts instead of rebuilding generic JavaScript behavior.

## Prioritized design limits and acceptance scenarios

### P0 for broad operational recommendation: bounded work and shutdown must form one contract

SQL query/transaction APIs lack a caller deadline or cancellation capability: pool launch awaits native SQL directly (`runtime/platform/sql/pool.ts:88-120`), transaction begin awaits the native callback (`runtime/platform/sql/transaction.ts:199-229`), and PostgreSQL establishment accepts only URL/max and awaits connect (`runtime/platform/sql/postgres.ts:57-76`). Database/backend defaults may eventually fail; that is not a request-level latency guarantee. SQL descriptors reject SET/DDL, so declaring a session timeout through ordinary Can SQL is not an alternative (`compiler/internal/sql/cardinality.go:51-55`). SQLite does expose a busy timeout in file options, so this is not an assertion that all dialects have no timing control.

Race selects; it does not cancel. Owner drain retains outstanding groups/callbacks and never discards a live lease (`runtime/owner-core.ts:612-649`). A shutdown timer records cleanup failure but still awaits ownership completion. This is deliberately safer than pretending a Promise race cancels writes. However it means an HTTP handler can select a fallback and then remain stuck in its request scope until its SQL loser finishes (`runtime/platform/server.ts:289-290`). The saved race-drain probe confirms winner selection while root completion remains false, followed by successful root exit only after the loser is released. Existing tests explicitly retain a losing participant's resource (`runtime/test/coordination.test.ts:537-581`).

**Acceptance:** Run a request with a 200 ms budget against a blocked query and an unresponsive outbound operation; send client disconnect and SIGTERM. Demonstrate a defined response bound, a defined service shutdown bound, ownership retained until safe native disposal, no late transaction commit reported as rollback, and a clearly reported uncertainty outcome. Distinguish a waiting deadline from effective native cancellation. Do not silently replace the current ownership semantics with loser abandonment.

### P0/P1: make server failure visibility and production observations composable

HTTP handler failures are converted into fixed 500 responses; `serveOuter` does not report the failed Completion and catches thrown faults without a diagnostic (`runtime/platform/server.ts:300-313`). `Bun.serve.error` also returns fixed 500 (`:341`). Main and late-owner diagnostics do exist and carefully redact secrets (`runtime/entry.ts:20-55`, `:87-97`), so the language has diagnostic machinery; the missing connection is request boundary visibility. The only authored logging surface in `runtime/platform/log.ts:25-56` writes level/message, leaving request correlation, structured safe fields and timing to manual conventions. A handled SQL failure mapped to a 503 is likewise silent unless the author logs it. Counterevidence: an authored wrapper can catch a standard failure (`[_] as standard_failure failure`) and inspect its message, as maintained `compiler/testdata/current/arrays/contracts.can:106-112` demonstrates; it can call logging manually before returning a response. SQL failures already carry sanitized operation/code (`runtime/platform/sql/errors.ts:54-58`), and PostgreSQL preserves SQLSTATE via errno (`runtime/platform/sql/postgres.ts:32-41`). The gap is an automatic safe request-boundary reporter/correlation contract, not inability to catch or log failures at all.

**Acceptance:** Cause a handler bounds fault, SQL denial, expected validation rejection and cleanup failure. Each unexpected fault must emit one redacted correlation record with source/occurrence and request context; expected failures must be distinguishable; client response must not leak payloads. Authored tracing/metrics should survive asynchronous participants without asking every helper to hand-build JSON. A native structured sink and a request reporter contract suffice; an entire observability framework is unnecessary.

### P1: recommend a complete Can worker, or state the external-worker boundary explicitly

The webhook sample delegates downstream delivery and scheduling to an operator carrier (`examples/webhook/README.md:79-90`). That carrier is Go test code, with polling and acknowledgement done outside Can (`tests/integration/webhook_test.go:101-147`). It proves the storage/replay protocol, not a Can-authored durable worker. Current connection endpoints must be string literals (`compiler/internal/check/connections.go:54-75`), and runtime paths cannot change origin (`runtime/transport/request.ts:88-92`), so tenant-selected webhook destinations are outside the present contract. Static clients are a strength for controlled service integrations; dynamic destinations need an explicit policy rather than unrestricted URL fetch.

General indefinite pull loops use recursive authored functions and duplicated cleanup arms (`examples/stream/src/main.can:5-63`). Finite arrays support asynchronous fold/map/for_each, but map is sequential (`runtime/collections/array.ts:73-77`) while coordination launches every supplied participant (`runtime/coordination.ts:52-62`). There is no authored bounded worker pool in these primitives. This is a composition gap, not proof that recursion or finite concurrency is broken.

**Acceptance:** A Can worker pulls a durable bounded batch, claims each job safely under two instances, performs bounded parallel delivery, persists retry/backoff, handles poison jobs, and stops cleanly. Kill it before delivery, after external success and before ack; prove at-least-once delivery with deduplication and no lost jobs. Also prove destination allowlisting/private-network policy if tenants choose targets. If workers deliberately stay in another language/service, document that deployment architecture and recommend Can only within it.

### P1/P2 depending on target: scalar-only SQL and restricted statement forms constrain ordinary storage workflows

SQL deliberately rejects arrays/JSON/timestamps/decimals/arbitrary variants and nested options (`compiler/internal/types/sql_schema.go:5-9`, `:32-71`). Only concrete ordinary nongeneric records are admissible (`:74-81`). RETURNING-free INSERT/UPDATE/DELETE and bounded SELECT are admitted; mutation RETURNING and DDL are rejected (`compiler/internal/sql/cardinality.go:30-55`). Schema application is explicitly operator-owned (`examples/webhook/README.md:19-21`), and SQLite/Postgres/MySQL mappings are dialect-specific. These are design boundaries, not parser defects or failures of native Bun behavior.

For an invoice with integer minor-unit money these limits are manageable; that example is good counterevidence to 'needs decimals for all SaaS'. For arbitrary accounting precision, JSONB documents, timestamp-rich audit records, generated-key writes and migrations, callers must use text/integer encodings or external tools. Broad recommendation should demonstrate a coherent selected subset rather than promise generic database portability. PostgreSQL constraint errors abort a transaction; webhook's reread-after-insert-conflict is qualified for SQLite only (`examples/webhook/README.md:98-100`). No savepoint/isolation operation exists in the transaction surface. That makes porting the existing algorithm a semantic redesign, not just a dialect toggle.

**Acceptance:** Ship a PostgreSQL tenant application with generated identities, a concurrent upsert/replay race, precise values, nullable timestamps, a JSON payload boundary, and an operator migration/rollback recipe. Show typed rejection or faithful codec conversion, no precision loss, no assumption that LIMIT bounds query execution cost, and no reread within a poisoned PostgreSQL transaction. Native RETURNING or a demonstrated equally safe identity strategy should be available for the declared target.

### P2: keep failure bounds distinct from purity/effects and transaction safety

`emits []` describes domain errors, not purity: transaction decision functions perform SQL with empty emits after handling failures (`examples/webhook/src/model/model.can:67-112`). The compiler's callable error bound admits no separate effect dimension (`compiler/internal/syntax/ast.go:42-46`); ownership capture analysis explicitly adds no authored ownership/effect syntax (`compiler/internal/ir/resources.go:5-8`). A total transaction callback can therefore handle an outbound HTTP/AI failure and still have emits []; there is no evidence here of an SQL-only effect restriction. This is coherent, but does not protect an author from placing costly or nontransactional external work inside a DB transaction.

**Acceptance:** Document the contract unambiguously and demonstrate an approved pattern: AI/HTTP computation precedes a short SQL transaction, commit decides a durable outbox entry, delivery follows through a worker. Show how an author audits side effects and how tooling highlights potentially long external work inside a transaction. An effect system is one option, not a prerequisite; compositional tooling or a narrower transaction API may be enough.

### P2: AI primitives need operational evidence beyond shape validation

The native AI example runs a CLI pipeline and fixture providers (`examples/native-ai/src/oracles/oracles.can:14-30`, `examples/native-ai/src/app/main.can:15-73`), not a live multi-tenant AI service. Model output schemas and question answer validation protect shape/range, not judgment correctness. Responses deliberately rejects tool output and multiple assistant messages (`runtime/ai/responses.ts:136-165`) and disables streaming/background (`:95-98`). These are useful narrow semantics, not a general provider abstraction. Settings are compile-time connection metadata, not a per-tenant budget/model policy.

**Acceptance:** A real service evaluates fixture and held-out judgment quality, model/version changes, refusal/failure policy, latency and cost, and cross-tenant data isolation. Tests should show prompt/state injection does not alter application authority. Expose whatever accounting/correlation data the service actually needs without weakening typed output. Only add streaming/tools/more providers when the SaaS use case requires them.

## Implementation/example defects, separate from design changes

1. **Invoice startup still uses a fake environment failure.** `examples/invoice/src/web/web.can:502-519` claims failures originate only in catalogue calls and calls `env::required("")` to reject a malformed origin/window. Current authored error origination already works: parser `compiler/internal/syntax/declarations.go:439-454`, checker `compiler/internal/check/completions.go:349-360`, emitter `compiler/internal/emit/regions.go:575-583`; a maintained source directly emits `codec::invalid_data` (`compiler/testdata/current/arrays/contracts.can:78-79`). Fix the sample with an accurately named authored startup error. This needs no new language feature.
2. **Webhook is an incomplete security/operations exemplar.** It compares HMAC hex with ordinary equality (`examples/webhook/src/model/model.can:44-46`), explicitly excludes constant-time comparison (`examples/webhook/README.md:94-95`), mounts outbox pending/ack without carrier authentication (`examples/webhook/src/web/web.can:326-329`), and exposes health as a fixed `ok` rather than database readiness (`:306-315`). Binding loopback helps but does not define carrier authorization. These are example omissions; the protocol is not a safe internet-facing deployment template until resolved. Native constant-time signature verification would be a useful catalogue addition if this becomes the recommended production idiom.
3. **The webhook's PostgreSQL caveat is honest and must survive marketing.** It currently is a SQLite application and its README states the reread-after-conflict caveat. Do not label its successful live crash tests as cross-dialect application correctness.

## Coverage and evidence limits

- Full runtime/compiler/integration results belong to the coordinator; I do not claim to have rerun them. My saved probe imports the current runtime, prints `rootDone:false` after the winner is selected, and `rootDone:true` after the losing promise resolves. It is a deterministic semantics probe, not a throughput or cancellation stress test.
- Runtime transaction tests cover important negative behavior, including escape, nesting, unknown commits and original primary errors. HTTP transport tests cover typed status/deadline outcomes and unexpected decoder faults (`runtime/test/transport-http.test.ts:83`, `:127`). These are valuable implementation checks.
- `when` fixtures replace native calls and cannot prove driver behavior, lock races, cancellation or deployment reliability. The webhook README explicitly says local SQLite cannot force commit_unknown; assertions pin the reconcilers, while live tests cover surrounding crash/replay semantics (`examples/webhook/README.md:101-103`). Keep this distinction.
- Live webhook crash tests include duplicate external receipts by design; the Go stub counts two deliveries after the external-success-before-ack crash. They prove replayable ledger/outbox behavior, not exactly-once delivery or a production downstream deduplication implementation (`tests/integration/webhook_test.go:488-533`).
- Reviewed examples do not establish sustained load, saturation fairness, reconnect behavior, slow-client ingress, long-running worker memory stability, bounded shutdown against permanently hung native work, dynamic destination policy, live AI quality or production diagnostics. None can be inferred from passing assertions.

The small examples substantially widen the platform evidence: crypto proves SHA/HMAC, password verification and scoped Ed25519 keys (`examples/crypto/src/main.can:5-74`); cookies combines validated Set-Cookie, session lookup and CSRF (`examples/cookies/src/main.can:34-143`); files preserves explicit bounded directory/I/O failures (`examples/files/src/main.can:29-44`); process specifies independent output caps, execution deadline and termination grace (`examples/process/src/main.can:22-41`, native group SIGTERM/SIGKILL `runtime/platform/process/wait.ts:12-36`); SQLite/MySQL use the same typed query composition with different opening/credentials (`examples/sqlite/src/main.can:30-62`, `examples/mysql/src/main.can:30-62`). Stream and websocket readers have explicit terminal cleanup; websocket has dynamic URL input, message/queue/send limits and a connect deadline (`examples/websocket/src/main.can:145-157`), so the HTTP fixed-origin finding must not be generalized to all outbound protocols. Markdown distinctly separates plain native HTML preview from opaque safe publication (`examples/markdown/src/main.can:4-36`; native Bun.markdown at `runtime/platform/markdown.ts:46-61`). Utilities show native URL/query order, timezone presentation, regex and base64 capabilities (`examples/utilities/src/main.can:5-61`); this is counterevidence to an obsolete claim that timezone or base64 are unavailable. These are capability demonstrations, not end-to-end SaaS authentication or operational qualification.
