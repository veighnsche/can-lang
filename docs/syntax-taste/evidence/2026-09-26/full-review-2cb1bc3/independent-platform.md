# Independent platform/frontend review — Can at 2cb1bc35435ab5075d51f9f945adfb0e1f9dfe64

Review scope: current source, current tests, invoice/server/grid/shared-contract examples. I read AGENTS.md and did not consult prior reviews, recommendation plans, implementation plans, Jev outcomes, or git history. No repository implementation edits. The coordinator owns full-suite execution and the three fresh Jev consultations. The only fresh execution here is the native Chromium semantic probe described below; I do not claim an independently rerun end-to-end generated-Can application.

## Recommendation

Can now has a credible, coherent vertical slice for a bounded transactional web application. The shared action system, request-scoped authorization in ordinary Can code, browser capability isolation, and explicit immutable draft/replay state are substantive strengths. It is reasonable to continue using this as an experimentally developed application platform.

I would not yet recommend it as the general frontend/backend platform for a broad SaaS product. The decisive frontend issue is the combination of a small, sealed host capability surface and no supported authored JS/npm extension boundary. Missing capabilities cannot simply be supplied by an ordinary Can UI library. The grid proves text-input CRUD and conflict handling; it does not establish that the platform supports the range of browser interactions a SaaS team routinely encounters.

Preserve the shared contracts, explicit failure cases, capability checks, and immutable data. Prioritize a controlled, typed host-adapter extension boundary and a few missing native DOM primitives; then prove an ordinary reusable UI library on top. Merely increasing the built-in catalogue case by case risks making every product feature a compiler project. Unrestricted JS escape is not the only alternative: explicit adapter signatures, targets, error bounds, lifecycle contracts, and audited packaging could retain the language's useful guarantees. This is a design recommendation for the coordinator's independent Jev evaluation, not an implemented or validated design.

## Established strengths and counterevidence

- **The server and browser really share one contract.** `shared/invoice-contract/src/invoice_contract/invoice_contract.can:98` defines a captured JSON GET, `:109` a captured JSON POST with five exhaustive outcomes/statuses and byte bound, and `:122` a keyed-row form POST. Consumers import the same locked billing package, not copied local endpoint declarations. `compiler/internal/driver/invoice_grid_test.go:130` verifies canonical shared identities; the integration contract tests mutate routes, captures, fields, leaves, statuses, limits, body modes, and pairing manifests (`tests/integration/invoice_contract_test.go:481`, `:597`, `:689`, `:778`, `:884`, `:971`, `:1053`, `:1148`). Do not frame missing cross-target contracts as an open problem.
- **Server binding and authorization context are expressible.** `examples/invoice/src/web/web.can:481` mounts each shared action using a named handler whose `near` parameters capture the pool, public origin and retention window. `:8`, `:32`, and `:65` receive `http::request`, decode the session cookie on every request, apply exact-Origin checks for writes, and call authorized domain operations. The request is explicitly included in the checked mount callable (`compiler/internal/check/action_bindings.go:180`). This is a workable request/auth context story, though session lifecycle, identity-provider integration and reusable policy composition remain application/library work. The language does not magically authenticate an action because it has a contract.
- **Typed transport distinguishes domain results from infrastructure failures.** The client uses canonical route captures, exact finite status/leaf agreement, bounded codecs and same-origin credentials (`runtime/platform/action-client.ts:6`, `runtime/platform/action-json.ts:313`, `:585`). Transport/codec failures are not mislabeled as a domain success. Captured paths are guarded against malformed values and ambiguous routes (current tests in `runtime/test/action-mount.test.ts:389`, `:609`, `:770`).
- **The grid covers more than a happy-path form.** `examples/invoice-grid/src/records/records.can:25` represents clean, dirty, saving, failure, uncertainty, denial and conflict separately; `:64` explains attempt ownership, the acknowledged snapshot, draft and focus intent. Current browser tests exercise typing, pending saves, conflict/replay, retained drafts, malformed bootstrap links, native keyboard cancellation and focus (`tests/integration/browser/grid.mjs:226`, `:319`, `:399` onward). App-specific state machines are not themselves a language defect.
- **Native resource lifecycle has useful guarantees.** `runtime/platform/browser.ts:286` aborts listeners, clears timers, removes view nodes and disposes scoped state. `:637` provides versioned state replacement, and `:474` uses native EventTarget/AbortController. This is a sound low-level basis for a library; no virtual DOM is required to obtain reusable UI composition.
- **Browser delivery is real and intentionally isolated.** The driver verifies assertion roots, emits a distinct browser entry, audits/bundles the graph and publishes content-addressed assets (`compiler/internal/driver/browser.go:51`, `:119`, `:122`). SQL/files/env/process/credentialed services are denied transitively (`compiler/internal/browser/browser.go:57`, `:121`). Tests inspect the grid bundle for server-only code and HTMX absence (`tests/integration/browser/grid.mjs:176`). Styling is possible through CSS assets and `html::stylesheet`; absence of inline style does not mean there is no styling (`compiler/internal/project/assets.go:29`, `runtime/platform/html.ts:445`).

## Prioritized limitations

### 1. Closed host surface prevents broad frontend capabilities — platform boundary/design choice, highest priority

The browser profile expressly has only main-thread and Bun targets, no worker or arbitrary authored-JS profile (`compiler/internal/browser/browser.go:1`, `:22`). The manifest only accepts source/error registry/project/dependencies/assets/sql (`compiler/internal/project/manifest.go:97`); dependency paths load Can packages, and unresolved external package names fail (`compiler/internal/resolve/symbols.go:392`). Authored script assets are also absent from the admitted asset-media table (`compiler/internal/project/assets.go:29`). Compiling *to* TypeScript does not supply a supported *from Can to arbitrary npm library* API.

The native DOM catalogue lists ~22 operations (`compiler/internal/check/browser.go:21`), fixed tags (`:52`), fixed attributes (`:68`) and ten events (`:85`). No pointer/touch/drag/composition event surface, History API, client storage, layout/measurement/observer API, canvas/SVG drawing or browser WebSocket access is present in this reviewed surface. WebSocket capability is explicitly server-only (`compiler/internal/browser/browser.go:71`). Native anchors and full-page navigation still work; a History-based client router is a different capability. These are not all required by every SaaS app, but the closed extension boundary makes ordinary chart, rich editor, upload, drag/drop, offline or real-time library adoption materially difficult.

**Acceptance exercise:** implement one useful third-party browser widget and one SaaS identity/payment SDK through a supported typed adapter mechanism, including target restriction, packaging, runtime error mapping, disposal, and immutable input/output adaptation. No hand-editing generated TypeScript and no compiler changes specific to the chosen vendor. If adapters are intentionally rejected, supply an explicit alternative supported application scope and demonstrate equivalent required capabilities in the catalogue.

### 2. DOM form state and event observations are incomplete — missing native contract, not just missing UI library

`runtime/platform/browser.ts:320` snapshots exactly `kind`, target id, string `value`, and `key`. It omits checkbox `checked`, multiple selected values, file handles, modifier keys and composition status. `:433` writes the HTML attribute via native `setAttribute`; no operation sets the live `value`/`checked` DOM property or reads selection/caret position. A reusable Can library cannot derive information the host boundary never exposes.

Fresh Chromium native-semantic probe:

- After a text input is edited to `user edit`, `setAttribute('value', 'normalized')` leaves actual `input.value` at `user edit`, although its attribute becomes `normalized`.
- A checkbox's checked and unchecked change events yield the identical current Can snapshot: `{kind:'change',target:'check',value:'on',key:''}`.

Exact source: `/tmp/can-review-20260926-platform-probes/dom-semantics.mjs`; observed output: `/tmp/can-review-20260926-platform-probes/dom-semantics.out.json`; successful stderr file is empty. This probe exercises native calls matching the adapter, **not the generated Can frontend end to end**. Chromium initially could not launch in the filesystem sandbox; the same local probe succeeded with the appropriate launch permission.

These results do not show `set_attribute` violating its promised attribute semantics. They show why controlled form components need additional primitives. Checkbox state can be approximately tracked by toggling app state for a narrowly controlled widget, and a dirty input can be rebuilt; neither is a general replacement for reading actual checked state or setting the live property while retaining focus/selection.

**Acceptance exercise:** an ordinary reusable field component with editable text normalization, checkbox, multiselect, file input and IME typing. Dirty text must receive a server correction without losing caret/focus; checkbox state must follow the actual control after reset/autofill; key modifiers and composition must be available where needed. Unmount/remount while a handler is awaiting must neither mutate disposed widgets nor leak listeners. Run the exercise against emitted Can in Chromium and another browser engine, not only fake DOM hosts.

### 3. Shared-action client has no author-visible deadline/cancellation — missing platform contract

The lower-level fetch function has `signal?: AbortSignal` (`runtime/platform/action-json.ts:246`) and forwards it (`:324`), but the catalogue client projection calls it without `signal` or a timeout (`:576`). `runtime/platform/action-client.ts:22` has only captures/body/site/context operands. The current grid waits for the shared action result before completing save/reread (`examples/invoice-grid/src/web/web.can:973`, `:992`), and mid-flight presses are ignored. A request that remains pending therefore has no app-controlled bounded completion or cancel path through this API. I did not independently run a never-responding-server probe; this finding is static API/adapter evidence.

Counterevidence: stale-attempt and uncertainty logic already protects the grid against late and uncertain results, and browser view disposal already owns listeners/timers. Those do not cancel this network request. A timeout must preserve “save may have committed,” not claim rollback. Render-view disposal should also not casually destroy an app-owned save merely because the grid rerendered.

**Acceptance exercise:** stall response headers and separately stall a response body; let the user navigate away or cancel/read again. Demonstrate an explicit deadline, correct unknown-commit state for interrupted writes, ignored late responses, and no indefinite pending state. Prove intended request ownership across rerenders separately from DOM view ownership.

### 4. Captured HTML GET pages are not representable — deliberate language/checker restriction

Plain route mounting rejects `:capture` segments (`compiler/internal/check/http.go:369`). The shared action checker requires GET actions to use JSON (`compiler/internal/check/actions.go:315`). Consequently a normal `/tenants/:tenant_id/invoices/:invoice_id/edit` server-rendered page cannot use either current checked route path. The example uses `/invoices/form?tenant_id=...&invoice_id=...` (`examples/invoice/src/web/web.can:407`, `:493`). This works and is not an authorization defect, but is a surprising hole in an otherwise typed route system.

**Acceptance exercise:** add a captured server-rendered read route with the same typed capture/URL-building/ambiguity checks, truthful denied/not-found/error status handling, and appropriate document rendering. Reuse the shared route machinery rather than creating a second URL grammar. Separately demonstrate typed client navigation/back/forward if a SPA router is intended.

### 5. UI reuse/composition needs a library proof — mostly missing library/ergonomics, with lifecycle primitive constraints

The grid's web module is 1,186 lines and model module 1,525 lines (including assertions/comments). `web.can:526` manually constructs cells, attributes and listeners; `:739` disposes/rebuilds views on structural changes; `:779`/`:802`/`:828` update selected text nodes in place to preserve typing. These are valid native DOM strategies, but most application code is handling mechanics that a reusable library should centralize. The runtime also prohibits appending a node from a different view except to the app root (`runtime/platform/browser.ts:451`), so independently disposable nested widgets need an explicit composition/ownership strategy.

Do not conclude “needs React,” “needs a virtual DOM,” or “all the line count is bad.” Can functions, records, callables and state cells could support considerable reuse. Prove that reuse before adding syntax. One visible consequence of current manual coordination is row amount cells staying stale while aggregate totals update: the current browser test explicitly waits for rerender to check amounts (`tests/integration/browser/grid.mjs:234`). This is a documented application behavior/UX limitation, not evidence of incorrect money arithmetic or a compiler defect.

**Acceptance exercise:** extract a reusable keyed editable table and a reusable field/error/status component, consume them in two apps with different domain records and actions, and independently dispose a nested component. Exercise insertion/reorder/deletion, focus/caret, errors, pending state and mid-flight edits. Clarify whether nested view ownership needs a primitive change or can be expressed cleanly using the existing lifetime model.

### 6. Qualified production path remains narrower than “compiles to Bun” — delivery/operations limitation

The reviewed path is build browser first, pair one manifest into server build, then serve the report-selected generation with the installed Bun. `examples/invoice/README.md:8` explicitly says `canlc run` rebuilds without pairing and cannot serve the grid. The root README states no Linux support is claimed and releases remain unsigned pending credentials. The operator owns schema setup and session provisioning in the example. None of these invalidate the language design, but broad SaaS readiness needs an operated deployment story rather than assuming Bun output automatically implies a supported Linux/container/service environment.

**Acceptance exercise:** from a clean supported install, create credentials/session, provision/migrate database, build and pair frontend/backend, deploy to the intended production host, roll forward/roll back both together, observe request/handler failures, and retain old browser assets during a rolling update. Demonstrate a deployable Linux/container path if that is the actual target; do not infer support from a cross-platform runtime alone.
