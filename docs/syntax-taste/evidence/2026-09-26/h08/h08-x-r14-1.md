# H08 X-R14-1: complete-call bound qualification analysis

**Verdict: no metering profile qualifies. W6-AI is blocked.**

A qualified metering profile must supply a conservative upper bound
U for the complete encoded call's provider input plus output
consumption — instructions, schemas/questions, provider overhead,
and applicable output limits — pinned to one provider/model/version.
What follows is every derivation H08 examined, why each fails or
what would repair it, and the exact evidence still missing. No
derivation below is adopted; the registration stays `unqualified`.

## Examined derivations

### 1. Provider-published enforced caps (the qualifying path — missing)

A U qualifies if the provider publishes, for the pinned
`typesafe/jev/1.13.0` identity, a hard complete-call token bound that
it enforces by rejecting over-limit requests: any admitted-then-
settled call then has actual usage A ≤ U by construction, and
over-limit attempts fail into conservative unresolved holds rather
than silent excess.

Status: no such published bound was found. The preparation reads
(TypeSafe docs index, HTTP API, Choice primitive) document completed
`usage.input_tokens`/`usage.output_tokens` and no request output-cap
field — accounting is decodable, but no enforceable input or total
cap is stated for any model. Live verification of over-limit
rejection additionally needs live access, which is itself blocked
(see `h08-report.md`).

Repair: a provider-published enforced bound for the pinned identity
plus live verification (usage decodes within U across the registered
cases; over-limit input fails closed with no silent consumption).

### 2. Pinned-bytes measurement (works only for fixed requests)

For exactly fixed request bytes and a pinned model version, the
provider tokenizer determines one exact input-token count, so one
live observation establishes it — no estimation involved.

Status: inapplicable to triage. Ticket subject/body text varies per
call, so no finite set of measurements covers future inputs. This
derivation qualifies only a degenerate fixed-request feature, not a
real triage profile. Adopting it here would silently narrow the
feature to its eval fixtures.

### 3. Measured-max-plus-margin over eval cases (rejected: not a proof)

Taking the maximum observed usage over the 18 frozen cases plus a
margin bounds the fixtures, not the feature: the next real ticket
can exceed it. That is estimation, in the same class the contract
excludes ("an estimated tokenizer count [is] not proof of such a
bound"). A margin is a hope with arithmetic, not a bound.

### 4. Byte-derived bounds, e.g. tokens ≤ bytes + overhead (rejected)

Byte caps (`maxBodyBytes`) bound request bytes, not provider tokens.
The contract states this directly: "Bytes … [are] not proof of such
a bound." Any bytes→tokens inequality rests on tokenizer internals
no provider guarantees in-repo; adopting one would be an
unverifiable assumption at the exact point the allowance must hold.

### 5. Full-context-window reservation (rejected: unpublished + unusable)

Reserving a whole context window per call would be conservative only
given (a) a published window for the pinned identity, (b) enforced
over-limit rejection, and (c) a separate output-side cap (SystemOne
has no request output-cap field). None of (a)–(c) is established for
`jev-1.13.0`, and a window-sized U would spend most of an epoch per
call, making the allowance unusable in practice. Not pursued.

### 6. Responses-leg profile (blocked on access)

The OpenAI Responses adapter sends `max_output_tokens`, which caps
only the output side; the input side (instructions + state + schema +
overhead) has the identical gap as derivations 1–4. No OpenAI
credential env name is adopted and no access exists, so the leg is
doubly blocked. It inherits this analysis when access lands.

## Missing evidence (exact)

1. A provider-published, enforced complete-call token bound for one
   pinned provider/model/version covering input (instructions,
   schema/questions, state, overhead) plus output.
2. Live verification against the registered cases: usage decodes
   within U on every settled call, and over-limit behavior fails
   closed (typed rejection, conservative holds, quarantine on
   breach).
3. Live access itself: explicit spend-cap approval and a pinned
   per-token price table (see `h08-report.md`).

Until all three land, every budgeted dispatch correctly rejects
with `ai_budget::unavailable/missing-qualification` before send —
proven with zero provider I/O by the rejection-only fixtures in
`runtime/test/ai-eval-triage.test.ts` — and that rejection is not a
successful live pass.
