# Can language review for SaaS — 26 September 2026

Reviewed revision: `2cb1bc35435ab5075d51f9f945adfb0e1f9dfe64`.

**I would now consider Can for a bounded SaaS pilot built around its supported stack. To recommend it as a normal choice across SaaS products, I need ordinary product requirements, reusable libraries and production operations to fit without repeatedly extending the compiler or working around the language's authoring rules.**

The central design has become convincing: immutable domain data, protected constructors, explicit failures, shared client/server contracts, executable examples and checked native boundaries work together. The next investment should make that foundation economical to use. My strongest conditions concern host extensibility, complete browser controls, bounded execution, reusable failure handling and test setup. Several are platform/library contracts; a larger syntax surface is not automatically the remedy.

| Application shape | My current recommendation |
| --- | --- |
| Controlled Bun backend or server-rendered tenant CRUD with supported SQL and fixed integrations | A credible pilot, with explicit operational acceptance tests and supported-host deployment. |
| Can-authored browser CRUD similar to invoice-grid | A credible evaluation project; validate the required controls, request lifetime and component reuse before committing the product to it. |
| Rich client with specialist widgets, browser SDKs, offline behavior or complex input | Establish the host integration and UI composition path first. Current closed APIs substantially constrain this scope. |
| Integration-heavy service with tenant-selected webhooks and durable workers | Prove destination policy, worker execution, deadlines and failure observation, or explicitly assign those responsibilities to companion services. |
| Production object-upload workflow | Resolve the cancellation/deletion contract discrepancy described below before relying on it. |

**What the current language gets right.**

- Shared actions now separate the wire contract from server implementation. Both targets import the same locked package; server handlers receive the request and capture startup services, then perform session/tenant checks in ordinary Can. This is a major improvement in actual application composition. See the [shared contract](/Users/vince/Projects/can-lang/shared/invoice-contract/src/invoice_contract/invoice_contract.can:98) and [server mounts](/Users/vince/Projects/can-lang/examples/invoice/src/web/web.can:481).
- Browser delivery now has a compiler-owned audited bundle, manifest pairing and explicit ownership runtime. This capability should be credited as implemented. See the [current build pipeline](/Users/vince/Projects/can-lang/docs/implementation/cli.md:23) and [browser driver](/Users/vince/Projects/can-lang/compiler/internal/driver/browser.go:51).
- Exported generics now support declaration-level symbolic composition, explicit callable/dictionary requirements and checked recursion patterns. Owner records defend construction and representation across package boundaries. These are useful foundations for reusable domain libraries. See [generic validation](/Users/vince/Projects/can-lang/compiler/internal/check/exported_generics.go:15) and [owner boundary tests](/Users/vince/Projects/can-lang/compiler/internal/check/owner_record_test.go:111).
- Transactions distinguish a chosen commit from a known committed result. The examples model tenant authorization, optimistic revisions, replay ledgers and outboxes rather than assuming retries are harmless. Preserve [commit uncertainty](/Users/vince/Projects/can-lang/runtime/platform/sql/transaction.ts:234) and the application-level reconciliation patterns.
- Native operations remain native: immutable adapters surround arrays, maps, promises, Bun transport and database calls. Typed fixtures and mandatory examples produce useful evidence, provided their scope remains explicit. The previous Unicode empty-match defect now uses native `matchAll`, and browser auditing has structural checks with benign-literal regression cases. See [regex scanning](/Users/vince/Projects/can-lang/runtime/text.ts:165) and [audit tests](/Users/vince/Projects/can-lang/compiler/internal/browser/audit_test.go:68).

**1. I would recommend Can more broadly if a missing host capability had a supported integration path.**

The compiler owns a closed native catalogue. Ordinary Can dependencies cannot introduce a JavaScript/npm binding; the browser build does not admit arbitrary script assets. Consequently a rich editor, charting widget, identity/payment SDK or missing browser API may require compiler/runtime changes. Compiling to TypeScript does not itself provide supported TypeScript interoperation. See [manifest admission](/Users/vince/Projects/can-lang/compiler/internal/project/manifest.go:97), [asset types](/Users/vince/Projects/can-lang/compiler/internal/project/assets.go:29) and [browser capability closure](/Users/vince/Projects/can-lang/compiler/internal/browser/browser.go:57).

There are useful existing boundaries: server code can invoke bounded processes and HTTP services; a companion frontend can communicate with a Can backend. The immediate limitation is especially consequential for missing in-process browser capabilities. It should not be exaggerated into an inability to integrate with anything.

My preferred experiment is small: add universal DOM primitives where needed, extract one ordinary Can widget, then integrate one genuinely required third-party widget. Compare a reviewed adapter with a companion implementation. An adapter needs explicit target availability, input/output types and copying, failure mapping, callback/reentrancy rules, ownership/disposal and reproducible packaging. Whether this should become a general extension system remains unsettled; the three Jev consultations chose three different approaches.

**Acceptance:** a second vendor integration can be added without a vendor-specific compiler patch or hand-edited generated code, while browser capability rejection and lifecycle tests remain meaningful. If the deliberate product choice is a closed platform, publish the supported SaaS scope and the companion architecture clearly.

**2. I would recommend the frontend if common controls and reusable components worked naturally.**

The current event snapshot contains `kind`, `target`, `value`, `key`. It lacks actual checkbox state, selected files, multiple selected values, modifiers and composition information. `set_attribute` delegates to native `setAttribute`; it does not expose a live input-value/checked property setter. A fresh Chromium probe confirmed two practical consequences: checked and unchecked checkbox changes produce identical current snapshots, and changing the value attribute after an edit leaves the live input value unchanged. This is a native semantic probe matching the adapter, not an end-to-end emitted-Can test or an attribute-setter correctness bug. See [event snapshots](/Users/vince/Projects/can-lang/runtime/platform/browser.ts:320) and the [probe](/Users/vince/Projects/can-lang/docs/syntax-taste/evidence/2026-09-26/full-review-2cb1bc3/platform-probes/dom-semantics.out.json).

The grid already handles immutable drafts, versioned state, stale results, conflicts and disposal. Its manual field callbacks, rebuilding and focus repair should now be extracted into ordinary libraries. Independently scoped nested widgets need particular attention: the current append contract restricts cross-view children except at the app root. A declarative component syntax should follow demonstrated library limitations, rather than being assumed necessary. See [view composition](/Users/vince/Projects/can-lang/runtime/platform/browser.ts:451) and [grid rendering](/Users/vince/Projects/can-lang/examples/invoice-grid/src/web/web.can:510).

**Acceptance:** two applications share a keyed editable table and field/error controls. Cover text normalization after editing, checkbox reset/autofill, multiselect, upload selection, IME, caret/focus, reordering, independent disposal and replies arriving after unmount. Small native property/event additions are necessary before a library can solve all of this.

There is also a narrow route-language gap: ordinary routes reject captures, while GET actions require JSON. Captured HTML read pages therefore use query-based URLs in the invoice example. Reuse the existing capture/URL machinery for server-rendered reads. This is a useful bounded extension, independent of adding a SPA router. See [plain route validation](/Users/vince/Projects/can-lang/compiler/internal/check/http.go:369) and [GET action checking](/Users/vince/Projects/can-lang/compiler/internal/check/actions.go:315).

**3. I would recommend production services if deadlines, cancellation and ownership formed one understandable contract.**

Race selection and scope completion have different timing. A fresh runtime probe selected the winner while the owning root remained pending until its loser completed. HTTP request handling waits for scope drainage before publishing a response. This preserves leases, but a race around slow work does not necessarily bound response latency. SQL query/transaction calls await native operations without caller-level deadlines. SQLite busy timing and database administration can help; declared server HTTP clients already have deadlines. See [SQL launch](/Users/vince/Projects/can-lang/runtime/platform/sql/pool.ts:88), [request drainage](/Users/vince/Projects/can-lang/runtime/platform/server.ts:289) and [the ownership probe](/Users/vince/Projects/can-lang/docs/syntax-taste/evidence/2026-09-26/full-review-2cb1bc3/backend-probes/race-drain.ts).

Browser shared actions have a separate gap: the lower fetch adapter accepts an abort signal, but `action::request` and `action::post` expose no transport deadline/cancellation operand and their projection supplies no signal. Timers and attempt IDs can change UI policy and ignore late results; they cannot inject an absent native abort contract. A cancelled save must retain uncertainty about whether it committed. See [action client inputs](/Users/vince/Projects/can-lang/compiler/internal/check/action_bindings.go:374) and [fetch construction](/Users/vince/Projects/can-lang/runtime/platform/action-json.ts:576).

Start with enforceable native operation budgets and an explicit request ownership model. Evaluate cooperative cancellation/supervised remaining work where that does not suffice. Do not release a live lease merely because a timer won. Existing server shutdown already demonstrates reliance on an external supervisor for permanently nonsettling work; that boundary needs clear operational documentation, not a promise that a timeout undoes effects. See [shutdown behavior](/Users/vince/Projects/can-lang/runtime/test/server.test.ts:664).

**Acceptance:** stalled SQL, response headers and response bodies; client disconnect; overlapping requests; SIGTERM. Show bounded user-visible behavior, defined shutdown escalation, no resource use after disposal, and honest unknown-write outcomes. These are the behaviors that passing finite assertion examples cannot establish.

**4. I would recommend the core for growing workloads if iteration had a predictable stack and memory model.**

A freshly checked/emitted synchronous tail-recursive countdown succeeds at 100 steps and overflows at 20,000 on local Bun 1.4.2. The runtime invokes the recursive thunk before suspension; async function syntax does not remove the native stack growth. This is an observed limit, not a violation of a promised tail-call guarantee. The exact emitted program and final logs are retained in [core probes](/Users/vince/Projects/can-lang/docs/syntax-taste/evidence/2026-09-26/full-review-2cb1bc3/core-probes/recurse-large-runtime-v3.log).

Array folds already cover stack-safe traversal of existing arrays. Dynamically continuing work needs an intentional approach: a small immutable-state iteration primitive or proven self-tail lowering to native loops. Compare both while preserving evaluation order, failure identity, fixture paths and diagnostic cost. Async recursion after real suspension has different behavior; the probe does not establish one universal recursion limit.

Bulk collection construction belongs to the same performance discussion. Repeated immutable map/set insertion copies prior content and can produce quadratic work for growing unique collections. Add useful native bulk construction/aggregation contracts before requiring users to discover this through latency. See [collection implementations](/Users/vince/Projects/can-lang/runtime/collections).

**Acceptance:** a 100,000-step state machine, a growing collection aggregation and a bounded worker batch, with measured stack/memory behavior and meaningful diagnostics. A new keyword alone is insufficient evidence.

**5. I would recommend Can library authoring if generic failure handling and test setup composed economically.**

Public generic value composition now works. The narrower remaining issue is that authored `emits` cannot quantify over an error set, while native collection helpers preserve callback-specific failure bounds. A reusable trace/retry helper must enumerate a fixed family or translate failures into result data. A fresh probe rejected a type parameter used as an error bound. A separate public generic using nominal success/failure data checked, emitted and executed five assertion roots successfully. That demonstrates representability and value forwarding; its examples do not independently prove retry count or success after an initial failure. See [core review and counterevidence](/Users/vince/Projects/can-lang/docs/syntax-taste/evidence/2026-09-26/full-review-2cb1bc3/independent-core.md).

I would first make the result-data approach concise and test its conversion/provenance costs. If reusable infrastructure still needs extensive adapters, evaluate an explicit finite error-set parameter. A broad effect system is not established as necessary. `emits []` currently says there are no escaping domain failures; it does not imply purity, absence of standard faults or termination.

Mandatory assertions have a related abstraction cost. A consumer cannot directly construct a foreign owner record, correctly. Its legitimate fallible smart constructor also cannot be called directly in an assertion argument, because the row has no setup region to handle failure. A private no-domain-error fixture helper can handle the constructor and fail the test through a standard fault on unexpected rejection; no public sample API is required. It still adds another function and assertion obligation merely to extract a safe helper. See [assertion grammar](/Users/vince/Projects/can-lang/compiler/internal/syntax/declarations.go:259) and [argument checking](/Users/vince/Projects/can-lang/compiler/internal/check/assertions.go:87).

**Acceptance:** reuse one infrastructure helper with two unrelated callback error sets; add an error to one caller without editing unrelated consumers. Extract a handler helper accepting an owner value while retaining useful tests and requiring minimal setup plumbing. Compare reusable test factories with checked test-local setup before weakening mandatory examples or permitting forged values.

**6. I would recommend everyday authoring if routine refactoring had less ceremony.**

Fresh probes confirmed that an exhaustive Boolean match with `true` before `false`, and a meaningful final local such as `subtotal = price * quantity; ok subtotal`, are compilation errors. These are intentional style policies. I would allow both and leave canonical spelling to formatting/lint. Separately, `near` captures bind using the callee parameter name in the caller's scope; renaming a library capture therefore changes source-level caller obligations even if the callable type is unchanged. Explicit binding and safe rename support would help. See [Boolean order](/Users/vince/Projects/can-lang/compiler/internal/check/completion_matches.go:444), [local forwarding](/Users/vince/Projects/can-lang/compiler/internal/check/locals.go:84) and [capture lookup](/Users/vince/Projects/can-lang/compiler/internal/check/callables.go:127).

The editor provides diagnostics and definition lookup. Completion, hover, references, rename and formatting are not advertised by the current LSP. The compiler has formatter machinery, so this is delivery/tooling work as well as language policy. See [LSP capabilities](/Users/vince/Projects/can-lang/compiler/lsp.go:156).

**Acceptance:** extract and rename a callback, change a shared record, inspect its inferred/declared contract and repair callers using normal editor tools. Keep the semantic guarantees while reducing incidental edits and test scaffolding.

**Production breadth that also affects my recommendation.**

SQL's supported subset is explicit and useful, but narrow: scalar row fields, bounded SELECT and mutations without RETURNING; schema changes remain operator-owned. JSON/timestamp/decimal workflows require chosen encodings or additional codecs. Integer minor-unit money already works well for invoices. Prove a real PostgreSQL application with generated identities, precise values, nullable audit times, JSON data, concurrent replay and a migration recipe before claiming broad relational portability. A SQLite reread-after-conflict algorithm does not transfer unchanged to an aborted PostgreSQL transaction. See [SQL schema admission](/Users/vince/Projects/can-lang/compiler/internal/types/sql_schema.go:32) and [statement admission](/Users/vince/Projects/can-lang/compiler/internal/sql/cardinality.go:30).

The webhook application demonstrates durable outbox/replay storage, but its carrier and retry scheduling live outside Can. A complete Can worker should prove bounded concurrency, claims across two workers, retries/backoff, poison jobs and crash recovery. Fixed-origin HTTP connections also need an explicit destination policy for tenant-configured webhooks. Dynamic WebSocket URLs already exist, so the HTTP restriction must not be generalized to all outbound protocols. See the [carrier boundary](/Users/vince/Projects/can-lang/examples/webhook/README.md:79).

Unexpected HTTP handler completions become fixed 500 responses without the default boundary reporting them. Authors can catch standard failures and log safe details, and SQL codes are available, but that relies on every application adding wrappers correctly. A redacted request-failure hook with correlation/source identity would make production diagnosis dependable. Main/late-owner reporting already provides useful machinery; browser callback reporting also exists. See [server failure conversion](/Users/vince/Projects/can-lang/runtime/platform/server.ts:300) and [logging](/Users/vince/Projects/can-lang/runtime/platform/log.ts:25).

There is an implemented Linux target: Debian 13-or-newer amd64/glibc, with pinned runtime, packaging/install and Docker smoke orchestration. The main README's contrary statement is stale. This review did not rerun that lane. Use and qualify the existing path for paired server/browser deployment, credential provisioning, migrations, rollout/rollback and retained old assets. A contract-locked build pair does not by itself prove how an already-open browser behaves against a newly deployed server; include that acceptance scenario. See [Linux target selection](/Users/vince/Projects/can-lang/distribution/manifest.go:196), [Linux workflow](/Users/vince/Projects/can-lang/distribution/linux/README.md) and [asset retention](/Users/vince/Projects/can-lang/compiler/internal/driver/pairing.go:19).

AI primitives are a useful differentiator: typed state, finite judgments/probabilities, structured output and raw-provider fixtures. Their shape guarantees do not establish prediction quality, cost or latency for a SaaS feature. Validate those separately and demonstrate tenant budgets/correlation and model-change evaluation. The current Responses adapter deliberately supports a narrow nonstreaming workflow; expand it only for an actual product requirement. See [AI response policy](/Users/vince/Projects/can-lang/runtime/ai/responses.ts:81).

**Concrete contract/example problems, separate from language proposals.**

1. **S3 cancellation can complete and delete the destination key.** The catalogue says cancellation releases the sink without completing and never deletes the key. Runtime cleanup instead calls `sink.end()` followed by `file(key).delete()`; its comment explicitly acknowledges removing a pre-existing object after writing begins. This is a source-confirmed contract discrepancy with data-loss implications, not a freshly executed live-S3 deletion experiment. Do not treat final absence of a new test key as proof that cancellation preserved an existing object or prevented transient publication. Resolve the contract and test cancellation while replacing an existing key, observer visibility and service failures. See [declared behavior](/Users/vince/Projects/can-lang/compiler/internal/catalogue/catalogue.json:12399) and [cleanup implementation](/Users/vince/Projects/can-lang/runtime/platform/s3.ts:204).
2. **The S3 stream deadline only checks between awaits.** It cannot bound a never-settling reader, writer, flush, completion or metadata operation. This differs from an effective abortable transport deadline. See [stream loop](/Users/vince/Projects/can-lang/runtime/platform/s3.ts:413). Qualification needs a stalled-await test, not only a slow finite producer.
3. **The invoice startup example teaches an obsolete workaround.** It calls `env::required("")` to synthesize failure and claims only catalogue calls can originate errors. Authored error completions already work. Replace that example with a meaningful startup error when updating it. See [the example](/Users/vince/Projects/can-lang/examples/invoice/src/web/web.can:502) and [error emission](/Users/vince/Projects/can-lang/compiler/internal/emit/regions.go:575).
4. **Documentation and deployment examples need one current supported story.** The top-level Linux/browser claims contradict implementation. The webhook sample explicitly omits constant-time signature comparison and carrier authorization; it is a scoped protocol demonstration, not a complete internet-facing deployment template. These should be corrected or bounded clearly in an authoritative user guide. See [webhook limits](/Users/vince/Projects/can-lang/examples/webhook/README.md:92).

**What I would build next to earn the recommendation.**

First close the concrete S3 contract issues and prove request budgets/failure reporting. Then use the existing invoice foundation for a second app with shared field/table libraries, additional native control semantics and one required external integration. In parallel, run a small library-authoring exercise covering fallible owner-value setup, result-data failure composition and constant-stack iteration. Finally operate the pair and a durable worker on the existing supported Linux path, including slow dependencies, crash recovery and a rolling deployment with an old browser still open.

Success would give me a positive recommendation for a well-defined, substantial class of SaaS products. The decisive evidence is that the second application and second integration get easier while the contracts remain trustworthy.
