## Minimal setup and file boundary

The future execution instrument is **T**, one separately reviewed Python standard-library parent outside every tested child. Select the existing `/opt/homebrew/opt/python@3.14/bin/python3.14` (observed 3.14.7), not an interpreter found implicitly at run time. Bun is the repository-pinned `.local-deps/pinned/bun-darwin-aarch64/bun`. Browser work uses the explicitly identified installed engine in its card. The [input record](preparation/native-can-test-preparatory-checks-2026-09-30/inputs.json) distinguishes observed identities from future preflight checks.

T is a disposable instrument for four fixed fixtures. It does not implement the proposed runner, generic native capability API, scheduler, Can binding catalogue or arbitrary command execution interface. Python POSIX mapping answers the descriptor mechanics question; Go `ExtraFiles` and the real product launcher stay untested. Direct candidate source import answers only source-level ingress; generated Can wiring stays untested. Do not expand a failed tiny job into building the compiler or N.

In the execution step, prepare/review only a small `owner.py` and the selected job's subject files inside one registered `/private/tmp/can-native-prep-<run-id>` root. Native files are `native-subject.ts` and `codec-subject.ts`; descriptor files are `descriptor-subject.ts` and `nonreader-subject.ts`; browser files are `browser-driver.ts` and a tiny HTML response served by T. A static allowlist of subject paths/operations replaces any generic evaluator. Scripts have no authority to edit product files. Source reads use fixed absolute imports; identify their transitive local modules before execution. Keep reference judging separate from candidate imports even though these early jobs use a host observer.

No compiler build, Go build, source/dependency copy, private package cache, app build, database, browser download, benchmark, full test command or worktree is needed. Bun uses explicit startup flags/config with installation and ambient env files disabled. Use synthetic descriptor values, no private credentials. Browser traffic generated by the fixture is loopback only; browser startup flags do not constitute a network sandbox, and this scope makes no egress-containment claim.

## Acceptance for each job

**PM-N1.** T fixes the complete action sequence before launch. Construct one getter-backed `then` object; return/alias only numeric handles. Before any explicit read, both observations report zero getter calls and the raw `Object.is` comparison confirms alias identity. An explicit read then causes exactly one getter call and the fixed thrown marker. The sealed action log contains every required action, without extra access. In a fresh control child, `Promise.resolve` must make the zero-access assertion fail. A rejection merely caught and omitted from the report cannot pass. This selects inert handles for this one value kind only.

**PM-N2.** After PM-N1's transport control works, send the getter-array handle to one fixed command invoking the imported `encodeJSON`. Use the actual `CodecIssue` class and observe `reason="type"`, `path=""`, zero getter calls and the wrapper's direct-invocation fact. Check these against fixed parent expectations; do not use a candidate verdict. First use an ordinary `[1n]` with the same inline schema as a setup witness and require exact encoded bytes `[1]`, preventing a malformed schema/setup rejection from impersonating the accessor result. The control reads index 0, catches its deliberate marker, then performs the same adapter call; the counter mismatch must fail. No mutation of candidate source is allowed. The setup witness and both variants belong to this one job's limits. This establishes neither emitted `createCodec` wiring nor an ordinary Can call.

**PM-F1.** Require four explicit legs: valid UTF-8 snapshot with empty/absent distinction and exact binary stdin; a withheld-EOF delivery failure; malformed non-string snapshot rejection; and non-reader exit with a stopped writer. Values, local deadlines and required outcomes are fixed in the descriptor card. T controls separate pipes and compares fixed facts, without accepting a child-provided verdict. Every leg closes descriptors and reaps its direct child. The non-reader leg cannot swallow a different child failure.

**PM-B1.** Use a button that submits a POST form navigation, rather than assuming a fetch-starting click stays pending. Observe the actual click promise directly. T receives a route token and a ping acknowledgment before sending its one-use resolve decision. The child log must show that the click had not settled before resolution, then show fulfillment and the exact parent-supplied response marker. T's independent server trace shows no POST because this minimal route is fulfilled locally. The negative child queues route decisions behind the click; its bounded failure must be detected and cleaned up. If the browser legitimately settles the positive click early, record **inconclusive**, retaining the order. Never make the input appear pending by delaying a wrapper acknowledgment. Upstream fetch, altered delivery, replay and durable effects remain outside this job.

For all jobs, acceptance requires the complete positive observations, the named negative-control detection, every declared leg and confirmed cleanup. A missing fact, extra effect, malformed/truncated frame, absent terminal seal, unexpected exit, exceeded limit or unresolved cleanup prevents `mechanism_supported`. A control's expected failure remains visible in the record; it is not a passing product test.

## Cleanup owner and recovery

The named cleanup owner for every job is **T, the surviving Python parent**. The implementing agent records its actual executable/script hashes, PID/start identity and run ID before launching subjects. T holds the cleanup authority; child `finally` blocks and driver close messages are advisory.

1. **Before allocation:** register a cleanup callback and a compact intent record outside the disposable root. Select a unique root name; create it exclusively with mode 0700. Immediately record its device/inode plus marker identity, hold a nonblocking ownership lock, and update the intent record. A reserved name alone is never enough authority to delete an existing directory.
2. **Before effects:** register pipe/socket/process/profile roles and cleanup actions. Close the startup signal race while spawning; retain direct child handles and record observed start identities before releasing the subject's ready barrier. The record describes permitted descendants before launch; it does not pretend to know future PIDs. Native/descriptor subjects cannot spawn children. The browser card defines the exact controlled engine launch and descendant observation.
3. **On every handled exit:** stop admitting operations; close writers and route decisions; request graceful child/browser shutdown within the cleanup reserve; terminate then kill still-owned processes if necessary; `wait` direct children; verify owned descendants are gone; close listeners/descriptors; verify the root/marker identity, remove only that root and verify removal. Return all failures and forced actions in a cleanup receipt. T cannot `waitpid` arbitrary grandchildren: it verifies their disappearance and records uncertainty if that cannot be established.
4. **After T disappears:** there is no successful result. Do not intentionally kill T in this preparatory batch. A later T may recover only the exact recorded owned root after obtaining its lock, validating identities and proving the recorded owner/subjects and relevant open references are inactive. Recheck process start identity before any signal; PID reuse is not authority. Use bounded process and open-reference inspection for this known graph. If identity/inactivity is uncertain, retain the compact recovery record, report the unresolved path/process and admit no further live job. Never kill processes by name or delete a directory merely because it is old.
5. **Terminal evidence:** copy only bounded identities, observations, control outcomes and the cleanup receipt to this preparation directory. Remove scratch immediately on successful cleanup. No persistent execution workspace, generated bundle or cache remains. Recovery failures are visible exceptions requiring resolution, not an undocumented retention policy.

The tiny instrument must be reviewed for these concrete obligations in the execution step. This is not an additional full-runner bootstrap project. It does not claim owner-SIGKILL recovery, arbitrary detached-process containment, hard memory/disk quotas or immutable source leases. T remains alive in all planned fault controls. Unsupported guarantees remain explicit integration work.

## Evidence and decisions after execution

Use result statuses `mechanism_supported`, `mechanism_failed`, `blocked` or `inconclusive`; the original pre-execution status was `scoped_unrun`; current statuses are in the linked results. Each record contains exact inputs and tool/source identities, script hashes, fixed expected facts, observed ordered facts, per-leg outcome, budget consumption, cleanup receipt and the limited claim it supports. Missing setup/tools are `blocked`; a valid setup producing contrary observations is `mechanism_failed`; an observation that cannot answer the question is `inconclusive`. Cleanup uncertainty prevents acceptance regardless of the positive leg.

After the bounded run, use the observations to revise the affected design. A bounded defect in the disposable instrument may justify a separately recorded repair/rerun; a failed native mechanism may require a different interface. Neither invites silently repeated trials until one succeeds. Keep all failed/inconclusive evidence. Only then review the design and prepare ordered parallel implementation lanes. Those lanes still include reference acceptance, external-owner implementation, ordinary Can bindings and integrated N1/N2/B1/F1 qualification before migration credit.

The [registered integrated experiments](preparation/native-can-test-hard-cases-2026-09-30/experiments.md) remain **unrun** after these preparatory scopes. In particular, opaque numeric edge cases, C-compiled ingress, Can-owned browser decisions/upstream effects, and Go/Can descriptor integration remain unproven. Four passing preparatory jobs would not close all those gates.
