# Post-upgrade review: implementation and decision reconciliation

24 September 2026 · source baseline `fbd2a5614dbba660b085b6fec8aef4f5d902c051` · review baseline `961f921a6a8cf40be54735683caf29613c19cbd8`

This reconciles every substantive finding in the [post-upgrade review](post-upgrade-language-review-961f921-2026-09-24.md) with current source and earlier selected requirements. The changes between the two baselines contain only the review and its evidence; compiler, runtime, catalogue and application sources are unchanged. The original review and its recorded probes remain historical evidence. This reconciliation changes documentation, not the language or implementation scope.

**The upgrade exists. Some accepted application contracts remain unfinished.** T01–T27 have recorded integration and test results, including a Can-authored invoice server and browser grid. Shared request-aware action binding and supported browser runtime delivery were already selected outcomes; passing the narrower test harness did not fulfill them. Public generic helper composition and most other language extensions require new decisions against deliberately retained or deferred rules.

## Classification and authority

- **Bug (B):** an implementation contradicts its existing operation contract, or documentation incorrectly describes implemented behavior/evidence. A documentation fix is not a runtime fix.
- **Unfinished accepted requirement (U):** an earlier selected outcome has only partial implementation or acceptance. This does not automatically select the review's proposed mechanism.
- **New proposal (P):** additional behavior, a change to a retained rule, or renewed consideration of a deferred feature. “New” is relative to accepted implementation scope; the idea may have appeared before. It does not mean approved for the next upgrade.

Positive findings and reminders of existing limits are recorded separately as **implemented/retained observations**, rather than inventing bugs or proposals for behavior the review already accepts. Recommendations with multiple parts are split below. The sequence and acceptance examples in the review map to these same findings; they are not additional grants of scope.

Earlier selection evidence comes from [decisions](decisions.md), the [September 22 dispositions](../implementation/language-design-dispositions-2026-09-22.md), the [September 24 selection ledger](preparation/design-disposition-ledger.md), and its linked contracts. The [T01–T27 execution record](can-implementation-task-list-2026-09-24.md) establishes what was integrated and what tests were reported. Neither current implementation nor a checked task silently overrides a selected requirement.

The preparation inputs were committed in `961f921`, after the T27 audit commit. T27's then-missing DI descriptions therefore cannot be used as current rejection decisions: the preparation ledger explicitly describes DI-11 browser scope, DI-13 companion observations, DI-14 SQL boundaries and DI-16 Linux support. The [T27 status correction](t27-release-audit-2026-09-24.md) preserves the original audit while exposing this provenance limit.

This is factual reconciliation, not selection among difficult design alternatives. No new Jev consultation or language decision was made. The saved consultations remain advice; later mechanism selection must follow the repository's three-fresh-request process. Can's AI-agent audience, native JavaScript/Bun lowering, immutability and lack of compatibility obligations remain constraints. Human familiarity alone is not a reason to reverse a rule.

## Verification and next boundary

Three parallel source audits checked core, platform and native/support findings; their [evidence index](evidence/2026-09-24/post-upgrade-reconciliation/README.md) records the baseline, checks and final documentation validation. Current source was compared with the earlier contracts and the saved review probes. The new records do not claim a fresh HTTP hedge, release build, installed Linux run, live database/provider flow or Playwright matrix.

The review's recorded compiler/runtime counts describe that review's commands. The earlier T19/T20/T25 results remain earlier evidence, including the repaired emulated Linux run; none is recast as a new execution. Agent-task comparisons still have no live attempts or demonstrated token advantage.

B03/B04 and the identified U06 documentation obligation are corrected as documented above. B01/B02 and U01–U05/S01–S03 remain open at this step. (Status 26 September 2026: all 11 are implemented and staged-qualified; see the [fix evidence](post-upgrade-fix-evidence-2026-09-26.md) and the [completion audit](post-upgrade-completion-audit-2026-09-26.md).) At this reconciliation step, P rows were proposals rather than selections; O01–O05 were retained observations and did not create new work. The subsequent disposition selects P03 as a bounded fix and records a decision for every other P row. Mechanism selection and the implementation graph still require their own design work; this factual ledger does not supply them implicitly.

The subsequent [next-upgrade dispositions](post-upgrade-dispositions-2026-09-24.md)
now select which of these findings to fix, retain or defer. The factual
classification and current-source evidence above remain the inputs to those
scope choices; the disposition does not claim implementation.
