## R04 — Budgets, cancellation, ownership (F-R04-01..06)

### (1) Best supported current Can idiom + actual limitation

- **Overlap work:** `match call concurrent` / `match call race` (first-success via native `Promise.any`) / `race with error` (native `Promise.race`), `docs/syntax-taste/decisions.md:2073-2110`, `docs/syntax-taste/coordination-spec.md:13-15`. Limitation: **selection ≠ cancellation**. `settle()` in `runtime/coordination.ts:102-165` publishes the winner but the losing participant's owner group stays live; the owning root cannot finish until every participant settles (`runtime/owner-core.ts:634-640` drain loop; `beginClose` waits for leases at `:332-354`, "Never force close or discard a live lease", `:642-643`).
- **HTTP request lifetime:** handler runs in a per-request `withScope`; response returns only after scope drain, and the request token is revoked after drainage (`runtime/platform/server.ts:284-293`). Limitation: **a race around slow work does not bound response latency** — the HTTP boundary waits for the loser (F-R04-01). Retained probe proves it (see §3).
- **SQL:** plain `sql::query_one/query_optional/query_rows/execute` and `sql::with_transaction` (`examples/sqlite/src/main.can:30-62`; `examples/invoice/src/model/model.can:939-965`). No caller deadline or cancellation operand exists anywhere on these paths: `runtime/platform/sql/pool.ts:88-124` (`launch`) and `:232-246` (`execute`) do `await client(template.strings, ...values)` directly under a `useResource` lease; `runtime/platform/sql/transaction.ts:199-229` awaits `client.begin(...)` directly; `openPostgresClient` passes only `{adapter:"postgres", bigint:true, max}` (`runtime/platform/sql/postgres.ts:57-78`). SQLite file pools accept `busy_timeout_ms` (`examples/sqlite/src/main.can:75`, `runtime/platform/sql/config.ts:25-41`, `runtime/platform/sql/sqlite.ts:99-104`) — **that bounds lock waits only, not query execution**. There is no Can spelling for `SET statement_timeout`: descriptors admit only SELECT (+trailing LIMIT) and RETURNING-free INSERT/UPDATE/DELETE (`compiler/internal/sql/cardinality.go:24-55`); anything else is rejected, so a session-timeout workaround through ordinary Can SQL is not available (F-R04-02).
- **Outbound server HTTP / AI (the contrast case):** declared `connection` blocks require literal `endpoint` + `timeout_ms` (`compiler/internal/check/connections.go:153-154`; e.g. `examples/native-ai/src/oracles/oracles.can:15-30`). At runtime each request gets a `Deadline` whose controller aborts native `fetch` (`signal: deadline.signal`), with bounded body reads (`runtime/transport/fetch.ts:43-98`, `runtime/transport/deadline.ts:40-97`, `runtime/transport/body.ts:26-37`). `http::timeout` carries `timeout_ms` (`runtime/transport/http.ts:55-57`). Limitation: per-operation cap, not a composed request budget; native/cleanup work stays owned until settlement.
- **Browser `action::request/post`:** typed calls over the shared contract (`examples/invoice-grid/src/web/web.can:18,46`; checker derives captures+body-only contracts, `compiler/internal/check/action_bindings.go:374-452`). The client projection (`runtime/platform/action-client.ts`) delegates to `fetchJsonAction`, whose `ActionFetchInput.signal?: AbortSignal` field exists (`runtime/platform/action-json.ts:246-256`) but **the projection never supplies it** (`:576-584` passes url/method/request/body/response/cases/requestLimit only). Best current idiom is UI policy only: attempt IDs + version-checked `browser::replace_state` to ignore late results (`examples/invoice-grid/src/web/web.can:68-99`), which cannot abort the wire request. A cancelled save must keep commit uncertainty (`runtime/platform/action-json.ts:590-594` maps `aborted` to `transport_failed("cancelled")`, "must not be read as server rollback") (F-R04-03).
- **Shutdown:** explicit `server_stop` closes sessions, then `closeResource` with `shutdownMs`, returning `shutdown_failed("deadline")` while the resource stays closing (`runtime/platform/server.ts:478-486`); `server_wait` installs SIGINT/SIGTERM handlers that call `closeResource` **without** a deadline and await `native.settled`, so `shutdownMs` is not a signal-path wait bound (`:488-511`). Catalogue wording is honest: "timeout does not revoke ownership" (`compiler/internal/catalogue/catalogue.json:9140`, `:9173`). `sql::pool_close` likewise: "Drain leases then close with remaining deadline; leave timed-out close owned" (F-R04-04).

### (2) Platform / primary-source facts

- **Bun.SQL (pinned `bun-types@1.4.2`, `node_modules/bun-types/sql.d.ts`):**
  - Connection options expose `connectionTimeout` (default 30 s), `idleTimeout`/`maxLifetime` (default 0 = none) (`:276-327`). **No per-query execution-timeout option exists** — consistent with "backend defaults may eventually fail; that is not a request-level latency guarantee."
  - `Query<T> extends Promise<T>` has `active`, `cancelled`, and **`cancel(): Query<T>` — "Cancels the executing query"** (`:454-470`). Queries are lazy until awaited/executed (`:477-482`). Can never retains this handle (`await client(...)` inline), so this native foothold is currently unused. Whether `cancel()` issues a real PostgreSQL cancel request vs. only client-side abandonment is **not stated in the type docs** — needs isolated qualification.
  - `reserve({signal})` aborts only pool reservation while still queued (`:96-100`), not a running query.
  - `close({timeout})` takes **seconds** (`:683-693`); Can converts ms→s at `runtime/platform/sql/pool.ts:273-277` — correct units.
- **fetch/AbortSignal (WHATWG Fetch + DOM Standard, stable; same behavior in Bun and browsers):** `fetch(url,{signal})` rejects with `AbortError` DOMException; Can's `Deadline.expire()` aborts the controller and races an `expired` promise (`runtime/transport/deadline.ts:70-92`); body-reader cancel is requested on timeout (`runtime/transport/fetch.ts:71-72`, `runtime/transport/body.ts:55-58`). `ownerSignal` integration exists (`deadline.ts:55-68`) but **no production caller passes it** (only `fetch.ts:16,43` reference it outside tests) — a foothold for a future ingress-lifetime signal, not a live policy.
- **Signal handling (Bun/Node `process.on`, POSIX):** SIGTERM/SIGINT are catchable; Can registers in `server_wait` (`runtime/platform/server.ts:503-504`). Delivery is context-free, so each firing re-enters ownership via `guardCallback` on the server scope (`:491-501`). There is no in-process substitute for the supervisor's SIGKILL bound.
- **Recorded env pins (from P02.4, not re-verified here):** PostgreSQL 17.11, Chromium 140 / WebKit 26, Debian 13+ amd64, Go 1.27.1 (Go verified locally).

### (3) Probes

- **None run — deliberately.** The retained `race-drain` probe (`docs/syntax-taste/evidence/2026-09-26/full-review-2cb1bc3/backend-probes/race-drain.ts` + `.stdout.txt`) is undisputed and fully consistent with current source: `{"phase":"winner selected","rootDone":false,…}` then `{"phase":"loser released","rootDone":true,…}`. It is corroborated by `runtime/test/coordination.test.ts:537-583` ("retains a losing participant's captured resource until late work finishes": `finished === false` after selection, `leases > 0` until the loser resolves). Rerunning would re-prove an uncontested deterministic semantic at fan/thermal cost on this Air; code is unchanged since the review (zero drift per P01). No HTTP-latency benchmark was or is claimed — the probe establishes selection-vs-lifetime timing only.
- SQL/S3 stall probes were not run: the gaps are structural in source (no deadline operand threaded, no retained cancel handle), so a probe could only demonstrate the already-evident unbounded await.

### (4) Facts vs uncertainties vs counterexamples

- **Facts:** race selection leaves root pending until loser settles; request scope drains before response (`server.ts:289-290`); SQL paths take no deadline; browser action projection supplies no signal; signal-path shutdown has no wait bound; `server_stop`/`pool_close`/stream-close deadlines are *waiting* deadlines that leave work owned (`owner-core.ts:359-390`, `STREAM_CLOSE_MS = 5000` at `runtime/transport/stream/lifecycle.ts:21`).
- **Uncertainties:** `Bun.SQL Query.cancel()` actual server-side effect per dialect; whether Bun's `Request`/serve stack exposes a disconnect signal Can could project (no `request.signal` read anywhere today); what "remaining request budget" composition should be (serial 5 s + 5 s + 5 s vs one 5 s budget — reconciliation §"Why operation deadlines alone are insufficient").
- **Counterexamples (things that DO work today):** outbound fetch/LLM/TypeSafe deadlines with native abort; `process::run` deadline → SIGTERM-then-SIGKILL of the process group with reaping (`runtime/platform/process/spawn.ts:209-247`, `wait.ts:12-36`) — the one true native-termination path (though reporting still awaits exit+drain, so return is not exactly at deadline); WebSocket handshake timer closes the socket (`runtime/platform/websocket.ts:463-493`); `stream::cancel_reader` precancel interrupts a pending read (`runtime/transport/stream/lifecycle.ts:169-189`); SQLite `busy_timeout_ms` bounds lock waits; `sql::pool_close(pool, ms)` caller deadline exists at the close layer (`examples/native-ai/src/app/main.can:50`).

### (5) Guarantees to preserve

Owner drainage, leases never revoked by timers, `commit_unknown` on post-decision failure (`runtime/platform/sql/transaction.ts:234-252`), loser-capture retention (`coordination.test.ts:537-583`), honest unknown-write outcomes on cancel/timeout, explicit-supervisor shutdown boundary (`server.test.ts:664-708` requires SIGKILL for nonsettling work), byte/budget caps that exist today. Per P06 disposition: changed ownership stays deferred until a real HTTP hedge measurement compares operation-local deadlines vs cooperative abort vs supervised loser ownership.

### (6) Technical decision vs user syntax choice

- **Technical decisions (need design + measurement, not taste):** operation-interruption contracts per adapter (SQL cancel semantics, S3, streams); request-budget composition + disconnect/SIGTERM propagation policy; shutdown escalation documentation (F-R04-04/05/06). Prior reconciliation already decided the layering: operation contracts first, under a written request-policy spec.
- **Possible syntax after evidence:** a caller deadline/cancellation operand on SQL and on `action::request/post` — but only once the native contract it maps to is qualified; no syntax is established as necessary yet.

## R12 — Failure observation (F-R12-01..03)

### (1) Best supported current Can idiom + actual limitation

- **Authored catch + log works today:** `match call …` with a `[_] as standard_failure failure` arm exposes `failure.kind/message/occurrence_id` (`compiler/testdata/current/arrays/contracts.can:106-112` — `standard_stop`; `:171-176` — `nonfinite_sort`); `log::write_info/write_error` emit `{"level","message"}` JSON lines to stderr (`compiler/testdata/current/cli/utilities.can:13-52`; `runtime/platform/log.ts:25-56`). SQL failures carry sanitized `operation`/`code` (`runtime/platform/sql/errors.ts:54-58`), Postgres preserves SQLSTATE in `code` (`runtime/platform/sql/postgres.ts:32-41`). A mapped 503 + manual log is expressible per handler.
- **The gap (F-R12-01):** the default server boundary converts any failed `Completion` to fixed 500 and swallows thrown faults with no diagnostic (`runtime/platform/server.ts:300-313`; `Bun.serve error:` → fixed 500 at `:341`). Handler faults inside the JSON-action adapter likewise become fixed 500s (`runtime/platform/action-json.ts:184-201`). An unexpected fault in the logging wrapper itself, in response adaptation, dispatch, or scope drain therefore produces **zero server-side records** — F-R12-03's fragility point. `runtime/platform/log.ts` writes only level+message: correlation IDs, structured safe fields, and timing are manual conventions.

### (2) Platform / primary-source facts

- No new platform dependency is needed: the redaction/diagnostic machinery already exists in-repo. Entry reporting (`runtime/entry.ts:20-56`) redacts payloads (`"<redacted>"`), identifies domain errors by `can.error.v2:` declaration identity + type identity, standard failures by category + occurrence, and never serializes native messages/paths/credentials (`:20-25`). Late/cleanup owner diagnostics carry `{kind, phase, occurrence, category, message}` (`runtime/owner-core.ts:21-27,129-153`) and are delivered through the root reporter (`entry.ts:87`). Browser handler faults report once per occurrence through a sealed record `{phase, occurrence, category, file, line, column}` via `console.error`, with native causes/stacks/secrets never crossing (`runtime/browser/diagnostics.ts:38-93`), invoked on every failed event/timer callback (`runtime/platform/browser.ts:301-319`).
- Occurrence identity: every standard failure allocates a `bigint` occurrence ID (`runtime/failure.ts:30-36`); domain failures carry occurrence IDs + native/emitted provenance (`runtime/failure.ts:22-24`, `freezeProvenance`).

### (3) Probes

- None run. The finding is a source-level control-flow fact (both conversion sites return fixed responses with no report call on any path), fully corroborated by the backend reconciliation's counterevidence review. A live probe (failing handler → observe stderr) would add nothing unless disputing that `fixed(500)` paths are silent, which they textually are.

### (4) Facts vs uncertainties vs counterexamples

- **Facts:** silent-500 conversion at the two cited sites; manual catch+log idiom proven by maintained fixtures; `log::write_*` level+message only; main/late-owner/browser reporters exist and redact.
- **Uncertainties:** what correlation/source identity a hook should carry (request ID? route? occurrence linkage?); whether reporting belongs in `serveOuter` only or also `dispatch`/adapter layers; redaction rules for request context (reuse `entry.ts` policy vs new).
- **Counterexamples:** main-function failures DO report (redacted, exit 1, `entry.ts:89-97`); late-owner failures DO report; browser handler faults DO report once per occurrence (S02, `browser.ts:307-319`); handled SQL failures are fully inspectable in-band. The missing piece is narrowly the **server request boundary's default reporter**, not a general inability to observe failures.

### (5) Guarantees to preserve

Fixed safe client responses (no payload leakage — `fixed(500)` carries no wire detail); failure-identity preservation (occurrence IDs, domain declaration identity); redaction of secrets/native messages; "diagnostic delivery alone cannot invalidate an already selected completion" (`owner-core.ts:140-141`); exactly-once-per-occurrence reporting discipline shared by owner and browser reporters.

### (6) Technical decision vs user syntax choice

- **Entirely a technical decision** (F-R12-02): a small automatic redacted request-failure hook with correlation/source identity, reusing main/late-owner/browser machinery — no syntax change established as necessary. [Coordinator correction of a stray non-English word in the research packet; meaning unchanged.] Open design points: hook shape (built-in reporter vs author-registered callback — note an author callback that itself throws must not break the boundary, cf. browser `settle` at `browser.ts:307-319`), correlation ID source, and the documented manual policy for expected failures. No user syntax choice is implicated.

## R15 — S3 cancellation/deadlines (F-R15-01..04) — contract defect, not taste

### (1) Best supported current Can idiom + actual limitation

- **Multipart uploads:** `s3::begin_upload` (no I/O until first write) → `s3::upload_write*` → `s3::upload_finish` → metadata, or `s3::cancel_upload` (`runtime/platform/s3.ts:643-724`). Catalogue contract for cancel: *"Retire the handle and release the sink without completing, so the key never materializes; never deletes the key"* (`compiler/internal/catalogue/catalogue.json:12399`; identical at `std/catalogue/README.md:541`).
- **Actual behavior contradicts the contract (F-R15-01):** `scrub()` (`runtime/platform/s3.ts:199-225`) calls `await sink.end()` — **completing** the upload — then `await client.file(key).delete()`, with the comment explicitly acknowledging *"A pre-existing key under the same name is removed rather than preserved once the first byte was written; completion is the only sink release the pinned API offers"* (`:211-213`). Both awaits are best-effort/suppressed (`:215-224`). `retire()` marks cancelled *before* cleanup (`:226-232`), so the handle reads `cancelled` while the key is transiently completed-then-deleted underneath. Same `scrub` path serves write_stream aborts (`:404-409`, `:471-475`) and scope-drain abandonment (upload closer at `:669-677`).
- **Streamed writes:** `s3::write_stream(client,key,reader,options,max_bytes,deadline_ms)` — catalogue: *"Pump a byte reader into a multipart upload under byte and deadline budgets"* (`catalogue.json:11983-12031`). Actual deadline (`runtime/platform/s3.ts:413-474`): a `Date.now()` check **at the top of each loop iteration only** (`:432-435`); the `source.read()` (`:438`), `sink.write/flush` (`:457-458`), terminal `pump().end()` (`:465`), and post-success `statOf` (`:467`) awaits are unbounded — a never-settling await hangs past the deadline forever, and final success never rechecks expiry (F-R15-03). There is no timer, no race, no native abort in this path — strictly weaker than the transport `Deadline` used for HTTP.

### (2) Platform / primary-source facts

- **Pinned `bun-types@1.4.2` S3 surface (`node_modules/bun-types/s3.d.ts`):** `S3File.writer(options?: S3Options): NetworkSink` (`:584`); `NetworkSink` extends file-sink with `write/flush/end(error?: Error)` (`:69-91`) — **no `abort()` method**, confirming the "no abort" half of the `scrub` comment. `S3File.delete()` exists (`:791`).
- **New open question from the pinned types:** the writer doc example states *"Writer will automatically abort multipart upload on error"* (`:574-583`), and `end()` accepts an optional `Error` (`:91`). Whether `sink.end(new Error(...))` releases the event-loop pin *without* completing/publishing the key is **unstated** — this is the single highest-value question for isolated storage qualification, since an affirmative answer would let cancel honor "never materializes; never deletes" without the end+delete sequence. The current code never tries it (calls bare `end()`), and the "un-ended sink pins the Bun event loop forever (unref and GC do not release it)" claim (`s3.ts:204-206`) is taken as reported, not independently verified here.
- **S3 semantics (AWS S3 documented behavior, stable):** S3 has offered strong read-after-write consistency for PUT/DELETE since December 2020, so a transiently completed key is promptly visible to readers — the end+delete window is genuinely observable, and `delete()` after completion removes whatever object is current at the key, including a pre-existing one. Conditional writes (`If-None-Match`/`If-Match`, added November 2024) are a possible future guard but are not in the pinned Bun surface used here. Overwrites are last-writer-wins; there is no transactional MPU-cancel primitive at the S3 API level beyond AbortMultipartUpload, which Bun's sink does not expose.
- **Versions:** Bun 1.4.2 observed locally; S3-compatible test endpoint was unavailable at review (12 S3 tests skipped) and remains unprovisioned here — no live storage was touched.

### (3) Probes

- None run, per the explicit prohibition on live deletion experiments. Both findings are established by direct source contradiction (catalogue text vs implementation text) plus the implementation's own comments. A probe is unnecessary to confirm the *discrepancy*; only the *remedy* (`end(error)` semantics, replacement-key preservation) needs future live testing in an isolated disposable bucket.

### (4) Facts vs uncertainties vs counterexamples

- **Facts:** catalogue-vs-`scrub` contradiction is textual and complete; between-awaits-only deadline is textual; live tests assert only *new-key absence* after cancel (`runtime/test/s3.test.ts:771,784-785`, `:685`, `:719`), never old-object preservation — so "absence of a new test key proves nothing about preservation" (F-R15-02); the S3 deadline live test uses a slow-finite producer (500 ms pulls, 50 ms deadline, asserts eventual `timeout` + `pulls <= 2`, `:688-721`) and asserts no latency bound and no hung-pull behavior (F-R15-04); lazy sink creation means pre-first-byte failures never touch the service (`s3.ts:404-409`) — cancel-before-write is safe, cancel-after-first-byte is the dangerous window; `uploadFinish` failure leaves the handle open for retry-or-cancel (`:711-715`).
- **Uncertainties:** `end(error)` semantics (above); whether any observer can see the transient key *during* cancel (cleanup awaits both, so post-cancel observation is settled-absent — but concurrent readers during the window are untested); service-failure behavior of each `scrub` await (suppressed by design); multipart-part garbage/orphaned uploads on failure paths (AbortMultipartUpload never issued — potential orphaned parts/cost, unexamined).
- **Counterexamples:** `s3::delete` is honestly specified ("Delete idempotently", catalogue) and implemented as direct `file.delete()` (`s3.ts:510-525`); read paths are honestly bounded by eager stat + counting wrapper (`:319-361`); `write_bytes` is a single atomic-ish PUT with no cancel semantics needed (`:362-384`).

### (5) Guarantees to preserve

Whichever contract is chosen must then hold absolutely: either true "never materializes; never deletes" (requires a verified no-complete release path) or an explicitly destructive cancel contract with caller-visible warnings — plus honest unknown-outcome reporting on any ambiguous completion, no silent `delete()` of caller data under a "cancel" name, and the existing terminal-state guards (`upload_closed` after finish/cancel, `s3.test.ts:416-444,749-752`).

### (6) Technical decision vs user syntax choice + required future qualification

- **Technical decision only:** resolve the contract discrepancy (fix code to match catalogue, or re-specify the catalogue with data-loss warnings — the former is strongly indicated). No syntax is implicated.
- **Isolated storage qualification must test (F-R15-02/04), in a disposable bucket with env-provided credentials, never in this packet:** (a) **cancel-while-replacing an existing key**: seed key with known bytes+etag → begin/write/cancel → assert original bytes+etag preserved (this is the test that distinguishes preservation from absence); (b) **observer visibility**: concurrent reader polling during cancel/write_stream abort, asserting it never observes partial/transient bytes; (c) **never-settling awaits**: hung `source.read`, hung writer, hung `end()`, hung `stat` under `write_stream` deadline — assert bounded return; (d) `sink.end(Error)` semantics: pin release + key non-materialization; (e) service-failure injection at each `scrub` await; (f) orphaned-multipart-part accounting after failures. Local fakes cannot establish (a)/(b); substitutes are explicitly insufficient per P02.4.
