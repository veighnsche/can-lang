# Browser execution and shared contracts: evidence packet

24 September 2026. Preparation evidence only; no browser architecture, syntax, or implementation is selected here. Can's confirmed audience is AI coding agents, human comfort is not a goal, and total tokens per successful coding task is a secondary measured objective ([decision](../decisions.md#design-direction)). The recommendation program's rich-client gate asks whether an editable invoice grid can be authored in Can; its server-driven gate is narrower ([Gate 5](../can-recommendation-program-2026-09-24.md#gate-5--support-a-can-authored-rich-client)).

## Verified present boundary

* [P1](../platform-testing-spec.md#p1-authority-scope-and-classifications) and [P11](../platform-testing-spec.md#p11-htmx-distribution-and-browser-boundary) specify Bun execution for application Can and upstream HTMX plus ordinary HTML in the browser. The compiler-owned HTMX asset is the only admitted executable browser asset; project JS, TS, HTML, SVG/XML and WebAssembly are rejected. The maintained catalogue is the only platform extension path; applications cannot import arbitrary native modules. The [compiler emitter](../../../compiler/internal/emit/program_state.go) imports server runtime code. This is a deliberate current target boundary, not evidence that a browser compiler cannot be built.
* [P9](../platform-testing-spec.md#p9-safe-html-and-htmx-constructors) and [runtime/platform/html.ts](../../../runtime/platform/html.ts) provide catalogue-owned safe HTML, escaped text, validated URLs/attributes, `hx-get`/`hx-post`, ID targets, inner/outer swaps, change/input/poll triggers, indicators and disable-this. Inline event handlers, authored scripts and raw HTML are excluded. The author-tag inventory includes tables and form controls but excludes `dialog`, `canvas` and SVG. The present `role`, `aria-*` and `tabindex` attributes can express some semantics but do not implement keyboard handling.
* The [signup renderer](../../../examples/form-validation/src/render/render.can) separately spells `/signup/validate`, `name`, `tags`, `note` and a target ID; the [server](../../../examples/form-validation/src/web/web.can) mounts and decodes the corresponding operation. `html::url` proves URL admission, not route existence, request compatibility or target presence. Exact static routes and shallow form fields are the current [HTTP contract](../platform-testing-spec.md#p10-http-request-response-routing-and-server-catalogue): `str`, `option::value<str>` and `str[]`, with explicit application parsing needed for other values. This is a cross-boundary contract gap relevant to either browser option.
* The [runtime response policy](../../../runtime/platform/html.ts) swaps 422 but excludes 400–599 otherwise; the [account search handler](../../../examples/account-search/src/web/web.can) returns a 503 feedback fragment on database failure. Thus its intended target feedback is not displayed under the default policy. This is source-verified; a specific 503 account-search browser reproduction was not run. Existing [Chromium integration scripts](../../../tests/integration/browser/accounts.mjs) exercise 200/422 swaps, polling and no external requests; the [asset script](../../../tests/integration/browser/assets.mjs) checks 500 no-swap. The Go browser test is conditional on a staged Bun archive and installed Playwright Chromium ([harness](../../../tests/integration/applications_test.go)). These tests do not exercise local Can state, rollback, offline drafts or component disposal.

## Reusable data contracts and their limits

* [C4](../technical-spec.md#c4) defines nominal immutable records, finite named variants and copy-update; variants are unwrapped native values in memory. [A6.1](../ai-io-spec.md#a61-admitted-values-and-representations) derives an exact JSON wire codec for primitives, arrays, ordinary records/errors and tagged variants. All record fields are required; unknown/duplicate fields fail; `option::value<T>` is a tagged ordinary variant, not JSON null. Opaque resources, functions, choice arms, connections and byte buffers are not generally wire-admissible. This is a concrete candidate for sharing server/browser data shapes, but shared source type identity does not automatically make a separately compiled browser decoder validate the same way.
* The codec admits public ordinary record construction and decoding. A record named `email` or `positive_seats` is nominal but does not itself guarantee application validation. The [review's protected-value finding](../saas-language-review-2026-09-24.md#4-i-would-recommend-can-if-applications-could-enforce-their-own-valid-value-construction) applies at the browser/server boundary: an untrusted client payload must be validated by the protected server operation even if a browser compiler typechecks it. A client-held tenant ID cannot authorize a mutation; server operation-bound authorization remains necessary.
* Can's `int` JSON contract preserves exact mathematical integers from original number tokens and canonical decimal output; `float` uses finite binary64 ([A6.1](../ai-io-spec.md#a61-admitted-values-and-representations)). Grid totals involving money therefore need the same exact-domain representation and rounding rule on client and server. A test should compare totals and serialized bytes at limits, rather than assuming native browser `Number` can faithfully hold Can's full `int` domain. Any browser target must preserve immutable native aliases and non-thenable completion boxing across promises ([C4](../technical-spec.md#c4)); sending server runtime modules directly to the browser would not satisfy target separation.

## Browser facts relevant to the grid

* The [W3C ARIA grid pattern](https://www.w3.org/WAI/ARIA/apg/patterns/grid/) describes an interactive grid as a composite widget requiring authored focus management, arrow/Home/End navigation and distinct editing/navigation behavior. Its [editable data-grid examples](https://www.w3.org/WAI/ARIA/apg/patterns/grid/examples/data-grids/) warn that browser and assistive-technology combinations need testing. A semantic HTML table with ordinary inputs is also a valid baseline to compare; adopting `role=grid` incurs the additional keyboard contract. These are accessibility interaction requirements, not a selection of rendering technology.
* Native browser [Fetch](https://fetch.spec.whatwg.org/) accepts an `AbortSignal` and defines abort behavior for a request and response body. Aborting on view disposal can stop local work, but cannot prove that a server mutation was not committed. The grid's save protocol needs revision/conflict or idempotency behavior and explicit handling of a response arriving after a newer edit or after unmount. That last sentence is an inference from the native abort contract and the requested optimistic interaction, not a feature Can currently provides.
* The [HTML online state](https://html.spec.whatwg.org/multipage/system-state.html) can emit online/offline events when its heuristic changes. The standard says `true` means the user agent might be online and explicitly calls the attribute inherently unreliable; it does not prove that this application's endpoint is reachable. A failed fetch, timeout or server response must drive real save state. “Useful offline behavior” must be defined: preserving an in-memory draft until navigation differs from durable offline editing and eventual upload.
* If durable local drafts are in scope, [IndexedDB](https://www.w3.org/TR/IndexedDB/) supplies browser transactions, while the [Storage Standard](https://storage.spec.whatwg.org/) describes implementation-defined quotas and best-effort versus persistent buckets. Neither source makes unsent edits automatically durable forever. The product must decide whether offline work survives reload, storage eviction and device loss; test the stated promise. The grid acceptance wording currently leaves that open.

## Viable baselines to compare, without a decision

| Baseline | What current evidence supports | What a bounded probe must establish |
| --- | --- | --- |
| Current Can SSR + HTMX | Safe server fragments, forms, validation swaps, indicators and polling already work. An HTML table/form can retain rejected input after a server round trip. | Can the product narrow its grid requirement to server-driven editing? Under the stated requirement of local unsaved drafts, immediate calculations, keyboard model and rollback authored in Can, the current boundary does not supply those operations. Test latency and no-swap failure display before claiming adequacy. |
| Can browser execution target | Shared Can declarations and exact wire codecs offer a plausible contract source. Native browser DOM, event, Fetch and storage operations are available. | Produce a minimal separately compiled browser bundle with a browser-only catalogue; demonstrate type/codec parity, immutable state transitions, event/focus handling, save ownership, disposal, capability rejection and actual browser/version qualification. No frontend framework or syntax is implied. |
| Typed bridge to an established browser language | The current server could expose a typed JSON action and an external browser client could implement the rich grid. The same endpoint/wire contract work is required. | Show generated or checked client contract drift diagnostics, authorization and error mapping, and browser interaction tests. This qualifies Can as the server language for that app; it does not prove a Can-authored frontend. |

The baseline comparison should use the same invoice rows, edits, responses and injected failures. Record generated-code size and agent edit/diagnostic/repair effort only after the agent-evaluation and token criteria are agreed ([preparation stages 2–4](../can-design-preparation-2026-09-24.md#2-agree-the-target-and-evaluation-criteria)). Human syntax convenience alone is not a valid discriminator under Can's frozen identity.

## Open contracts for a representative probe

1. **Endpoint and wire identity:** one operation should connect route, path parameters, request decoder, response cases, URL/action use and client call. A route or field rename should either diagnose all consumers or be explicitly classified as a runtime-tested bridge. Distinguish safe URL parsing from router membership and target existence. Coordinate this with the server flow/form work.
2. **State and rollback:** define draft, acknowledged server revision, pending mutation ID, optimistic display, failure/409/422 responses and the rollback/rebase rule for edits made during an in-flight save. Specify which state survives navigation and reload, and whether a retry can duplicate a business effect. Use server authorization on every protected operation.
3. **Lifecycle and cancellation:** identify ownership of DOM listeners, timers, in-flight fetches, pending saves and retained draft storage. Demonstrate cleanup when a view is removed, including late success/failure after disposal. Abort is a resource action, not proof of server rollback.
4. **Accessibility and HTML coverage:** choose the table-versus-interactive-grid keyboard contract based on the actual interaction; test focus, edit mode, labels, field errors and announced save status with keyboard and assistive technology on a named browser matrix. Inventory `dialog`, canvas and SVG use cases separately before widening the safe author surface.
5. **Capability separation:** browser compilation must reject server-only `env`, SQL pools, process/files and server HTTP operations transitively through imports and generics. Shared data/validation code needs a documented browser-safe dependency closure. The controlled catalogue must specify native browser emission recipes and conformance cases; do not reuse Bun-only runtime modules by assumption.
6. **Observable evidence:** inject slow, failed, duplicated and out-of-order saves; disconnect and reconnect; navigate away mid-request; reload with unsent edits if persistence is promised. Assert displayed totals and error status, focus, network requests, server rows, and absence of leaked listeners/requests. Current source-level `=> ok` on an opaque response does not establish these browser observations ([review](../saas-language-review-2026-09-24.md#6-i-would-recommend-can-if-attached-tests-and-runtime-checks-proved-what-the-user-sees)).

## Claims still unverified

There is no measured Can browser bundle, browser-safe catalogue closure, shared-codec cross-target conformance, rich-grid prototype, offline durability test or assistive-technology matrix in the inspected evidence. The cited reviews correctly identify a missing browser model, but their desired state/event/renderer vocabulary is a proposal. Browser capability, performance, agent ergonomics and token outcomes require the bounded experiments above. The current spec is sometimes ahead of implementation by its own [status statement](../platform-testing-spec.md); source and executable tests must determine each claimed implemented behavior before a final design or recommendation.
