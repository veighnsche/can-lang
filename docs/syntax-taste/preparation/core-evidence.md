## Pattern and variant identity

The current ordinary-match rule first tries to resolve a bare name as an admitted nominal leaf. An unresolved unqualified name becomes a whole-value binding with `any` coverage; a qualified or explicitly specialized non-leaf fails ([pattern checker](../../../compiler/internal/check/patterns.go#L65), [spec](../technical-spec.md#L156)). Thus current source implies `decliend` in the final arm of a `paid | pending | declined` match is accepted as a catch-all and remains accepted after a new leaf is added. The correct three-leaf match becomes non-exhaustive after that addition. The earlier [probe summary](../evidence/2026-09-24/clean-room-full-review/probe-summary.json) executed and confirmed all three outcomes, and confirmed `decliend()` fails, at the prior reviewed revision. The current source still encodes the rule, but this task did not rerun that Can program. The evidence does not identify which replacement syntax is best.

`Assignable` on current HEAD first rejects differing specializations of one generic declaration, even if its type parameter is phantom; it then accepts a leaf or a different variant whose complete leaf set is included in the expected variant ([compatibility](../../../compiler/internal/types/compatibility.go#L9)). Current `TestPhantomVariantArgumentsRemainInvariant` and `TestNominalAndVariantCompatibility` pass. The earlier [three variant probes](../evidence/2026-09-24/clean-room-full-review/probe-summary.json) show `tagged<int> -> tagged<str>` rejected directly, but `tagged<int> -> bridge -> tagged<str>` and narrowing through the `unit` leaf accepted when all three variants admit only `unit`. A variant has no source constructor/wrapper; values are the nominal leaves ([spec](../technical-spec.md#L133), [runtime JSON encoding](../../../runtime/codec/json.ts#L108)). This is an assignment-rule inconsistency, not a demonstrated runtime identity or memory failure. Ordinary generic records have their own specialized nominal identities; the phantom-variant probe does not establish a generic-record problem.

Current idiom: declare independent record leaves and a closed named variant, construct a leaf directly, then match bare leaf names; within an arm the scrutinee is narrowed and can be copy-updated as that record ([decisions](../decisions.md#L1690), [spec](../technical-spec.md#L135)). `option::value<T>` follows this ordinary `none`/`some<T>` shape ([spec](../technical-spec.md#L135), [codec fixture](../../../compiler/testdata/current/codec/roundtrip.can#L62)).

## Authored validated values and decoding

Source records and errors are marked constructible without a separate construction-visibility bit ([symbol creation](../../../compiler/internal/resolve/symbols.go#L291)). Qualified lookup applies the declaration's one `Public` bit, including constructor lookup, and an exported signature cannot expose a private type ([lookup](../../../compiler/internal/resolve/symbols.go#L425), [signature check](../../../compiler/internal/resolve/symbols.go#L601)). Record construction is positional in declared field order, public fields can be projected, and `with` creates a same-type value with named replacements ([decisions](../decisions.md#L1707), [constructor checker](../../../compiler/internal/check/expressions.go#L356), [update checker](../../../compiler/internal/types/compatibility.go#L66)). Runtime values are frozen nominal records and updates create fresh frozen records ([runtime data](../../../runtime/data.ts#L21)); immutability does not enforce a predicate such as valid email or positive quantity across every creation path.

Codec specialization builds a schema from the concrete type graph. Ordinary records/errors expose each declared field, and variants expose the flattened leaves; opaque resources and callables are rejected ([schema](../../../compiler/internal/types/schema.go#L45), [codec specialization](../../../compiler/internal/check/codec.go#L118)). JSON and other document decoders project wire fields into a nominal record with `record(node.identity, entries)` directly ([projector](../../../runtime/codec/project.ts#L168)); the source factory is not involved. A currently transparent `email(str value)` could therefore be constructed by an importer, copy-updated, or decoded from structurally valid but semantically invalid wire data. That last point is a source-and-runtime inference, not a newly executed public-email probe. The existing [codec roundtrip fixture](../../../compiler/testdata/current/codec/roundtrip.can#L1) demonstrates current explicit `codec::encode_json<T>`/`decode_json<T>` use and option variant tags.

Current idiom: use a transparent nominal record plus an explicit validating function at ingress and operation boundaries; retain a separate validation result or error for failed input. The [form-validation example](../../../examples/form-validation/src/model/model.can#L1) maps a shallow decoded form to a response view; it does not claim an unforgeable domain value. A private record cannot be returned from a public function under the current visibility rule. The recommendation's email, positive quantity, and tenant identifier are benchmark candidates, not implemented abstractions ([program Gate 2](../can-recommendation-program-2026-09-24.md#L41)). A tenant identifier's structural validity would not prove actor authorization at an invoice operation.

## Generic operations and finite errors

Authored generic declarations are checked at concrete specialization sites, including the whole body and unused branches ([specialization loop](../../../compiler/internal/check/program.go#L487), [whole-body test](../../../compiler/internal/check/specialize_test.go#L54)). `identity<item>` works for the admitted `int` and `str` instances in the fixture, but a body operation such as `+` is admitted or rejected after substitution; the public generic header does not enumerate required operations ([operator checker](../../../compiler/internal/check/expressions.go#L169), [spec C4](../technical-spec.md#L131)). The current compiler catches invalid concrete uses; the issue is what a separate library's public signature communicates before use. The existing [generic gallery function](../../../examples/gallery/src/25-generic-function.can#L1) illustrates parametric forwarding, while [generic array fixture](../../../compiler/testdata/current/arrays/main.can#L181) illustrates a body that requires concrete operator support.

`emits` entries must resolve to named error declarations; type parameters are not eligible in the error-use namespace ([eligibility](../../../compiler/internal/resolve/symbols.go#L94), [bound check](../../../compiler/internal/resolve/symbols.go#L593)). Callable compatibility accepts a concrete callback error subset of an explicitly written larger bound; it does not quantify over an arbitrary finite error set ([compatibility](../../../compiler/internal/types/compatibility.go#L42), [callable bound test](../../../compiler/internal/check/callables_test.go#L120)). The compiler-owned array operations calculate their bound from the actual callback errors ([array contract](../../../compiler/internal/check/array.go#L223)). This confirms a difference between catalogue `map`/`filter` and an ordinary authored generic wrapper. It does not prove that every useful `retry` or `audit` helper needs new error syntax.

Current idioms to benchmark: `match chain` sequences fallible calls with a written error set and explicit terminal handlers ([account-search model](../../../examples/account-search/src/model/model.can#L15), [codec roundtrip](../../../compiler/testdata/current/codec/roundtrip.can#L8)); a named helper can accept a callable with one concrete finite bound and handle or relay each case ([account-search model](../../../examples/account-search/src/model/model.can#L15)); a record/variant result-as-data shape could carry failures through a generic data parameter, but I did not find a maintained example proving that exact wrapper pattern. The example's `search_accounts_model` instead converts SQL failures to `search_view` status data. A result-as-data benchmark should therefore be measured, not cited as already successful. Explicit callable or dictionary-record parameters are expressible with today's named functions and records, but I found no maintained library example establishing their cost for two unrelated operations and error sets.

## Captures and construction

Only named top-level functions are declared; `callable name` makes a value and `near` marks captured inputs ([decisions](../decisions.md#L113), [capture fixture](../../../compiler/testdata/current/callables/captures.can#L14)). At a reference site, the checker synthesizes a name lookup using the callee's exact parameter spelling, then requires its exact type ([capture resolution](../../../compiler/internal/check/callables.go#L124)). The [capture test](../../../compiler/internal/check/callables_test.go#L23) verifies captured positions, and its refusal tests cover missing and mistyped captures. Runtime closure creation retains the selected immutable values ([runtime callable](../../../runtime/callable.ts#L25)). Consequently, a callee parameter rename may break a reference site, while a same-typed local with the new name may change what is captured; the latter is a source-rule inference and needs a dedicated controlled-change execution in the product slice.

Current explicit baseline: put request context in a record and pass it as a normal argument or receiver; named methods can be referenced with their receiver captured ([decisions](../decisions.md#L1129), [capture fixture](../../../compiler/testdata/current/callables/captures.can#L47)). `near` reduces explicit argument passing where the ambient names line up. The proposed invoice slice should compare these under a callee rename and a same-typed shadow, rather than assuming a new capture form is necessary ([program Gate 3](../can-recommendation-program-2026-09-24.md#L51)).

Constructor arguments are parsed as plain ordered expressions, and checker index `i` is checked against field `i` ([parser](../../../compiler/internal/syntax/expressions.go#L204), [checker](../../../compiler/internal/check/expressions.go#L367)). No named constructor-argument form is present in that path. `triage_report` has adjacent `int total` and `int recent`, and its call passes `numbers[1].value, numbers[0].value` in that order ([record](../../../examples/native-ai/src/records/records.can#L11), [call](../../../examples/native-ai/src/app/main.can#L61)). Swapping those fields and arguments can typecheck while changing meaning. The source inspection proves same-type positional exposure, but this task did not execute the controlled reorder. `with` replacement is already field-named; it solves updates, not creation ([decisions](../decisions.md#L1742)).

## Confirmation boundaries

| Claim | Status in this note |
| --- | --- |
| Generic variant direct rejection and different-variant leaf inclusion | Current source and focused type tests; older exact Can programs executed at the unchanged compiler revision. |
| Bare-name typo becomes whole-value match binding | Current checker source; older exact Can program executed at the unchanged compiler revision. |

| An explicit callable/dictionary record is adequate for generic operation contracts | Expressible in current grammar, but not established by a representative multi-package benchmark. |
| Same-typed `near` shadow changes the captured value | Follows current lexical name resolution; no dedicated controlled-change runtime probe was run here. |
| Same-typed positional field reorder silently changes behavior | Source shows the susceptible constructor and example; no controlled reorder execution was run here. |

## Questions still open for the design round

1. Which variant identity rule should direct, bridge, leaf, ordinary `option<T>`, and generic-record cases jointly obey? The present probes establish behavior but do not select semantics.
2. What must be observable or constructible for a package-owned immutable value across factory calls, equality, matching, `with`, assertions, generic decoding, and schema derivation? In particular, where may decoded wire data enter the owner-controlled construction path?
3. How much do current `match chain`, named-helper, fixed-bound, explicit-operation, and result-as-data idioms cost for one helper serving two distinct finite error sets and two operation requirements? No maintained fixture answers that exact benchmark.
4. What compiler-visible operation requirements should a public generic signature reveal, if explicit callable/dictionary inputs prove insufficient on the benchmark? Current concrete-specialization checks establish correctness only for known applications.
5. Do an explicit context record and current positional construction survive the invoice slice's parameter rename, same-typed shadow, and same-typed field reorder with acceptable diagnostics and behavior? The existing source shows the risks; the product mutation run is still outstanding.

These questions are evidence boundaries. No new syntax, runtime behavior, or design selection was made here.
