# DI-05b error identity consumer audit

24 September 2026. Source inspection only; this is a comparison input, not an adopted contract, migration, or Jev consultation. The [package/assertion evidence](packages-assertions-evidence.md#package-and-error-identity-already-in-use), [I1–I3 alternatives](core-alternatives.md#di-05b--application-error-identity-and-reporting-codes), and [three earlier consultation findings](jev-core-contracts/findings.md#di-05b-audit-requirements-before-treating-a-report-key-as-a-design) motivate the audit. Those findings explicitly left outside reporting needs and rename policy unknown. `AGENTS.md` says there are zero external users and no compatibility requirement for old syntax, ABI, generated layouts, or goldens; that removes a migration obligation, but does not itself choose a reporting contract.

The actual externally visible domain line has both `"id":1000000` and a full `typeIdentity`; the integer is currently a convenience field, not the only information emitted. Its short `error` name alone does not identify an independently loaded owner. The [root reporter](../../../runtime/entry.ts#L24) deliberately redacts payload and native messages, which every candidate must preserve. No reviewed repository source establishes a consumer that stores a **naked** application ID and resolves it across two different locked builds, or requires that a number survive declaration rename. That is an evidence boundary, not proof such a requirement cannot arise. No two-build report interpretation test or published rename/retirement policy was found; acceptance below makes those questions explicit.

## Exact trial cases for I1, I2, and I3

Use two independently authored dependencies `A` and `B` with distinct canonical project/package owners, and a root that imports and triggers both. Keep dependency source and registries untouched for the **current-input I1 trial**; I2/I3 require a declared source/registry migration and must be scored on migrated inputs, never credited for accepting old numeric source unchanged. Resolve the separate duplicate-short-package-name issue through an explicit DI-05a trial precondition; do not let that earlier loader rejection masquerade as an error-identity result. Preserve catalogue reservations, direct dependency visibility, lock reproducibility, exact type matching, and redaction.

1. **Active/active:** `A::failed` and `B::failed` both allocate `1000000` in their owner registries. Build, invoke each failure separately, and decode two distinct terminal reports. I1 reports `(canonical owner A,1000000)` versus `(canonical owner B,1000000)`; local retirement may not reserve the foreign number. I2 reports distinct build-local integers with a collision-free reverse map from each integer to its qualified declaration, and includes build/manifest identity. I3 reports two distinct qualified textual declaration keys directly. Every option preserves distinct nominal type identities and accepts both dependencies without author coordination.
2. **Active/foreign-retired:** `A` has active `1000001`, while `B` retires `1000001` and has another active error. Both projects load; `B` cannot reuse its **own** retired identity under the candidate's retirement policy. I1 scopes the numeric tombstone to `B`. I2/I3 must specify owner-key tombstones and prove they do not reserve `A`'s active declaration. Trigger `A`'s active failure and decode it unambiguously.
3. **Generic specialization:** Trigger `A::failed<int>` and `A::failed<str>` with the same declaration-level reporting allocation. Their reports may share I1's owner/number, I2's mapped number, or I3's declaration key, but must include concrete argument/type identity sufficient to distinguish them; checked matching, bounds, and assertion comparison remain exact. A report code cannot stand in for a nominal error type.
4. **Two locked builds:** Build 1 contains `A` and `B`; capture their reports and archive its lock plus any report map. Build 2 adds unrelated dependency `C` (and, separately, relocates checkout without changing the graph); capture the same triggered errors. Decode both generations using only the artifacts the contract promises to retain. I1 must keep the same owner/number for unchanged declarations and must show how canonical owner identity survives graph growth or explicitly delimit when it changes. I2 may renumber after adding `C`, but each report must identify its build and decode against that build's archived collision-free reverse map; within one locked graph, allocation must be deterministic. I3 must keep the same textual key for unchanged canonical declarations; an optional compact number is build-local metadata and needs its own map if reported. Relocation must not affect identities under any candidate. Then rename one declaration and retire its old reporting identity: specify whether old reports remain interpretable, whether the new declaration has a new key/code, and what owner metadata forbids old-key reuse. Current sources do not settle that rename policy.

For each case inspect source and registry edits, lock diff, emitted plan, runtime admission, actual JSON line, assertion/bound behavior, and agent repair cost. A naked hash without collision resolution cannot satisfy I2 uniqueness. These are acceptance criteria for comparison, not an implementation choice.
