# DI-03/DI-04: current generic-helper idioms

This preparation probe uses one separate `helper` package and two `main` callers with disjoint finite domain-error sets: `domain::a_failure` and `domain::b_failure` ([error declarations](probes/generic-helper/src/domain/domain.can)). It changes no language rule or canonical decision. The complete reproducible project is [here](probes/generic-helper/can.project.json); its [helper](probes/generic-helper/src/helper/helper.can) and [callers](probes/generic-helper/src/main/main.can) are the examples, not pseudocode.

The test criteria, fixed before running the program, were: (1) an exported helper should serve both callers while each public caller still emits only its own typed error; (2) success and failure paths should retain the distinction between the two domains, without a catch-all failure; and (3) a consumer should see the two required operations, integer transformation and acceptance check, in the public helper signature. The direct [`match chain` callers](probes/generic-helper/src/main/main.can#L45) provide the current no-shared-helper baseline.

| Idiom | Observed result | Measured source cost, including assertions |
| --- | --- | --- |
| Direct `match chain` | Each caller has its exact error contract and clear sequential handling; the transformation and check are repeated in both callers. | `a_chain` + `b_chain`: 27 lines. |
| Named helper with fixed written bound | [`audit_fixed`](probes/generic-helper/src/helper/helper.can#L45) accepts both concrete callback subsets and its signature spells `transform` and `inspect`. Each caller's [fixed wrapper](probes/generic-helper/src/main/main.can#L72) must handle **both** errors, even though its action can produce only one. The sample maps the impossible other error to its own error so the wrapper keeps an exact outward bound. A caller that instead relays all kinds would expose both errors. | Shared helper: 18 lines; two success callers: 17 lines; each caller has one extra completion arm and conversion. |
| Generic result as data | [`outcome<int, failure>`](probes/generic-helper/src/helper/helper.can#L8) carries a different nominal failure record per caller. [`audit_data<failure>`](probes/generic-helper/src/helper/helper.can#L63) handles both without a domain `emits` bound. Each caller needs an [adapter into data](probes/generic-helper/src/main/main.can#L106) and an [adapter back to its own domain error](probes/generic-helper/src/main/main.can#L135). Both operations remain explicit callable arguments. | Shared generic helper: 17 lines, plus 7 lines of generic result declarations; two success adapters: 14 lines; two outward callers: 16 lines. Failure-path fixtures add further mirrored adapters/callers. |

The data result preserves *data type* distinction (`a_detail` versus `b_detail`) and the two outward functions reconstitute their respective named Can errors. It does not transport Can completion errors transparently: conversion code is required at each boundary. The fixed-bound idiom also retains named error kinds rather than merging them, but exact caller signatures require code for a bound member the callback cannot emit. For a small one-off workflow, the two direct chains were shorter than either shared approach; this is a source-count observation, not an agent-maintenance or runtime-performance result.

Reproduce from the repository root (the archive is the pinned local development input):

```sh
go run ./tools/distbuild --archive .local-deps/bun-darwin-aarch64.zip --out /private/tmp/can-generic-helper-bundle --version generic-helper-probe
/private/tmp/can-generic-helper-bundle/can-generic-helper-probe-bun-1.4.2-darwin-arm64-v1/bin/canlc build /Users/vince/Projects/can-lang/docs/syntax-taste/preparation/probes/generic-helper
python3 docs/syntax-taste/preparation/probes/generic-helper/negative-probes.py /private/tmp/can-generic-helper-bundle/can-generic-helper-probe-bun-1.4.2-darwin-arm64-v1/bin/canlc
```

On the tested revision, the build returned `validation: verified` and **28/28 real-Can assertion roots passed**, covering success and actual A/B failures for the fixed and data forms. The [negative script](probes/generic-helper/negative-probes.py) produced exit 1 for both controlled edits: omitting the fixed wrapper's B arm reported `missing completion arm for domain::b_failure; ... audit_fixed requires an arm for each bound member`; passing `callable double` where a `callable bool (int) emits []` inspection operation is required reported `expression type does not fit expected type at byte 1691`. The latter checks the contract at the consumer, though its byte-offset diagnostic is less helpful than naming `inspect` and the expected callable type.

The build's generated TypeScript contains a separate `audit_data` specialization for each concrete failure record, invokes the supplied callables, and dispatches named domain completions in the fixed helper. Its runtime assertions confirm the observable success/error behavior. Generated `dist/` is compiler output and is intentionally outside the evidence sources. Each caller has a singleton finite error set, so this probe establishes the cross-caller mismatch but does not measure growth with multiple errors per domain. It also does not establish whether a new finite error-set parameter or capability vocabulary is justified; that requires a workflow/repair benchmark beyond this single integer helper.
