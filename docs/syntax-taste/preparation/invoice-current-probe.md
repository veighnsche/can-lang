# Bounded current-Can invoice edit probe

24 September 2026. Scope fixed before compilation: one shallow form record with string `seats`, `details`, and `revision` fields; explicit `text::to_int` conversion and domain bounds; a server supplied actor/tenant context checked with the invoice's tenant at the protected edit operation; five explicit application result cases (saved, invalid with raw text retained, forbidden, conflict, unavailable). One SQLite `UPDATE` descriptor will use tenant, invoice, and revision predicates and report affected rows. This is a current-language evidence slice for DI-09/13/14, with no compiler or runtime change and no claim of SaaS qualification.

Predeclared checks: `canlc build` must compile and run attached assertions for valid edit, invalid number, out-of-range seats, stale revision, cross-tenant invoice, and unavailable storage. `canlc run` is attempted only if the project can have a minimal runnable entry point. The SQLite descriptor must pass static admission; an actual SQLite transaction and durable row test are stretch checks, reported as unrun if unavailable. No HTTP request, browser swap, production database, concurrent membership change, or commit-unknown injection is part of this probe. After the first successful build, I added an exploratory handler boundary with `http::request_form` and five opaque response assertions. Those added checks were not part of the original predeclared set.

The strongest bounded idiom is a shallow [`invoice_form`](probes/invoice-current/src/main/main.can#L6), explicit [`validate_edit`](probes/invoice-current/src/main/main.can#L39), and named [`protected_edit`](probes/invoice-current/src/main/main.can#L60) that accepts a server-supplied actor context and stored invoice. It produces 200, 422 with the exact rejected strings, 403 for actor/tenant mismatch, 409 for a stale revision, or 503 for a simulated unavailable store. The [`decode_and_edit`](probes/invoice-current/src/main/main.can#L121) boundary compiles against the actual native request form decoder, but no request was sent to it. Badly encoded or structurally invalid forms map to a generic 422 because the decoder has not produced a record whose values could be retained. The [`form_response`](probes/invoice-current/src/main/main.can#L105) function constructs a status and text body; its attached `=> ok` assertions only prove execution, not the status or body.

The [SQLite descriptor](probes/invoice-current/can.project.json) admits a parameterized `UPDATE` with tenant, invoice ID and revision in its `WHERE` clause, and [`save_invoice`](probes/invoice-current/src/main/main.can#L88) exposes affected rows. Its assertion supplies a SQL completion. The descriptor is **not connected to `protected_edit`**, and this slice neither opens SQLite nor executes a transaction. Thus the 200 case is an application decision over supplied state, not proof of a persisted invoice edit or checked membership. A real handler still needs to resolve actor and resource from server-controlled state, then perform the protected write and classify zero affected rows inside a transaction. This is the deliberate boundary of the smaller path allowed by the probe scope, not a product implementation.

I copied the source project to `/private/tmp/can-invoice-current-probe` before building, so generated output stayed outside the evidence directory. On the tested checkout, the bundled development `canlc build /private/tmp/can-invoice-current-probe` returned `validation: verified`, **18/18 assertion roots passed**, with `real-can` and `supplied-completion` evidence. `canlc run /private/tmp/can-invoice-current-probe` exited 0 with no output. The 18 roots comprise four validation cases, six operation cases, one fixture-supplied SQL case, five opaque response cases, one fixture-supplied decoder case, and the no-op entry point. The project is 145 lines of Can including comments, blanks and attached assertions, plus one line of SQL manifest; `validate_edit` occupies lines 39–57, `protected_edit` 60–85, SQL adapter 88–102, and HTTP mapping/decoder 105–136. There is no syntax, compiler, or runtime change.

The first local `bin/canlc build` attempt failed with `CAN-DIST-UNBUNDLED: build a development distribution first`; the pinned Bun development bundle resolved that environment requirement. During authoring, the bundled compiler reported `exported signature exposes private type can.project.root/invoice_probe::invoice_row`, then `root project requires void main(str[] args)`, then `assertion saved arguments: assertion arguments omit a required input`. Exporting the record, adding `main`, and supplying the fixture argument respectively resolved those errors. No compiler or assertion failure remains in the final probe.

No HTTP protocol response, DOM target swap, focus/error announcement, live database row, concurrent authorization change, revision race, schema drift, or uncertain commit was observed. A browser or durable SQL claim requires separate protocol/browser/database checks as specified by [the evaluation protocol](evaluation-protocol.md) and [DI-09/13/14 alternatives](product-alternatives.md). This result only shows that today's language can express the bounded validation and status branches, not that they satisfy the complete server product flow.
