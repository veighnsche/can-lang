The TypeSafe [HTTP API](https://docs.typesafe.ai/api.md), [Choice guidance](https://docs.typesafe.ai/primitives/choice.md) and [documentation index](https://docs.typesafe.ai/llms.txt) were read live.

Three complete fresh requests to `jev-latest` compared publisher-declared project and instance IDs, root-lock-assigned IDs, and content-derived IDs. Every explanatory state field, question and option description was rewritten. The [wording audit](wording-audit.json) records the semantic comparison and exact-string checks. Raw [requests](request-1.json), [2](request-2.json), [3](request-3.json), [responses](response-1.json), [2](response-2.json), [3](response-3.json), and [reproducible caller](consult.py) are saved; the credential is not saved. Confidence was 0.89, 0.87 and 0.51. There is agreement on the leading label but a meaningful third-request shift toward root-lock allocation. Jev gives no rationale. The engineering investigation is that root-lock IDs can survive local alias edits when the same lock is carried forward, but a dependency imported by two unrelated roots could receive different report keys; publisher-wide retirement would require another durable owner identity. Content IDs are relocation-stable but change after any owner source edit, even when an existing error declaration is untouched. Publisher-declared IDs impose minting discipline but make ownership independent of the importing root.

The consultation described a release UUID as immutable. That wording is too strict if a harmless source/import edit is meant to preserve an unchanged declaration's report identity. The [planned contract](../package-error-contract.md) instead defines an **instance lineage UUID**, stable through compatible owner edits, plus a separately verified per-build content/edge snapshot. Two divergent snapshots under the same lineage may exist in different archived builds but cannot both be linked in one build; side-by-side versions require distinct lineage IDs. This refinement follows the identity requirements and is an engineering decision, not a behavior Jev tested. It also means an owner must preserve an append-only retired-name ledger across updates; a single current snapshot cannot prove all historical non-reuse in isolation.
