## Current behavior and best usable idioms

### Scoped resources and transactions

`runtime/owner.ts` assigns each resource a private token, root, lexical scope, state, native value and owner-keyed leases. `useResource` checks provenance, kind, scope and state, acquires a lease for the native operation, and releases it in `finally`. `launchOwned` retains captured resources before participants run; `withScope` waits for owners/callbacks and closes its resources before returning. A close refuses new owners but permits finishing work by an existing owner, then waits for remaining leases. Root shutdown drains owners and callbacks before reverse resource cleanup. Missing explicit close is itself a cleanup failure even when automatic close succeeds ([implementation](../../../runtime/owner.ts), [ownership account](../../implementation/ownership.md)).

The current useful idiom is to keep a transaction handle inside its `with_transaction<T>` callback and return durable data, not the handle. SQL transactions use one native `begin` callback, a scoped `sql-tx` resource, owner drain before the commit decision, private rollback sentinel, and `commit_unknown` when the native layer rejects after a commit decision ([transaction runtime](../../../runtime/platform/sql/transaction.ts)). The checker requires a concrete data `T` and an exact callback contract, but does not reject a `T` record/array/callable carrying the callback's transaction token ([specializer](../../../compiler/internal/check/transaction.go)). After scope exit, `resource_state` rejects that token before native work. A resource owned by an *enclosing* scope can still be returned and used while its owner remains live; a type-only ban on resource-bearing results would reject valid cases. The earlier [G5 probe](../evidence/2026-09-22/implementation-gaps/resource-lifetime.test.ts) was rerun at this HEAD: direct, record, array and callable escapes each failed on later use with `resource_state`, with native use count unchanged; all four tests passed. This proves runtime guarding for those shapes, not a complete static analysis of all aliases.

For an invoice or webhook transaction, keep authorization tied to the protected operation and request context. An opaque tenant value or transaction handle does not alone prove a current actor may edit a particular invoice. A callback/handle that outlives a request must remain subject to its actual owner scope. Coordinate any validation/capability experiment with DI-02 and DI-09c without presuming a new authorization syntax.

### Stream terminal paths and failure precedence

The [stream `pump` example](../../../examples/stream/src/main.can) says every terminal arm explicitly closes its reader. Its read-error arms (`read_failed`, `cancelled`, `limit_exceeded`) merely relay; only the empty-batch/EOF branch calls `close_reader`. The runtime read path marks a failed reader as errored; [stream lifecycle](../../../runtime/transport/stream/lifecycle.ts) permits close after a read failure and releases the native reader lock. Owner fallback cleanup closes an omitted handle but marks a cleanup failure. Thus the example's promise is inconsistent, while ownership still prevents an unguarded leak.

Current scoped failure precedence is narrower than an all-purpose language-level `finally`: `withScope` returns cleanup failure in place of a successful body result, but preserves an existing non-`ok` body completion while separately recording cleanup failure. `runOwnedRoot` likewise returns its body's completion plus `cleanupFailed` ([owner implementation](../../../runtime/owner.ts)). Explicit `close_reader` can itself return `close_failed`; a real read failure followed by close failure needs a chosen reporting contract before example repair. The current useful idiom is explicit close/cancel on every intended terminal route, with a separately stated policy for which failure remains primary. Do not infer that recursion or forwarded error arms perform that close.

The focused [stream tests](../../../runtime/test/streams.test.ts) verify native read failure, successful subsequent close, cancel during a pending read with no partial result, use-after-close and foreign-handle rejection. They do not execute the example's read-error path against a resource-close observation. Inject read, decode/limit, close, cleanup and cancellation failures through a whole generated Can flow before selecting syntax or precedence changes.

### Races, fault observation and drain

The emitter/runtime delegates four coordination selections to native `Promise.all`, `allSettled`, `any` and `race` with completion/ownership adapters ([runtime](../../../runtime/coordination.ts), [contract](../coordination-spec.md)). For first-success `race` (`Promise.any`), failures before a later winner are consumed; late standard failures from unselected participants are emitted as diagnostics. `race with error` (`Promise.race`) selects the first completion, including a failure. An empty dynamic spread into `Promise.race` stays pending; empty `Promise.any` reaches the all-failed result. The source rejects a syntactically empty block, but a nonempty spread entry may expand to zero participants. The best present service idiom is to guard dynamic races when a nonempty candidate set is required, and to treat fallback success plus hidden pre-winner failure as a deliberate observability choice. No implicit loser cancellation or altered native selection is selected ([LD19, LD24](../../implementation/language-design-dispositions-2026-09-22.md)).

`launchOwned` keeps losers and their captured-resource leases until their work settles. Root drain cannot return cleanly while a loser, callback or native subwork remains live. A close deadline races only the caller's wait, marks/report cleanup failure, and does not cancel the underlying native operation or release its lease. Registered shutdown deadlines likewise do not force an owner to settle. A permanently pending owner can retain the root indefinitely; external supervisor termination is a separate host action and proves neither cleanup nor rollback ([owner implementation](../../../runtime/owner.ts), [Q10 contract](../coordination-spec.md)). This is a boundedness/deployment gap, not a demonstrated ownership bypass.

The current [coordination tests](../../../runtime/test/coordination.test.ts) exercise native delegation, consumed pre-winner versus late standard diagnostics, pending empty race under a harness deadline, and a losing participant's retained lease followed by native use before close. [Hung-owner tests](../../../runtime/test/owner-hung.test.ts) exercise external termination. To justify an opt-in fault-observation policy (DI-15c/18b), use a replica/fallback service with intentional and accidental failures, state diagnostic timing/identity, and measure whether reporting consumed failures helps an agent diagnose faults without routine noise. This is one crosswalk question, not two separate features.

### Cancellation and service shutdown

The native boundary has operation-specific abort mechanisms. `runtime/transport/fetch.ts` passes a deadline `AbortSignal` to `fetch` and cancels response bodies; stream cancellation records a reason and may unblock a pending `ReadableStream` read; server stop has a configured deadline ([fetch](../../../runtime/transport/fetch.ts), [stream lifecycle](../../../runtime/transport/stream/lifecycle.ts), [server](../../../runtime/platform/server.ts)). The presence of those adapters does not establish general cancellation for SQL, arbitrary Can callbacks, process effects or a request after a remote commit. The [coordination contract](../coordination-spec.md) explicitly excludes automatic loser cancellation, transaction implicit deadlines and rollback of already observed effects. Qualify each operation's actual abort and aftermath in the service slice; a client disconnect is especially relevant to request-owned work and outbox effects.

## Distribution and Linux evidence

The only pinned target is `bun-1.4.2-darwin-arm64-v1` in [target.json](../../../distribution/target.json). The [distribution instructions](../../../distribution/README.md) and top-level README explicitly decline Linux support. This is more than a missing Linux manifest: `distribution/qualify.py` requires native Darwin arm64 and invokes macOS `sandbox-exec`; `distribution/build.go` builds the launcher with `GOOS=darwin`, `GOARCH=arm64`; `distribution/verify.go` requires the pinned OS/arch and checks a Mach-O executable. Existing release/install evidence applies to the Mac target, and the required-native-API inventory plus nine behavior probes alone do not prove HTTP, SQL, lifecycle or service behavior.

A Linux SaaS claim needs a named OS/architecture/libc/Bun target and provenance, verified archive and executable bytes, launcher/runtime packaging and installation, Linux-appropriate isolation and executable verification, native API/behavior qualification, then the invoice and webhook slices on that installed bundle. Exercise real database/provider protocols, slow dependencies, client disconnect, owned work, pending/empty races, close deadlines and supervisor grace/kill policy there. Record what exits cleanly, what merely reports timeout, and what can be abandoned by host termination. Do not label ordinary source-level Go/Bun tests on another OS as a qualified Linux distribution. The proposed Gate 4 is a deployment qualification condition, not a grammar request.
