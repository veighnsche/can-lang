# Representative observation boundaries for Can-authored tests

Status: source review and proposed mechanics only. No API, backend, test, build, browser run, or measurement was created or executed. These examples need ordinary Can functions and reusable Can helpers for action order, expected values, failure decisions, selection, and reporting. The native side may expose mechanics and raw facts; it must not contain a named case, expected answer, or a test-specific `page.evaluate` program supplied as a string.

## Browser: live value, attribute, and reset

The static [native-control scenario](../../../../tests/integration/browser/controls-native.mjs#L75) fills `#n-text` with `user edit`, changes its **attribute** to `normalized`, and expects the **live property** to remain `user edit` while `getAttribute("value")` returns `normalized`. The same script resets the form and checks live `value == "start"` and `checked == false` [at line 86](../../../../tests/integration/browser/controls-native.mjs#L86). The paired compiled Can program already has normal Can callbacks that call `browser::set_value`, `set_checked`, `set_selected`, and then `read_value`/`read_checked`/`read_selected` [in `on_reset_click`](../../../../tests/integration/testdata/browser-controls/src/main.can#L237). The host [controls scenario](../../../../tests/integration/browser/controls.mjs#L259) currently owns the dirty-reset actions and oracle. The Go matrix requires Chromium, WebKit, and Firefox and qualifies the static and compiled paths separately [native matrix](../../../../tests/integration/browser_controls_test.go#L102), [compiled matrix](../../../../tests/integration/browser_controls_test.go#L143).

For one representative Can case, choose a named browser and navigate to the static control page. Can then fills the field, sets the attribute, reads both live property and attribute, and compares the pair `("user edit", "normalized")`. A second phase reloads, dirties the field and checkbox, invokes reset, and compares live `("start", false)`. If using the compiled fixture instead, Can owns the fill/check/select/click sequence and compares the program's `v-reset` text with independently read live properties; a DOM attribute alone cannot stand in for the value property. Keep the static native fact and compiled production path as different evidence scopes.

Minimum proposed browser mechanics: named-engine launch/remote connection, navigation, fill/check/select/click, a **fixed generic** DOM property read, a separate attribute read and attribute write, and raw network/console/page-error events. A driver can implement `value`, `checked`, `selectedOptions`, and attribute access using fixed code. Can supplies selector, property identifier, value, timing, and expected result through ordinary calls; no arbitrary test callback or `evaluate` body crosses the boundary. Return a trace such as `{engine, step, selector, property, attribute, value, networkEvents, pageErrors, consoleErrors}` with missing nodes and driver failures represented explicitly. Can decides which values and failures pass. A deliberate mutant that returns the `value` attribute for a live-value read must fail the Can case. Browser availability remains a required capability/skip distinction, not an automatic pass; the existing `CAN_FIREFOX_WS` path is documented in the Go matrix header.

## Native: exact JSON lexemes and signed zero

The current [native qualification probe](../../../../tests/conformance/native.ts#L36) parses `{"large":9007199254740993,"zero":-0}` with `JSON.parse` source context, expects raw member tokens `9007199254740993` and `-0`, checks `Object.is(value.zero, -0)`, and uses `JSON.rawJSON` to emit the large integer unchanged. The separate [codec runtime test](../../../../runtime/test/codec-json.test.ts#L25) expects an exact bigint, negative zero, and canonical encoded bytes for a nested record. A compiled Can source already exercises ordinary `codec::encode_json`/`decode_json` calls and exact large-int results [in `roundtrip.can`](../../../../compiler/testdata/current/codec/roundtrip.can#L1). These are distinct observations: a Can codec roundtrip alone could share a defect with its own encoder, while the native probe independently establishes Bun's source-lexeme and numeric facts.

A Can-authored scenario chooses the JSON bytes, asks a generic host probe to return per-path `JSON.parse` source lexemes and a raw signed-zero observation (for example IEEE-754 bits or the result of `Object.is(number, -0)` as an observed boolean), and compares them in Can. It separately compiles and runs a normal Can function using `codec::decode_json` and `codec::encode_json`, then compares the output bytes and numeric result to Can-held expectations. The host probe takes the input bytes and paths; it must not embed the example JSON, expected token array, or a pass/fail assertion. Report `{inputDigest, tokenByPath, numericBitsOrSign, nativeError}` as data, including syntax failures. A mutant that normalizes `-0` to `0` or rounds the large token must fail the Can oracle. Preserve the native `JSON.rawJSON` emission check as its own raw observation if this qualification scope is selected; ordinary Can serialization is not a substitute for Bun API qualification.

This requires a proposed `NATIVE` probe surface for values Can cannot faithfully construct or inspect, plus ordinary Can `CAN`/`PROC`/`FILES` behavior already demonstrated by the compiler fixture. The exact probe API and execution backend remain open. Generic probing should avoid getter invocation or thenable assimilation in related hostile-value cases; see the [array runtime source](../../../../runtime/test/array.test.ts#L737), where the current host oracle counts getter calls and compares object identity.

## Managed child: readiness, SIGTERM, and in-flight drain

The [gate-3 child helper](../../../../tests/integration/gate3_matrix_test.go#L330) starts a staged production entry with a descriptor-3 environment snapshot, isolated cwd/env, waits for `/health` status 200, and exposes SIGKILL and SIGTERM plus bounded `Wait` behavior. The [lifecycle case](../../../../tests/integration/gate3_matrix_test.go#L1795) first rejects startup on an occupied port; then it saves, SIGTERMs, restarts and checks byte-identical replay and a new save [at line 1830](../../../../tests/integration/gate3_matrix_test.go#L1830). It next SIGTERMs while a trickled request body is in flight, accepts either initial completion or abort, retries the identical operation, and requires one durable effect using an independent database inspector [at line 1865](../../../../tests/integration/gate3_matrix_test.go#L1865). The one-shot current Can `process::run` example only returns after child exit [in `examples/process`](../../../../examples/process/src/main.can#L22); it does not by itself expose a running process handle.

For a bounded representative Can case, a normal Can helper owns the sequence: stage/compile candidate, allocate a child lease and descriptor-3 snapshot, start the server, poll `/health` to a Can-chosen deadline, send one request, signal SIGTERM, await exit, restart, replay, and compare response bytes and independent database rows. For the in-flight variant, Can starts a generic trickled-body sender, waits for a *body-progress observation*, then signals SIGTERM; it accepts the source's two permitted first outcomes while requiring a clean child exit and exactly one final effect after retry. A fixed sleep is a weaker synchronization witness than body progress. Can decides readiness policy, order, accepted outcomes, retry, and DB expectation. The supervisor only returns facts and enforces hard bounds.

Minimum proposed `CHILD`/`WORK`/`CLOCK`/`WIRE` mechanics: owned spawn with cwd/env/fd-3 input; a process handle supporting signal, bounded wait, kill escalation and process-tree cleanup; a monotonic deadline; HTTP status/body observations; gated or progress-reporting trickle sends; independent DB row inspection. A possible raw trace is `{spawnPid, readyPolls:[statusOrError,elapsed], bodyProgress:[bytesSent,elapsed], signalSent, wait:{exitCode,signal,timedOut}, firstRequest:{statusOrTransportError,body}, replay:{status,body}, dbEffects:[operationId,...], cleanup:{childrenRemaining,errors}}`. Native enforcement may kill/reap on deadline or controller loss, but cannot declare the scenario passed. Can failure reporting must distinguish readiness timeout, unexpected process exit, request ambiguity, DB mismatch, and cleanup failure. Owned resources must be registered before allocation and reclaimed after success, failure, interruption, and abandoned-controller recovery. No broad lifecycle run is implied by writing this design note.

For the five-example authoring package, these three cases show where a report should bind the Can case ID, runner/candidate identities, selected engine or host capability, action/observation trace, Can comparison result, and cleanup result. A missing browser, absent raw probe, or failed child cleanup leaves the required profile incomplete; it cannot produce a complete pass.
