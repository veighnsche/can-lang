# Native observation and compiler diagnostic contracts

Status: **design proposal from source review; no API or CLI implementation, build, test, or measurement**. This narrows the [execution architecture](../../native-can-test-architecture-2026-09-30.md) and [authoring examples](../../native-can-test-authoring-2026-09-30.md). Can owns scenario order, expected values, comparison and verdicts. A native service supplies bounded actions and facts from an isolated subject. Names and wire shapes below are proposed contracts, not present packages.

## Source boundaries

The existing [native qualification file](../../../../tests/conformance/native.ts) embeds both operations and answers in `probes`: it verifies JSON source lexemes and negative zero, `JSON.rawJSON`, sequential `Array.fromAsync`, nonassimilation of a boxed thenable, strict `Bun.deepEquals`, immutable arrays and native Set order. Its `qualify` function also chooses probes and decides `passed`. That policy must move to Can. [CORE-001](../native-can-tests-migration-ledger-2026-09-30/core.md), CORE-010 and CORE-012 retain getter/thenable hostility, identity, order, callback timing and late failures beyond the short JSON example. [HISTORY-007](../native-can-tests-migration-ledger-2026-09-30/sql-history.md) and HISTORY-008 require raw database facts independent of the Can SQL adapter. CORE-011 and CORE-047 require external HTTP/WebSocket facts and owned shutdown. A codec round trip, generated program response or adapter's own report cannot certify its independent native counterpart.

`driver.CheckSnapshot` currently returns `Snapshot.Diagnostics` with code, severity, message, canonical file, zero-based UTF-16 positions and related locations. It checks without running assertions or emitting. It has **no public `canlc check --json` command**, explicit diagnostic phase, completed-analysis flag or input digest report. `errorIssues` currently turns many project-load failures into a `CAN-PROJECT` diagnostic, so a new CLI cannot classify every returned diagnostic as a candidate source rejection. The [authoring example](../../native-can-test-authoring-2026-09-30.md) already proposes statuses 0/1/2; the details below specify the missing classification boundary.

## Generic native fact and fault surface

Open a disposable observation session with an **explicit candidate runtime identity** (executable, runtime/catalogue/bindings and options digests) and a case-owned scope. The reference-built Can worker calls typed operations through the trusted resource service; the candidate runtime and any candidate-generated code run in a different OS process. Only opaque session-local handles and bounded tagged facts cross back. A handle cannot be serialized into another worker, used after close or interpreted as a Can object. Record the observer implementation identity separately from the runtime observed. Missing required operation/capability is an explicit fact or execution failure, never a silent switch to the reference Bun.

The surface needs a small, reviewed **operation vocabulary**, not a JavaScript source string, arbitrary `eval`, or a `qualify_json`/`test_array` macro. Can can compose calls in any order:

| Family | Caller-controlled input | Returned fact or handle |
| --- | --- | --- |
| Value construction | Primitive with tagged IEEE-754 bits or exact text, array/record entries, JSON bytes, accessor/thenable/proxy descriptors | Session handle and construction error. Descriptors select reviewed trap behavior, throw point, gate and counters; they contain no executable callback text. |
| Native action | Named reviewed operation and typed arguments, such as `JSON.parse` with source capture, `JSON.rawJSON`/`JSON.stringify`, `Array.fromAsync`, `Object.is`, `Bun.deepEquals`, Set operation, `Reflect.get`, or a production-adapter invocation through an explicitly identified subject | Result handle, native exception kind, promise settlement and bounded event sequence. One action per call; no built-in expected result or prescribed action sequence. |
| Observation | Handle/path/property and requested representation | Exact JSON source token string, serialized bytes, number bits/sign, primitive tag, own-property descriptor, ordered collection entries, identity relation between two live handles, or counter/event snapshot. Unknown or unavailable facts are tagged, not coerced to false/zero. |
| Synchronization | Gate ID, release or bounded wait request | Call-start/finish, getter/proxy/then invocation and settlement events with monotonic sequence numbers. Can chooses when to release gates and what order matters. |
| Scoped fault | Fresh-session capability/property selector from a reviewed allowlist and a named fault mode such as absent/throw/revoked | Installed fault ID and observed effects; the service restores or destroys the isolated session on close/death. It never patches the controller, another case or a shared runtime. |

An identity relation is computed inside the session with strict reference identity and returned as a boolean plus the two handle IDs; copying both values into JSON would erase the property under test. Signed zero crosses the report boundary as tagged bits or a native `Object.is(value, -0)` observation, and large JSON integers/source tokens cross as exact strings. The probe records `JSON.parse` reviver source by unambiguous path (including array indexes and escaped property names) and reports absent source contexts explicitly. It never converts a source token through an ordinary JSON number before Can compares it. `JSON.rawJSON` construction and resulting serialization are separate actions, so Can can check each result and a missing API independently.

Getter/proxy/thenable descriptors must expose exact invocation counts, order, thrown value kind and settlement. A caller can make a getter return a handle, throw, or wait at a gate; a thenable can count `then` reads/calls and resolve or reject under Can-selected control; a proxy can select reviewed traps and revocation. These are mechanics for host values Can cannot faithfully construct. They do not carry an expected count. Counter snapshots before and after each candidate action prove when an extra read or assimilation occurred. Hold input/output handles until Can has observed identity and counts; release all on scope teardown. Bounded event transport must preserve order and state truncation, since a truncated trace cannot prove an absence of calls.

Native qualification and production behavior are separate evidence scopes. A raw `Array.fromAsync` probe establishes a candidate Bun fact; an invocation of the candidate Can array adapter exercises production behavior. Both can be compared by Can against Can-held expectations, but agreement between them alone is not an oracle. The reference judge never imports candidate modules. Faults such as masking `JSON.rawJSON` are installed only in fresh candidate probe processes and must be visible as failed capability observations, including when the case's Can expectation changes.

## Independent SQL and wire observations

For SQL, expose a scoped **raw driver** connection/transaction with typed parameter values, parameterized statement bytes, query/execute, commit/rollback and ordered row/error facts. Return database engine/version, SQLSTATE or native error code, affected count, nullable values, exact int64/decimal/byte encodings and transaction phase. The Can case chooses statements, concurrency, locking mode and accepted outcomes. The raw observer must use a separate connection path from the candidate Can SQL adapter and a separately identified driver; it cannot call the adapter and describe its output as independent. Compare committed effects through a fresh raw read after candidate operations, including rollback, ambiguous write and `RETURNING` ownership cases. Record fixture/database identity and transaction cleanup; never embed a fixed F02/F03 sequence in the driver. Credentials use scoped authority and must not enter report values.

For HTTP and WebSocket, a generic external client returns request/response bytes, status, headers (including repeated `Set-Cookie`), transport errors, frame opcode/payload, close code/reason and ordered connection events. A pending request or socket has an owned handle and bounded wait; request-body progress and peer-arrival events let Can synchronize signal and drain tests without a fixed sleep. The Can case chooses boot, request, signal, retry and expected ordering. Observation must be outside the candidate server's own callback path. A native peer may gate or trickle bytes and report progress, but cannot decide that shutdown, retry or one durable DB effect passed. Resource owner receipts cover sockets, connections, processes and database fixtures after worker death.

## General `canlc check --json` product contract

Propose `canlc check --json PROJECT_DIRECTORY` as a normal compiler command over immutable, explicitly identified project input. It uses the `CheckSnapshot` load/resolve/check path, without assertions, execution, emission or publication. The report is one bounded versioned JSON object on stdout for every **completed** analysis; stderr is reserved for invocation/infrastructure detail and is not parsed as a diagnostic oracle. It identifies compiler artifact/runtime-independent checker version, project root identity, options and a sorted inventory of project-relative input paths with byte length and SHA-256 of bytes actually analyzed (including manifest/dependencies). Validate the input lease before and after analysis; mutation or inability to prove identity is infrastructure failure. No absolute private path, credential or unbounded source text appears in the report.

The proposed top-level fields are `schemaVersion`, `kind`, `status: "completed"`, `result: "accepted" | "rejected"`, `compiler`, `inputs`, and `diagnostics`. Exit **0** means completed accepted analysis; **1** means completed rejected analysis; **2** means invocation, internal, input-identity or infrastructure failure. A failed status-2 invocation may emit a separate bounded error envelope with `status: "failed"`, stable failure kind and no `result`; it must never emit a completed rejection report. Signal, timeout, missing/truncated/malformed output or status/report disagreement is an execution failure in the Can wrapper. Warnings/notes can coexist with `accepted`; rejection requires at least one source error diagnostic and a complete analysis. An empty diagnostic list cannot imply acceptance if graph loading, resolution or checking did not finish.

Each diagnostic has explicit `phase` (`project`, `lex`, `parse`, `resolve`, `check`), `severity`, `code`, `message`, `primary` and `related`. Phase is attached at the producing stage; inferring it from code spelling or prose is unsound. Source locations carry project-relative path and zero-based UTF-16 start/end line/column; primary/related location is explicitly null when genuinely spanless or unavailable, with a reason. Optional byte offsets must be named byte offsets, bounded to the digested input and tested with astral Unicode. Do not serialize a spanless diagnostic as a fabricated line-zero squiggle. Preserve diagnostic order and separate related locations. Compiler-proposed fixes are not part of the minimal checking oracle and should not silently become applied edits.

Classification needs an explicit boundary in addition to `CheckSnapshot`: malformed candidate source or manifest content, including a deliberate missing declaration, is a **completed rejection** when the analyzed input set is known and the compiler can attribute a diagnostic. Missing project path, unreadable input, stale/mutating dependency, unsupported invocation, canceled analysis, internal panic, resource exhaustion or malformed report is **status 2**. A load error currently mapped to `CAN-PROJECT` is therefore not sufficient evidence of which class occurred. The CLI must check the load outcome and input provenance before emitting `result`. A parse-only rejection with the wrong phase/code remains a failed Can expectation; the valid control must also be accepted. Can's matching helper owns expected code, phase, severity, count and primary-span overlap with the changed bytes. It may require zero unrelated errors, while explicitly listed warnings/notes remain allowed.

Acceptance for this contract is a source-backed implementation review and bounded tests proving accepted controls, lex/parse/resolve/check rejections, wrong-phase negative controls, Unicode spans, related/spanless locations, warnings-only acceptance, missing/unreadable/mutated input as status 2, compiler/input identity agreement, no assertion execution or publication, and status/report mismatch rejection by the Can helper. This document records those obligations; it does not claim the command or native probe exists.
