# Capability-contract review observations

Status: read-only design review of [the shared contract](../../native-can-test-capabilities-2026-09-30.md) against the chosen architecture and cited source. No implementation, test, build or measurement was run. These are wording and implementation-gate corrections; the contract does not need to solve host containment in this documentation step.

1. **Recoverable operation IDs need an explicit crash outcome.** Section 2 says repeating an identical ID joins or returns the operation and claims at-most-once dispatch within a recoverable scope. A service can die after dispatch but before retaining the terminal fact. On restart, the same ID cannot safely be sent again merely because no reply exists. State that the pre-dispatch record and operation identity must survive service death, and an unresolved dispatched mutation returns `indeterminate` until subject-specific reconciliation establishes its result. A new ID for the same write is a new operation, so Can must decide whether to retry using observed effects. This is an implementation gate, especially for `db.commit`, `proc.spawn`, `browser.route_fetch` and `browser.route_resolve`; it is not a claim that exactly-once external effects are attainable. The current paragraph already says not to replay after lost acknowledgment, so this makes its failure behavior explicit.

2. **Subject-realm Can callbacks must remain observations.** Section 6 permits ordinary Can functions compiled into a probe artifact to serve synchronous callbacks locally. Clarify that the artifact is built and identified by R for a specific subject session, while its execution under C's runtime is untrusted subject behavior. It cannot gain the controller's private evidence/reporting channel or make a test verdict; raw callback events, values, throws and counts return to the reference worker for Can comparison. This preserves the architecture's rule that C never compiles or replaces the judge. It also distinguishes a callback's local synchronous result from a controller RPC: a getter/Proxy trap cannot block for a Can decision or return a Promise as if it were a synchronous value. The document already notes that candidate callback reports are not automatically independent facts; the role/provenance rule completes that boundary.

3. **`native.describe` should avoid hidden getter execution.** Section 6 says `native.describe` returns presence/type/availability “without invocation,” while the same section supports counted/throwing accessor and Proxy faults. Inspecting an accessor-backed API can establish that a descriptor exists, but reading its current value or callable type can invoke a getter or trap. Define `describe` as descriptor/presence inspection with a tagged unknown value type when inspection cannot be effect-free; use an explicit counted get/invoke action to establish callable availability. Otherwise a supposedly passive capability check could consume the very getter/thenable call count that a Can case intends to test.

4. **Name the completion boundary for operations with a partial response.** Section 2's `completed(facts)` is defined by each operation's documented condition, but `browser.route_fetch` says it returns upstream status/headers/body while section 5 acknowledges that body capture completes later. Likewise `http.read_headers`, stream reads and `native.invoke` may yield a pending action. Keep completion scoped to the named action: `route_fetch` can complete with a response handle after contact, with body completeness proved by a separate capture/EOF result; or it can require full bounded body capture before `completed`. The chosen rule should be explicit in the eventual wire contract. A known status plus missing/truncated body cannot masquerade as a complete response. This is an exact protocol-schema gate, not a demand for a new API family.

5. **Early compiler rejection needs a precise input-inventory scope.** Section 8 allows parse failure to stop later stages, while `inputs` promises sorted project/dependency byte identities and `completeness` promises a legitimate early stop. Specify whether `inputs` means only bytes actually read, with a separately identified declared/leased closure, or the full fixed input closure captured before analysis. Mark an early-stop phase and any unvisited units explicitly. Otherwise a correct parse rejection could present a partial read set as a fully checked project identity. Keep exit 1 for attributable source rejection and exit 2 for missing/unreadable/changing inputs or incomplete analysis; `CheckSnapshot`'s current `CAN-PROJECT` mapping cannot make that distinction on its own.

No further material contradiction found. The separation of Can policy from native mechanics, status-2 infrastructure failures, UTF-16 span contract, and the stated host-enforcement qualification gates are consistent with the cited architecture and source review.
