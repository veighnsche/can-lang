# Resource-contract review

Status: read-only review of the [main capability contract](../../native-can-test-capabilities-2026-09-30.md). No code, suite, build or host-enforcement probe was run. The existing source review remains [workspace/process](workspace-process-review.md).

1. **Do not release ownership on an unresolved `proc.close`.** The `proc.close` row says it will "release leases/quota and return cleanup receipt" ([main contract](../../native-can-test-capabilities-2026-09-30.md#4-managed-processes)). That must be conditional on confirmed stream/descriptor closure, leader reap and the claimed descendant containment result. On deadline, unknown descendant or failed cleanup, keep the external ownership/recovery record and charge the unresolved resource against the scope; return the partial close receipt. Otherwise an escaped child can outlive its lease and a later case can be admitted against falsely freed capacity. The same rule applies to `work.dispose`: only released entries disappear from accounting; remaining paths and shared read leases retain ownership. This is a contract correction, separate from the still-pending host containment mechanism.

2. **State the strength and completeness of a workspace revision.** `work.read` promises a distinction for a "changing file" and `work.list` says mutation invalidates pagination, while the seal section correctly admits that an external candidate can mutate and restore bytes without detection ([workspace rows](../../native-can-test-capabilities-2026-09-30.md#3-owned-temporary-workspaces)). A service-local revision detects *capability-mediated* writes, not every out-of-band write. Define `stable_snapshot` only when a qualified immutable snapshot/open-handle mechanism supplies it; otherwise return observed bytes/page plus `stability=unknown` or `changed_observed`, and do not claim complete pagination on an external mutable tree. This prevents a race from turning a mixed directory page or read into an exact fixture observation.

3. **Make the seal cover the project input closure used by the compiler.** `work.seal` currently accepts "selected input paths/revision" and returns a sorted manifest. A compiler project can be affected by a new sibling file, manifest/dependency change or symlink target even when every named file hash is unchanged. Either define a complete input-tree seal including directories, file names/kinds, link metadata and relevant absence expectations, or label the seal partial and prohibit using it as the identity of a full candidate project. This is particularly relevant to the [compiler rejection composition](../../native-can-test-capabilities-2026-09-30.md#9-compositions-and-coverage-gates), where the valid and invalid controls must differ by exactly the Can-selected mutation.

4. **Specify how an invalid revision is created after sealing.** The contract says further input mutation requires a new revision, but provides no `fork`/new-revision transition and the compiler example says "materialize/seal valid input → ... → make exactly one invalid revision" ([workspace](../../native-can-test-capabilities-2026-09-30.md#3-owned-temporary-workspaces), [composition](../../native-can-test-capabilities-2026-09-30.md#9-compositions-and-coverage-gates)). Choose an explicit new reservation/materialization from the sealed manifest, or a `work.revise` operation with copy-on-write/partial-state rules; keep the original sealed control immutable. Do not let `work.write` silently reopen sealed paths.

The document already marks pre-exec registration, detached-descendant containment, strict disk limits and filesystem confinement as pending host qualification. I found no reason to claim those mechanisms exist or to change the chosen Can-policy/native-facts boundary.
