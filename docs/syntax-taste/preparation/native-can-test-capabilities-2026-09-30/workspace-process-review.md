# Shared workspace and managed-process capability review

Status: **proposed contracts from source review; no implementation or execution evidence**. These are logical operations for ordinary Can helpers, not declarations that already compile. The [chosen architecture](../../native-can-test-architecture-2026-09-30.md) puts Can case policy in a reference-built controller and isolated workers, with a generic native supervisor retaining resource ownership outside a killable worker. The [migration ledger](../../native-can-tests-migration-ledger-2026-09-30.md#shared-requirements-exposed-by-the-mapping) groups `WORK`, `FILES`, `PROC` and `CHILD` across compiler, service and lifecycle cases. This review defines reusable mechanics for those groups, without embedding any old case sequence or oracle in a host service.

## Boundary and shared envelope

Can selects source fixtures, exact edits, child commands, readiness probes, signals, retry decisions, expected bytes and verdicts. Native mechanics return facts and enforce an upper envelope even if Can stops yielding. Every operation takes an opaque `run_scope` and `case_scope` granted by the supervisor; a handle is scoped to one run/case and carries a generation to reject stale or forged use. Raw absolute paths and PIDs may be reported for diagnosis but are never sufficient authority for destructive operations. The controller passes descriptors/identities, not its in-memory handles, to workers. The outside-worker service owns workspace and child records until it emits a final cleanup receipt.

Every request has a schema version, run/case/attempt identity, operation ID, idempotency key where replay matters, monotonic deadline bounded by the case/run envelope, and bounded input size. Every reply has request identity, operation state (`completed`, `rejected`, `timed_out`, `interrupted` or `indeterminate`), monotonic observation time, raw facts or a typed mechanical failure, and any cleanup consequences. `indeterminate` means an effect may have occurred; Can must not silently retry a write/spawn/signal as if nothing happened. The service preserves the first operation outcome and records cleanup failure separately. Case policy can map an *expected subject* timeout to passing behavior, but a timed-out judge or unknown owner cleanup cannot be a complete pass ([architecture](../../native-can-test-architecture-2026-09-30.md#evidence-transport-failure-and-resource-boundary)).

An ownership intent must be durable **before** a path or child is exposed. Operations serialize per handle. A duplicate idempotency key returns the original receipt when one was committed; if a crash left an effect without a committed receipt, it returns `indeterminate` and requires reconciliation rather than repeating the effect. State and receipt updates must be crash recoverable, with a bound on journal bytes. The exact durable journal, launch gate and host containment mechanism are unresolved implementation decisions; merely recording a PID after `spawn` does not close the crash window.

Mechanical failures use stable categories: invalid scope/handle/generation, unsupported capability, invalid path/argument/environment/descriptor, missing or changed source/artifact, kind/collision/permission failure, budget exceeded, deadline, transport I/O failure, and unresolved cleanup. A rejected validation request has no effect. Every failure after acquisition carries the current handle state and any partial byte/path/process facts, so Can can report the original cause alongside cleanup and decide whether a deliberate subject failure matches its expected oracle.

## Owned workspace

The workspace is one private run/case allocation with a fixed byte, entry and depth budget, rather than a copied repository or persistent build cache. It exposes logical relative paths rooted in an opaque workspace handle. Separate named areas are useful: `input` for authored fixture/project data, `scratch` for Can-selected mutations, `output` for candidate builds and compact `evidence` for bounded receipts. Native code creates and validates paths; Can chooses their contents and differences. A handle may be shared with a child only through an explicit scoped `cwd`/mount descriptor. It must not give that child deletion authority over another case or the shared installation.

| Logical operation | Inputs | Raw result and state effect |
| --- | --- | --- |
| `reserve` | Scope, purpose, declared budgets/expiry, optional requested fixture identity | Atomically claim unpredictable directory identity under an owned root and register the reservation before visibility; return handle, path for child invocation, lease generation and remaining budget. `reserved` contains no trusted fixture contents. |
| `materialize` | Handle, allowlisted source fixture identity plus relative file list/digests or Can-supplied byte entries, destination area, overwrite policy | Copy only selected bytes, count bytes/entries before retaining, verify source and final digests, return per-entry facts and new revision. Partial failure leaves the workspace owned and reports which entries became visible; it does not erase partial data behind a generic failure. No executable fixture callback runs. |
| `read` | Handle, normalized relative path, maximum bytes, expected revision if needed | Return raw bytes, actual count, kind, content digest and revision; distinguish absent, symlink/escape, kind mismatch, limit and I/O failure. Reading a changing file can return `changed_during_read`, not falsely stable bytes. |
| `write` | Handle, normalized relative path, bytes, create/replace/compare-revision mode, maximum bytes | Atomically publish one selected file where supported, return prior/new revision, byte count and digest. A partial or uncertain write is explicit; no silent overwrite, traversal or cross-case path. Multi-file edits are a Can-directed sequence with a partial-state receipt unless a separately specified transaction is added. |
| `seal` | Handle, selected input paths/revision and optional expected manifest digest | Return a manifest of exact relative names, kinds, sizes and hashes plus seal ID. Further *capability API* writes to sealed inputs reject. `scratch` and `output` can remain writable for a build. This is a logical input seal, not proof that an unsandboxed candidate cannot mutate or restore source bytes; revalidate before/after use and mark stronger isolation as pending. |
| `dispose` | Handle, expected lease generation, bounded cleanup deadline | Refuse new work; stop or refuse while owned children still use it according to explicit close policy; remove only identity-verified owned entries; return `disposed` or a receipt listing remaining paths and errors. Idempotent repeats may finish an interrupted disposal. |
| `recover` | Supervisor-owned run record and inactivity proof; never an arbitrary user path | Enumerate pending reservations and exact path identities, reconcile live leases/children, then finish cleanup only for inactive owned entries. Return recovered, still-active, foreign/mismatched or unresolved identities. Uncertain liveness blocks deletion. |

State transition: `intent → reserved → materializing ↔ ready → sealed-inputs → in-use → disposing → disposed`. An operation failure may leave `reserved`, `ready` or `disposing` with a recorded partial result; it never makes an allocated path ownerless. `recover` is a supervisor operation over inactive records, not a Can case shortcut for deleting arbitrary directories. `seal` does not require all workspace areas to become immutable; build output must remain writable. A new mutation of sealed inputs requires an explicit fresh revision/workspace, keeping old input identity for a running candidate.

Path handling must be rooted at an opened owned directory, reject `..`, absolute and symlink traversal for mutations, and verify the final object identity before removal. A text path check followed by ordinary `rm -rf` is race-prone. Imported symlinks/hardlinks need an explicit reject or safe-copy rule; writable hardlinks to shared source are unacceptable. Relative paths and source digests are useful evidence but do not by themselves confine an external candidate process. The existing `files` operations accept ordinary paths and provide byte-limited reads and create/replace writes ([read](../../../../runtime/platform/files/read.ts#L65), [write](../../../../runtime/platform/files/write.ts#L124), [directory](../../../../runtime/platform/files/directory.ts#L147)); they do not establish this handle-scoped ownership or storage quota. Current Go `stageProject` copies a fixture tree into `t.TempDir` and skips `dist` ([source](../../../../tests/integration/stdlib_test.go#L96)); the native replacement should select only required inputs and avoid persistent duplicate trees. The compiler output store already shows identity checks, an owned `dist` tree, lock and generation leases ([source](../../../../compiler/internal/driver/output.go#L37)); these are reusable ideas, not a general case workspace service.

## Long-lived managed process

`process::run` currently takes an executable, args and `process::options` with cwd, inherited/extra environment, complete stdin bytes, stdout/stderr limits, deadline and grace; it returns binary buffers and exit code/signal after completion. Its implementation uses `Bun.spawn` with pipes and a detached group, drains streams before retaining beyond a cap, closes stdin immediately after the supplied bytes, and registers cleanup in the process owner's runtime scope ([spawn](../../../../runtime/platform/process/spawn.ts#L43), [I/O](../../../../runtime/platform/process/io.ts#L25), [group termination](../../../../runtime/platform/process/wait.ts#L1)). That is valuable one-shot behavior, but no running handle, incremental stdin, event cursor, outside-worker owner or proven detached-descendant containment. The proposed managed child should reuse Bun/native spawn and binary stream mechanics through reviewed bindings, rather than reimplement process behavior in Can.

| Logical operation | Inputs | Raw result and state effect |
| --- | --- | --- |
| `spawn` | Scoped executable artifact/identity, literal argv, owned cwd handle/subpath, explicit environment snapshot, optional descriptor-3 bytes/lease, allowed inherited descriptors, stdin mode, stdout/stderr/event budgets, wall deadline, termination grace and containment requirement | Validate inputs and acquire process quota; register a launch intent and containment *before* exec is released; return opaque child handle, generation, observed PID/start identity and spawn timestamp, or a classified spawn failure. The service retains owner authority before the handle reaches Can. |
| `write_stdin` | Handle, byte chunk, idempotency key, deadline | Return bytes accepted into the pipe and possible partial/unknown delivery; never claim the child consumed them. Preserve binary bytes including NUL. Reject after EOF/close; enforce cumulative input cap and bounded backpressure. |
| `close_stdin` | Handle, deadline | Deliver EOF once and return completion/error; idempotent repeat reports the existing close result. Do not close descriptor 3 by confusing it with stdin. |
| `read_events` | Handle, cursor, max events/bytes, wait deadline | Return ordered, bounded raw events (`stdout_bytes`, `stderr_bytes`, stream EOF/read error, process exit, limit/deadline/forced-action facts), next cursor, dropped/truncated count and digest where applicable. Sequence order is per observed stream/channel; do not promise a causal total order between independent stdout and stderr. A reader may poll or await without consuming evidence for another reader. |
| `signal` | Handle, allowed signal enum such as `SIGTERM`/`SIGKILL`, deadline | Return delivery attempt, OS result, observed process identity and time. `sent` does not prove application receipt or shutdown progress. Exit racing the signal is represented distinctly; never signal a recycled PID. |
| `wait` | Handle, monotonic deadline | Return `exited` with raw code/signal/time, `pending` at deadline, or wait error. Exit is distinct from stdout/stderr EOF and descendant cleanup. A Can-chosen short wait does not disable the outer hard deadline. |
| `terminate` | Handle, TERM grace/KILL escalation within supervisor maximum | Return exact actions, observed exit/reap status, remaining descendant/stream/descriptor state and errors. Idempotent; an unconfirmed reap or escaped descendant is unresolved, not clean termination. Can may choose a deliberate SIGKILL crash scenario, while N still enforces its upper bound. |
| `close` | Handle, deadline | Stop admitting writes/signals, close stdin/streams, terminate if still running under the declared policy, reap and release quota/lease; return complete or cleanup-failed receipt. Repeated calls join the same close. The outside-worker service performs this after worker death. |

State transition: `intent → starting → running → exit-observed → streams-drained → closed`. `terminating` is an overlay entered by Can or N; an exit can race every operation. A failed spawn resolves its intent without issuing a handle. Handles bind to process start identity, not PID alone. `wait` may observe an exit while a pipe is still open in a descendant; `close` is complete only after stream/descriptor and owned-descendant accounting. A subject exit status is raw data; `process::require_success` is current Can-accessible policy for the one-shot API, but the managed capability must not silently apply it ([spawn](../../../../runtime/platform/process/spawn.ts#L284)).

The event journal is bounded. A cursor older than retained data returns an explicit `lost_events`/gap fact with counts and digests, not a shortened sequence that looks complete. On stream/event cap exhaustion, N records the first overflow, keeps draining or terminates the child within its hard envelope, and returns its forced-action and cleanup facts. It cannot let a blocked pipe turn an output-limit failure into an unbounded wait. Can treats lost required evidence as incomplete, even if the subject later exits zero.

Environment and descriptors are separate channels. The current trusted launcher creates a minimal Bun startup environment and sends an application environment snapshot on fd 3; fd 4 can hold a generated-output lease ([runtime launcher](../../../../compiler/internal/driver/runtime.go#L231), [RunOutput](../../../../compiler/internal/driver/output_runtime.go#L147)). Existing integration servers also receive a credential snapshot on fd 3 and use a bounded `/health` poll plus SIGTERM/Wait ([server helper](../../../../tests/integration/applications_test.go#L159), [gate-3 helper](../../../../tests/integration/gate3_matrix_test.go#L330)). Proposed `spawn` must state whether the subject expects a raw descriptor-3 snapshot, a launcher JSON snapshot, or no fd 3; do not double-allocate it. Keep secrets out of argv, inherited Bun startup flags and reports; allow only declared descriptors, keep the runner's private evidence channel out of candidate children, and record snapshot digest/byte count rather than secret contents. `inherit_env` as a convenience in current `process::run` is not an acceptable implicit default for managed candidate launch; Can selects an explicit snapshot, while native startup strips injection variables as required by the chosen executable contract. Can may intentionally test hostile environment values as *data* in the fd-3 snapshot without letting them affect the runner's own startup ([environment test](../../../../tests/integration/io_env_test.go#L56)).

The event API is a transport, not a hidden readiness engine. For a server, Can chooses the health route, expected status/body and retry/deadline; it calls a generic HTTP operation and compares the raw response. For drain, a signal-delivery receipt alone is not a causal witness that the server entered shutdown; Can needs an independent observation such as refusal of a new connection while a held request remains pending, followed by the held response and clean exit. The ledger requires actual shutdown/replay/crash behavior, not just a successful child spawn ([lifecycle case](../native-can-tests-migration-ledger-2026-09-30/lifecycle.md#life-008)). Native code may enforce a hard timeout or kill escalation, but may not decide that `/health == 200`, a response body or a DB revision constitutes passing behavior.

## Enforcement and failure boundary

Hard limits belong to N and apply before a Can request is accepted: one initial live case worker, at most the declared managed children/services for that case, finite run/case/operation deadlines, per-channel input/output/event limits, an owned-workspace byte/entry budget and bounded cleanup/recovery time. The authoring draft proposes a ten-minute run, one-MiB case-event budget and individual case deadlines ([source](../../native-can-test-authoring-2026-09-30.md#fixtures-and-resource-lifetime)); exact workspace/process ceilings and enforcement methods still need selection and target-host proof. Buffer limits must be applied **while receiving**; the current assertion supervisor uses `bytes.Buffer` and only later truncates forwarded diagnostics ([source](../../../../compiler/internal/driver/supervise.go#L240)).

A process group reaches only descendants that remain in the group ([source](../../../../runtime/platform/process/wait.ts#L1)). It does not prevent detachment, and killing a Bun worker cannot run its in-process `finally`/owner cleanup ([spawn](../../../../runtime/platform/process/spawn.ts#L264)). The current Go supervisor kills/reaps the direct assertion worker only ([source](../../../../compiler/internal/driver/supervise.go#L240)); the current launcher cleanup ignores `os.RemoveAll` failure ([source](../../../../compiler/internal/driver/runtime.go#L285)). None of these is an OS filesystem/network sandbox or a durable child-tree ownership service. The implementation must prove an enforceable containment strategy for supported macOS/Linux hosts, or reject the corresponding live capability as unavailable. A process launch gate plus outside-worker registration addresses the spawn race, but only an actual host mechanism can guarantee descendant containment across detachment and supervisor death. Treat the candidate as potentially able to access the host until that mechanism is demonstrated; never claim a sealed workspace alone is a sandbox.

On worker death, N closes or terminates every registered child and disposes its workspace, retaining raw exit/output prefixes and cleanup errors. On controller death, N stops admission and returns a generic incomplete execution envelope; it does not invent a Can verdict. On N death, a later entry uses durable ownership/path/process identity plus inactivity proof to reconcile abandoned resources. Unknown liveness, a changed path inode, unconfirmed descendant or cleanup error yields an unresolved receipt and blocks clean success. Do not delete active, foreign or shared resources to satisfy a budget. Keep compact evidence rather than full bundles; heavy retention needs an explicit expiry and automatic reclaim ([completion contract C8–C9](../../native-can-tests-completion-contract-2026-09-30.md#6-resource-limits-and-cleanup)).

The main unresolved host mechanisms are (1) durable pre-exec registration/launch gating, (2) descendant containment if a process detaches, (3) enforceable per-scope disk/process budgets and filesystem confinement for candidate subjects, (4) crash-safe identity/liveness checks for recovery, and (5) cross-process private channel/descriptor lifecycle. These are gates for claiming the managed capability, not reasons to move readiness, fixture choices or pass/fail logic into Go or JavaScript. No current code has been changed or run to demonstrate them.
