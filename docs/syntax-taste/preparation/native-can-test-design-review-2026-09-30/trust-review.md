# Trust-boundary review of native Can test design

Scope: read-only review of the 2026-09-30 architecture, capabilities, prerequisites, hard-case challenge, preparatory results, canonical execution summary, PM-N1/PM-N2 raw records and finalization, and the registered N1/N2/N3 experiments. This review did not run a build, browser, test or candidate. Severity describes the consequence if a seam is left unresolved; it does not imply the unimplemented system already has the defect.

## Findings

1. **P1 — Specify an independent witness for actual C-adapter invocation before N2 can be credited (design acceptance gap).** The design rightly keeps C outside R's judge and requires a reviewed same-realm ingress, but the current acceptance wording says only that evidence must prove a named export was invoked. A candidate-side wrapper's `invoked: true` is self-report, and a result shaped like `CodecIssue(type, "")` plus a zero getter counter cannot by itself prove that C-generated Can called its production adapter. The PM-N2 instrument sets `invoked = true` immediately before its direct `encodeJSON` call; it is good evidence for that fixed source-module probe, not for the future emitted path. See [architecture lines 105–110](../../native-can-test-architecture-2026-09-30.md#L105), [capabilities lines 167–185](../../native-can-test-capabilities-2026-09-30.md#L167), [N2 acceptance/control lines 114–126](../native-can-test-hard-cases-2026-09-30/experiments.md#L114), [PM-N2 scope lines 23–33](../native-can-test-preparatory-checks-2026-09-30/native-scope.md#L23), [raw PM-N2 facts](../native-can-test-preparatory-checks-2026-09-30/run-20260930T162840-599df6-results.json#L477), and [instrument snapshot](../native-can-test-preparatory-checks-2026-09-30/run-20260930T162840-599df6-instruments.json). Resolve by defining a reviewed, version-bound ingress/witness contract: a trusted host observer supplies the raw handle in the C subject realm, records the exact C artifact/export invoked and the same-realm counter/identity facts, and exports only inert facts to R. Qualify it with a deliberately bypassed export, a wrong export/signature, an eager-getter fault and a forged completion-shaped value. Keep product output and candidate claims as untrusted observations. Until that contract is demonstrated, N2 is an open implementation gate, not a failed backend decision.

2. **P1 — Keep native descriptors and operation catalogues mechanically finite (implementation review gate).** `native.make`, `native.invoke`, `native.fault` and browser `dom_batch` are powerful enough that a growing catalogue could turn into an authored host scenario interpreter even without an `eval` string. The current contract explicitly forbids whole-test operations, branches, loops, waits and native verdicts, so this is a boundary to enforce, not a defect already present. See [architecture lines 41–45 and 91–117](../../native-can-test-architecture-2026-09-30.md#L41), [capabilities lines 118–143 and 161–187](../../native-can-test-capabilities-2026-09-30.md#L118), and [hard cases lines 18–25, 63–75](../../native-can-test-hard-cases-2026-09-30.md#L18). Before admitting each binding, document its native primitive, typed inputs, raw facts, synchronous/async behavior and side effects; reject case-specific names, embedded assertion predicates, fixture selection, native retries or descriptor branches keyed by expected outcome. Put expected values, sequencing and verdicts in ordinary Can. A generic observer may count/read/compare identity inside a realm because those are native facts; the comparison to an expected identity must remain in Can.

3. **P1 — Generated Can ingress remains unqualified despite PM-N1/PM-N2 success (known implementation gate).** PM-N1 covered one getter-backed thenable and alias with zero pre-action accesses and a deliberate assimilation control. PM-N2 imported `runtime/codec/json.ts` directly, used one inline schema and found `reason=type`, `path=""`, zero getter calls, with a contaminated ingress control. The canonical summary marks both mechanics supported while `integrated_can_qualification=false`; the raw job statuses were pending final root cleanup and the finalization subsequently marked those jobs supported. None demonstrates emitted `createCodec` wiring, a C-built ordinary Can call, cross-realm completion authentication or the N1 exact-number/Proxy breadth. See [preparatory results lines 3–11, 44–50](../../native-can-test-preparatory-results-2026-09-30.md#L3), [execution summary lines 5–26](../native-can-test-preparatory-checks-2026-09-30/execution-summary.json#L5), [finalization lines 6–24](../native-can-test-preparatory-checks-2026-09-30/run-20260930T162840-599df6-finalization.json#L6), [PM-N2 scope lines 31–33](../native-can-test-preparatory-checks-2026-09-30/native-scope.md#L31), and [hard cases lines 69–77](../../native-can-test-hard-cases-2026-09-30.md#L69). Preserve the narrow mechanics result, then require the separate N1 breadth and N2 compiled-subject controls before migration credit. Do not rename direct source import as C adapter integration.

4. **P1 — Reference/suite promotion and external cleanup remain explicit trust gates, not architecture defects.** No accepted R bundle or qualified N executable was inventoried; source hashes and historical test results do not create either role. The plan gives R the judge, N the independent completion/cleanup receipt, and requires negative controls against early success, missing checks, malformed reports, death and cleanup failure. See [prerequisites lines 15–24, 45–52, 87–100](../../native-can-test-prerequisites-2026-09-30.md#L15), [architecture lines 119–159, 226–258, 291–325](../../native-can-test-architecture-2026-09-30.md#L119), and [capabilities lines 27–61](../../native-can-test-capabilities-2026-09-30.md#L27). Preserve separate reviewed acceptance records for R, suite/expected vectors and N. Bind reports to exact R/N/S/A/C identities and require both the Can verdict and matching N receipt. Bootstrap host controls may establish the first seed/owner; they must remain transitional evidence and cannot become a silent permanent oracle or let C promote itself.

5. **P1 — Browser host isolation must be part of native resource acceptance (observed preparatory failure).** The PM-B1 route protocol worked after one bounded instrument repair, but the user reported a Keychain dialog from the direct Chrome launch; the exact dialog process was not captured. The canonical summary correctly marks PM-B1 failed overall and blocks repeating that launch configuration. Process/profile cleanup alone missed a host UI effect. See [preparatory results lines 16–26, 40–50](../../native-can-test-preparatory-results-2026-09-30.md#L16) and [execution summary lines 37–67](../native-can-test-preparatory-checks-2026-09-30/execution-summary.json#L37). Before another browser admission, declare test-only credential behavior, observe absence of host UI and preserve the route/delivery versus input-settlement distinction. This is a concrete launch/isolation remediation, not evidence against Can owning browser policy.

## Overall assessment

I found no current design instruction to put expected answers, scheduling, retries, coverage reduction or pass/fail policy into N or browser/native services, and no claimed candidate self-qualification. The main risk is implementation drift at the flexible operation catalogue and C same-realm ingress. The architecture already says those are restricted; the actionable addition is an independently qualified witness contract for N2 so a C-produced fact cannot authenticate its own adapter execution. All integrated gates remain open as documented.

## Final reread after reconciliation

The [canonical review](../../native-can-test-design-review-2026-09-30.md#L83) and revised [capability contract](../../native-can-test-capabilities-2026-09-30.md#L251) address the main N2 acceptance gap. They require a reviewed version-bound observer at the adapter boundary, an adapter-bypass control, separate instrumented artifact identity when needed, and an uninstrumented production leg before parity is claimed. They explicitly deny that same-realm instrumentation is a sandbox against malicious C. I found no remaining contradiction in that trust model; the precise hook and the comparison criteria for the uninstrumented leg are still implementation/qualification work. A leg's existence alone must not be read as parity evidence: its relevant raw result, identity/counter facts, completion behavior and seeded fault sensitivity need to match the declared instrumented scope, with any observer-only facts labeled accordingly. This is a P1 acceptance detail, not a reason to replace the backend now.

The [lifecycle correction chain](../../native-can-test-lifecycle-2026-09-30.md#L104) preserves the original report/receipt and appends a late host-effect invalidation with run identity, scope and attribution limits; [campaign reduction](../../native-can-test-lifecycle-2026-09-30.md#L470) forbids selecting only later successes. The model is internally consistent. Implementation still must make the compact correction registry authoritative to consumers, including a distinguishable empty chain versus an unavailable/conflicting chain; the document already says the latter is unavailable evidence. This is a P1 consumer/registry qualification gate, not an observed design contradiction.
