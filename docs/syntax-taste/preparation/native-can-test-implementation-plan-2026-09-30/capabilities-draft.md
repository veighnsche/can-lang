# Capability lanes for the native Can test implementation plan

Status: planning input only. No implementation, browser launch, service start, build, integrated experiment or old-test deletion is authorized by this draft. The fourteen [integrated hard-case entries](../native-can-test-hard-cases-2026-09-30/experiments.md) remain unrun. The [design review](../../native-can-test-design-review-2026-09-30.md), [capability contract](../../native-can-test-capabilities-2026-09-30.md), [lifecycle contract](../../native-can-test-lifecycle-2026-09-30.md) and [hard-case challenge](../../native-can-test-hard-cases-2026-09-30.md) govern every task below.

These `K` IDs are capability tasks for the eventual main plan. `P-core` below means the separately qualified R, N, suite-snapshot, admission, typed transport, ownership, independent receipt and cleanup foundation; replace that shorthand with exact `P` IDs when merging. `Rnative`, `Rbrowser`, `Rdb` and `Rpeer` mean **new, separately accepted reference snapshot/capability slice** built by the single integration owner after the corresponding catalogue and package changes. These are dependency gates, not labels that an individual capability lane may self-award. An ordinary Can case/check ID, its R-built artifact, C subject identity, positive result, seeded defect/missing-evidence control and N receipt are required to credit an integrated entry. Native mechanics and bounded negative unit checks can proceed before `P-core`; integrated acceptance and migration cannot.

## Ownership and parallelism

Give each implementation lane a new prefix: `tools/runtime/test-services/native-values/`, `tools/runtime/test-services/browser-driver/`, `tools/runtime/test-services/http-peer/`, `tools/runtime/test-services/db-observer/`, and `tools/runtime/test-services/object-store/`. These are proposed homes for typed native services, data-only operation schemas and focused unit checks; move an entire prefix once during integration if the final build layout requires it. The descriptor lane owns `compiler/internal/nativetestdescriptor/` (new Go package). The **N foundation owner**, not that lane, owns the core Go supervisor, process spawning, `ExtraFiles`, journal, recovery, lease accounting and host enforcement. Capability lanes can supply narrow interface requirements and test fixtures to that owner. The single integration writer owns shared `compiler/internal/catalogue/`, `compiler/internal/check/`, `compiler/internal/emit/`, `compiler/internal/resolve/`, `compiler/internal/types/`, `runtime/catalogue.ts` generation, suite package wiring and any common N protocol file. Do not have independent lanes edit those files concurrently. Existing `runtime/platform/browser.ts`, `http.ts`, `websocket.ts`, `s3.ts`, `sql/*`, `runtime/codec/*`, and `compiler/internal/driver/{run,supervise,output_unix}.go` are product paths to compare with or touch only through a reviewed integration assignment; their current behavior does not qualify new test bindings. Old host tests under `tests/` remain intact until row gates pass.

The service interfaces may provide only reviewed typed actions and observations. They contain no case names, expected answers, retry/selection policy, scenario branches, arbitrary evaluation, `run_probe` or executable source strings. All scenarios, fixture bytes, expected values, retries, timeout meaning, checks and result reduction live in ordinary Can under a new `tests/native-can/` prefix, authored by the migration lane. Capability lane controls may use small native-focused tests to establish mechanics, but those tests cannot replace Can oracles. Shared core processes reserve the entire phase peak before a case starts; browser engines and DB services remain separately admitted dependencies. Hard memory/process/disk guarantees need identified host enforcement, charged scope and finite overshoot proof; polling cannot establish them. Use one live case, one verification worker and one build producer in the required phase order. No broad build, performance run, engine download or persistent full bundle cache follows from this plan.

Every `K` completion commit should contain its source plus focused bounded checks or an explicitly blocked result. The first reviewable commits are K01/K07/K17/K20/K22/K27 interface and ownership seams; follow with one or a few tasks per capability prefix. Reconcile a capability slice and record the exact R snapshot before any corresponding integrated trial. Authored `runtime/` or `tools/runtime/` TypeScript edits require `bun run lint:fix:runtime`, `bun run format:runtime`, `bun run check:runtime` and relevant tests; diagnostic runs can use `bun run lint:runtime --format=agent`. A service under `tools/runtime/test-services/` still needs its own focused lint/type/test gate. Allocate owned temporary roots with immediate cleanup registration and retain compact evidence only.

## Integration and deletion gates

Mechanics code can be merged once focused checks and review pass, even while a host/service is unavailable. `Rnative` refresh follows K01–K03; N2 needs a second accepted snapshot after K04–K05; N3 after K06. `Rbrowser` can begin after K07–K12, before QB1; B2–B5 require their own refreshed slice when bindings change. `Rdb` starts with K22–K23 and extends per D2–D4. `Rpeer` can start with K20. Each refresh records source closure, compiler/runtime/catalogue hashes, package signatures and reviewed binding effect contracts; an older R cannot silently exercise newly added operations. Commit each accepted slice before migration work depending on it, but keep one build producer and verification worker in a run.

No old harness row is deletable from a passing capability task or preparatory PM result. The [292-row ledger](../../native-can-tests-migration-ledger-2026-09-30.md) must first map every retained facet, variant and environment to ordinary Can case/check IDs with valid positive and seeded defect/missing-evidence controls, matched correction-aware R/N report and cleanup receipt, and resolved current callers. Required engines/services that are absent remain blocked. Browser row deletion additionally needs qualified host-effect admission through disposal. D1–D4 and the new sentinel/settlement checks are stronger qualification obligations, not evidence that older drivers already supplied them. Deferred `METRIC` rows remain open without running measurements. The responsible migration owner makes per-row deletion commits only after recording all gates; the capability lanes do not delete `tests/` files.
