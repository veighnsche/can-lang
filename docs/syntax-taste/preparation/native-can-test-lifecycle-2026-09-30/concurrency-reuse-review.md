# Concurrency, build reuse and failure-lifetime review

Status: design proposal based on source; **no builds, tests or measurements**. The [architecture](../../native-can-test-architecture-2026-09-30.md#L12) fixes one reference-built Can controller, fresh case-worker processes and outside-worker ownership. The [capability contract](../../native-can-test-capabilities-2026-09-30.md#L24) fixes scoped handles, at-most-once dispatch and incomplete cleanup reporting. This note fills in scheduling and reuse policy without turning a native cache into a hidden test planner.

## Default admission and order

**Proposed initial default:** one active live case/variant/attempt; one offline assertion worker during verification; one active candidate build fill; one browser-heavy leg and one DB-heavy leg at a time. These are *global run admission slots*, not limits of one child, page, browser context or DB connection *inside* a case. Cases that test two workers, several pages, or concurrent SQL writers must declare and receive bounded per-case subresource budgets ([LIFE-004](../native-can-tests-migration-ledger-2026-09-30/lifecycle.md#L125), [LIFE-011](../native-can-tests-migration-ledger-2026-09-30/lifecycle.md#L299)). The controller selects runnable cases and their order in Can; N atomically enforces the declared maximum and queues/rejects mechanical acquisitions. No implicit native retry or alternative-engine selection.

1. N registers the owned run/recovery record, validates R/N/C and the finite profile, reserves total run storage/process/event ceilings, then stages A through R in a nonpublishing scope. A is checked from one immutable suite-source snapshot and all offline roots run before live cases in the initial bootstrap. Thus the normal path has no live case competing with verification; “one case plus one verification worker” is an upper admission description for later qualified focused operation, not a reason to overlap bootstrap work ([architecture normal run](../../native-can-test-architecture-2026-09-30.md#L160)). Existing assertion supervision can fan out to four workers by default, but those workers are full Bun processes and its own source says higher fan-out adds heat/memory; this is evidence for choosing **one**, not importing four into the new laptop profile ([supervise.go](../../../../compiler/internal/driver/supervise.go#L20), [supervise.go](../../../../compiler/internal/driver/supervise.go#L103)).
2. The Can controller validates the complete registry/coverage plan and declares each selected case's maximum resource class before launch. N admits a case only when its whole declared heavy-resource reservation and run envelope fit; this prevents a case from holding a scarce DB namespace while waiting indefinitely for a browser slot. Can still chooses the actual acquisition/interaction order. A sensible ordinary browser case orders `build/lease → DB namespace/seed → server readiness → browser context/watch → actions → browser seal/close → server/DB close`; a case requiring a different race says so explicitly. Leases are acquired as late as the scenario allows and released before admitting the next heavy leg.
3. Request a common candidate build before launching cases that consume it, or let the first case trigger a **single flight** owned by N; Can chooses grouping and build-vs-run order. N's build admission is one fill at a time initially. Waiters for an identical key join the same operation and get either the same verified artifact lease or the same failure, never separate concurrent fills. Build admission reserves staging bytes and child slots before the first write/spawn. A waiting case does not hold browser/DB resources. The current Go harness already builds one bundle per input key, keeps per-test mutable state separate and checks each hit's manifest hashes ([harness_test.go](../../../../tests/integration/harness_test.go#L1), [LIFE-023/024](../native-can-tests-migration-ledger-2026-09-30/lifecycle.md#L614)).
4. Once a case starts, N launches one fresh Bun worker from A, grants its owned workspace/process/browser/DB handles, and records all admitted actions. Case completion requires worker outcome, Can evidence, and N's cleanup receipt before its reserved slots are reusable. On cancellation, stop *new* admission, resolve/abort held routes/requests, terminate/reap descendants, close browser/DB namespaces, and only then delete owned work; unknown cleanup blocks a clean pass and further reuse of the affected resource ([architecture cleanup boundary](../../native-can-test-architecture-2026-09-30.md#L265), [capability close](../../native-can-test-capabilities-2026-09-30.md#L51)).

The one-case default is more conservative than the current integration harness's three heavy slots, whose source says each heavy browser/server/build test is roughly 2 GB and four coinciding on a 16 GB host caused swap/stalls ([harness_test.go](../../../../tests/integration/harness_test.go#L64)). That statement describes the old harness and host, **not** a measured memory profile for the new runner. A future `--jobs` increase needs bounded measurements and a qualified profile; merely exposing the old configurable maximum of 64 assertion workers would contradict the laptop constraint. Retain a mechanical negative control that capacity blocks a third acquisition and release admits a waiter; exact old default `3` is not a compatibility requirement ([LIFE-021/022](../native-can-tests-migration-ledger-2026-09-30/lifecycle.md#L566)).

## Reuse identity and lifetime

Reuse is a **Can-selected policy over native verified facts**, and only within one owned run. N stores immutable read-only generations and checks requested identity/lease validity; it does not infer two named scenarios are equivalent. Distinguish these keys and receipts:

| Reusable item | Exact key / reuse condition | Lifetime and exclusions |
| --- | --- | --- |
| Suite artifact A | R acceptance identity (compiler/emitter/runtime/catalogue/Bun and relevant bindings), exact suite source/dependency/fixture-byte closure, lock/manifest/options/target and nonpublishing entry protocol. Retain A digest and checked-root inventory. | Exactly one run-owned generation normally; controller and fresh workers lease it. Suite-source or R change invalidates it. Verification is a **separate receipt** keyed by source graph, root set, R, profile/fixtures and selector-planner identity: a partial root receipt never upgrades to full because the compiled artifact is the same. Never compile A with C. |
| Candidate build subject | C compiler/build-tool identity; exact declared and actual-read source/dependency/lock/asset snapshot; target/options/feature flags; compilation-relevant environment and browser pairing/asset manifest; runtime/catalogue/executor identity where generated/runtime behavior depends on it. Verify artifact manifest/tree and input seal on every hit. | Successful, complete, immutable output only. Share by read lease across cases in this run. A build rejection, infrastructure failure, partial generation, mutable output, changed input or missing proof is not a reusable success. Per-case homes, DBs, ports, server processes and browser contexts are never cached with the executable. |
| Browser/DB observation | Candidate artifact plus exact engine/version/profile, input/seed and resource state, event-completeness/cleanup receipt and named coverage scope. | Prefer re-execution of live scenario legs; reuse only when Can explicitly establishes same observational scope and the full event/cleanup receipt matches. A screenshot or shorter report alone cannot satisfy another engine or leg ([migration ledger](../../native-can-tests-migration-ledger-2026-09-30.md#L80)). |

The candidate build key must be derived from **captured bytes and resolution facts**, not source paths, mtimes, or a memoized `(path, archive)` identity that remains valid after mutation. The present Go harness memoizes tree hashes under the assumption inputs cannot change mid-process ([harness_test.go](../../../../tests/integration/harness_test.go#L177)); the new suite intentionally mutates staged fixtures, so each input revision must carry its own seal and key. The product diagnostic contract distinguishes declared inputs from the actual-read set and resolution lookups ([capabilities](../../native-can-test-capabilities-2026-09-30.md#L207)). If a candidate's inputs change while building, invalidate the build and its waiters rather than publishing a result under the old key. If its runtime or browser target differs, either include that identity in the reusable item's contract or defer executor-specific verification to a distinct keyed receipt; a compiler build ID alone is insufficient.

Use an explicit `fresh_build`/`bypass_reuse` request for determinism, repeat/relocated-build, contamination-detection, tampered/stale-manifest, negative publication and build-corruption cases. The opt-out creates a separate owned staging/output generation and records that a real build occurred; it does **not** alter expectations or allow silent fallback to a cache hit. Repeated builds that intentionally compare identity should be two actual builds against separately staged but equivalently sealed inputs. Compiler-rejection cases invoke C on each selected invalid revision and retain paired valid-control evidence; they do not memoize an earlier rejection. The ledger specifically preserves repeat/relocated identity, changed-input invalidation, mutated-cache refusal and at most one fill for an identical key ([BROWSER-006/008/009](../native-can-tests-migration-ledger-2026-09-30/browser.md#L136), [LIFE-016–020](../native-can-tests-migration-ledger-2026-09-30/lifecycle.md#L446)).

On a cache hit, validate the generation's manifest/file hashes and active immutable lease before returning it. Never repair a contaminated entry in place while another case holds a read lease; quarantine it, fail/invalidate affected consumers, and fill a fresh owned generation only as an explicit new attempt. The existing cache tests protect pristine-hit acceptance, tamper detection and completion-key refusal ([LIFE-018–020](../native-can-tests-migration-ledger-2026-09-30/lifecycle.md#L494)). Run end releases all leases, removes A and candidate build generations/source copies, and keeps compact manifests/reports only. No cross-run private bundle persistence by default. Existing `tempcache` illustrates owned child deletion and liveness-checked abandoned recovery, but its age-based prefilter and warnings are not a complete new supervisor guarantee ([tempcache/cache.go](../../../../tests/support/tempcache/cache.go#L98), [tempcache/cache.go](../../../../tests/support/tempcache/cache.go#L130)).

## Failure and cancellation details

- **Builder fails or is killed before completion:** return failed/indeterminate build with partial output and input-read facts; invalidate its fill marker; keep the partial generation owned until cleanup. No waiter receives an artifact handle. A subject compiler's expected nonzero/rejection is case data; a build intended to supply a reusable production artifact is not complete on that result. If a waiter cancels, remove only that waiter; the run-owned fill continues for other waiters. If no waiter and no declared future consumer remains, Can/N cancel the fill through the run's bounded cleanup protocol.
- **Lost build acknowledgment:** query the same operation ID/generation under the at-most-once protocol. Do not launch a second compile merely because the first reply disappeared; if dispatch status remains indeterminate, make the case incomplete or start a separately identified explicit attempt after reconciliation. N must record intent before spawn and include partially created outputs in its recovery ledger ([capabilities](../../native-can-test-capabilities-2026-09-30.md#L30)).
- **Controller or worker death:** N stops admission, contains children and external browser/DB resources, revokes case leases, and returns a generic execution/cleanup receipt. It does not invent Can verdicts. A healthy shared artifact may still be retained for remaining cases only if the controller's Can policy remains available; controller death ends the run. A failed/unknown cleanup prevents another case from using the same workspace, browser connection or DB namespace ([architecture](../../native-can-test-architecture-2026-09-30.md#L285)).
- **Scarce service absence:** required browser/DB capability unavailable is an explicit incomplete/skipped-as-profile-limited result under Can's declared selection policy, never a green replacement leg. Do not silently substitute a local engine for remote Firefox, or SQLite for PostgreSQL. Resource wait itself has a finite deadline and a distinct admission failure. Distinguish a subject's expected timeout from a judge/driver timeout ([completion contract](../../native-can-tests-completion-contract-2026-09-30.md#L174)).

**Numerical envelope:** the only directly sourced current values are assertion-root default `5,000 ms`, allowed `1..600,000 ms`, old assertion fan-out default up to `4`, old heavy-test default `3`, and a retained 200-row drain obligation bounded by `120 s` with peak RSS below `256 MiB` for that subject ([supervise.go](../../../../compiler/internal/driver/supervise.go#L20), [harness_test.go](../../../../tests/integration/harness_test.go#L64), [LIFE-011](../native-can-tests-migration-ledger-2026-09-30/lifecycle.md#L299)). They do **not** measure the new controller, browser driver, database or whole suite. Propose `1` live case, `1` verification root, `1` candidate fill and `1` browser/DB-heavy leg as initial caps. Keep existing `5 s` only as a provisional offline-root default; named roots may request more within a reviewed ceiling. Do not freeze run/case/cleanup duration, RSS, disk, stream or event byte ceilings from these heterogeneous numbers. The first executable profile must state finite positive values for all of them and verify host enforcement before claiming admission; a 120 s subject leg needs separate teardown margin, not a case deadline equal to 120 s ([capabilities resource profile](../../native-can-test-capabilities-2026-09-30.md#L49)).
