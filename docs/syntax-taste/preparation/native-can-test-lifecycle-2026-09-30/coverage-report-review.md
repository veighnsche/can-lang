# Coverage and failure lifecycle review

Status: design review only. No implementation, test, build or measurement was run. This refines the [completion contract](../../native-can-tests-completion-contract-2026-09-30.md), [Can authoring design](../../native-can-test-authoring-2026-09-30.md), [execution architecture](../../native-can-test-architecture-2026-09-30.md), and [capability contract](../../native-can-test-capabilities-2026-09-30.md). The ledger's 292 entries identify obligations, not 292 automatically passing cases. Its environment gates include disposable PostgreSQL/MySQL/S3 services and browser engines; current Go `t.Skip` behavior cannot become full Can qualification.

## Keep independent dimensions

A single `passed/failed/skipped` field loses essential evidence. The report should preserve these axes for every expanded `(case ID, variant, attempt)` and for the run:

| Axis | Suggested values and rule |
| --- | --- |
| Selection | `selected` or `unselected(filter/profile)`. Expand the profile's declared variant matrix before capability admission. An unselected Firefox variant is distinct from a selected Firefox variant whose engine is absent. Zero selected work is a planning error. |
| Admission | `admitted` or `blocked(requirement, capability/guarantee, host evidence)`. Block means a selected case could not begin because a required service/engine/guarantee was unavailable. If it disappears **after** admission, record an execution failure, not a retroactive skip. |
| Execution | `not_started`, `running`, `completed`, `failed`, or `cancelled`, with cause and worker/transport facts. `completed` requires a valid terminal record and complete required event interval. A child subject's expected exit or timeout is observed data; worker/controller timeout, death or lost terminal evidence is execution failure. |
| Behavior | `passed`, `failed`, or `not_evaluated`. A Can mismatch is sticky even if caught and followed by `ok`; a short-circuit failure marks later required checks `not_reached`. A worker's bare `ok` with missing checks is execution/report error. |
| Cleanup | `complete`, `failed`, or `unknown`, with N's resource receipt. Cleanup can fail alongside a behavioral failure; keep both. Unknown or failed cleanup prevents clean success. |
| Verification | Complete required offline roots, qualified focused root closure, or incomplete, with root IDs and selection basis. Initial bootstrap verifies all roots. A focused closure is partial evidence even when it finished successfully. |
| Coverage scope | `full-profile` or `selected-subset`, with declared profile version, selected/unselected case-variant IDs, independent ledger obligation mapping and required environments. This describes **intended scope**, not whether execution finished. |

The most important split is **intentional partial scope versus incomplete execution**. A selected subset can finish and pass its stated scope; it is never labelled full qualification. If a selected variant is blocked, cancelled, unrun, or loses evidence, the selected scope is incomplete and cannot exit green. Required profile membership and obligations come from reviewed Can registry/coverage data reconciled to the independent ledger, not from events that happened to pass. Deleting a case/check and its local plan entry cannot erase the obligation. A successful listing validates selection but confers no live or offline verification credit.

For each required check, retain one of `passed`, `failed`, `not_reached`, `missing`, or `invalid_evidence` plus evidence scope (`supplied assertion`, `live production`, `native observation`, etc.). A named mismatch may ordinarily stop later checks, leaving `not_reached` without adding a protocol error. Returning `ok` with a `missing` check, duplicate/unexpected check ID, wrong scope, wrong case/variant/attempt identity, sequence gap, or missing final record is a protocol/execution error. A zero-check case needs a separately declared and validated obligation. Counts are derived from IDs and state, not trusted as a replacement for the records.

## Report and exit disposition

Can owns check plans, comparison, retry and aggregation policy. N owns launch/transport/cleanup facts and enforces bounds; it may emit an execution-failure envelope when Can cannot. Candidate stdout/stderr, candidate CLI JSON and browser events never become private worker messages. A complete machine result requires the Can report **and** matching N completion/cleanup receipt, bound by run ID, suite/reference/candidate identities, selected plan digest and terminal event boundary. A Can `passed` report written before cleanup is provisional. N may force the outer result to nonzero on missing/failed receipt as protocol enforcement, without inventing a Can case verdict.

The proposed exit mapping can stay simple while preserving all axes in JSON:

| Exit | Final disposition |
| --- | --- |
| `0` | Every selected case-variant has a Can pass, complete execution/required checks, successful verification for the declared scope and complete cleanup; no blocked/unrun selected work. Also valid for a successful `--list`, marked `mode=list` with no qualification claim. A filtered success says `selected-subset`, not `full-profile`. |
| `1` | At least one Can behavioral failure and otherwise valid, complete execution/coverage accounting and cleanup, with no selected blocked or incomplete work. Retain every failing check and observed fact. |
| `2` | Planning/identity mismatch, blocked selected capability, missing required service, malformed/missing private report, incomplete verification, selected unrun/cancelled work, worker/controller crash, timeout, transport gap, report overflow, infrastructure failure, or failed/unknown cleanup. Preserve any simultaneous Can behavioral failure rather than replacing it. |
| Interruption status | A conventional explicit user-interruption code may be propagated, but the report/receipt still marks all unfinished selected variants and cleanup state. It never grants completion. |

If a subject is meant to crash, exit nonzero, return HTTP 500 or time out, the **subject** operation returns that fact; Can can pass the case only after the corresponding named checks, bounded observation and cleanup complete. A judge worker crash, controller crash or lost private terminal report has no valid Can success decision. On controller death N stops new dispatch, contains existing resources and emits only a generic incomplete execution envelope with partial facts; it cannot decide which case would have passed. On N death, later recovery must reconcile owned work before any completion receipt is trusted. A malformed candidate product CLI report is a subject/protocol observation for Can to classify; it cannot satisfy an expected compiler rejection. A malformed Can suite report or mismatched N receipt is always a run-integrity failure.

## Stop policy, retries and required variants

Can may choose fail-fast, but it first records the full expanded selected plan. After the stop trigger, mark queued variants `not_started(reason=failfast)` and account for in-flight variants as completed, failed or cancelled with N's facts. N can enforce a hard stop or transport failure without making a case-specific stop-policy choice. Neither side may omit unfinished selected IDs from the final report. Fail-fast can save work; it cannot produce a successful complete selected scope or full qualification when selected variants remain unrun.

Default attempts are one. Any Can-selected rerun records all attempt IDs, original failures, inputs/candidate/profile identities, reasons and resource receipts. The final case policy (for example, whether an explicitly permitted flaky retry can pass) is Can code and must be declared in the selected plan; native services do not retry cases. An indeterminate write/commit/spawn from an attempt is reconciled or remains incomplete before a later attempt touches the same mutable subject. A passing retry never deletes a failed earlier attempt, and full qualification cannot silently treat an unstable required leg as if it passed once cleanly.

Profile variants are explicit identities, not incidental loops. For example, `engine=chromium|webkit|firefox` and PostgreSQL/MySQL/SQLite or S3 legs are included or excluded by the reviewed profile before execution. A profile may define a genuinely optional leg; its absence is recorded as unselected/optional and the resulting qualification scope excludes that leg. A leg required by the selected profile but missing locally is blocked and yields exit 2, even if every available variant passes. Evidence from separate bounded jobs may jointly satisfy a full profile only when the suite/coverage snapshot, reference qualification, candidate/input identities, required variant matrix and environment provenance are compatible. A quick local green cannot stand in for the required browser or database matrix.

## Controls that must not go green

Seeded controls should establish that a wrong observation, wrong diagnostic phase, early `ok`, missing/duplicate check, dropped terminal event, altered case/variant/attempt ID, malformed or missing Can report, mismatched N receipt, unavailable required service, blocked engine, subject crash misclassified as judge completion, judge crash, worker timeout, cancellation, failed cleanup and unknown recovery all prevent a complete green run. Include a control where Can reports a real behavioral mismatch and N later reports cleanup failure: both dimensions remain visible, with nonzero final status. Include an intentional subset that finishes green only for its declared subset and a full-profile request with one missing required variant that exits incomplete. These are future bounded correctness gates, not runs authorized by this review.
