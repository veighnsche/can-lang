# Final resource/lifecycle contract review

Status: read-only review of the [main lifecycle draft](../../native-can-test-lifecycle-2026-09-30.md). No implementation, tests, builds or measurements were run.

1. **Finalize absence/late-event checks only after their final observation seal.** The draft says required browser/native intervals are sealed before the worker's `body_terminal`, but N continues draining late callbacks after worker completion ([state transitions](../../native-can-test-lifecycle-2026-09-30.md#2-state-transitions-and-final-reports)). A worker cannot irreversibly mark `no late error` matched if later N-owned close/drain events belong to that check's interval. Specify either (a) the worker closes and seals the entire required interval before body terminal, with later N cleanup facts explicitly outside that claimed interval, or (b) body-terminal checks are provisional and the ordinary Can controller completes named late-event/absence checks after N supplies a final case seal. Option (b) preserves Can-owned policy and the stated post-worker drain. N must still carry gaps, callbacks and cleanup faults to the controller before its aggregate; a final seal with unresolved callbacks is incomplete, never a successful absence observation.

2. **Define admission arithmetic for the cleanup reserve.** The table declares total run time *including* cleanup, a reserved final portion, separate per-case cleanup maxima and case-body maxima ([finite envelopes](../../native-can-test-lifecycle-2026-09-30.md#initial-finite-envelopes)). As written, a body can run to the execution cutoff, leaving only the 60/180-second reserve for both case cleanup and run cleanup. State whether that reserve covers both; if it is intended for run-final cleanup, admit a new case only when its declared maximum body **plus** bounded case cleanup fits before the execution cutoff. In either interpretation, compute one absolute monotonic run deadline, execution cutoff and cleanup deadline at admission, and let all cleanup steps share the remaining interval. Otherwise the listed maxima can each be honored locally while the promised final reserve is already spent. Values are policy ceilings, not measured adequacy; this is scheduling semantics, not a request to benchmark them.

3. **Separate fixed selection from dynamically minted attempts.** The opening says to expand the complete selected plan before admission and defines a unit as `(case, variant, attempt)`, while Can owns retry policy and later diagnostic reruns retain all attempts ([scope](../../native-can-test-lifecycle-2026-09-30.md#1-keep-scope-results-and-completion-separate), [retries](../../native-can-test-lifecycle-2026-09-30.md#7-missing-services-retries-and-cross-job-qualification)). If retries can be chosen after an observation, all attempt IDs cannot be known at initial planning. Fix selected `(case, variant)` and maximum attempt envelope up front; mint each later attempt under an explicit, monotonic Can plan revision before its admission, retaining every earlier receipt and leaving the original selected scope unchanged. If all attempts instead must be predeclared, say so and remove adaptive retry language. Neither route permits a later pass to erase a failed attempt.

The draft otherwise keeps case-local, cleaned evidence faults distinct from run-wide containment/identity failures. It correctly treats N death as no final success and later recovery rather than immediate cleanup, and requires unresolved prior owned resources to block initial live admission. Its numeric limits are clearly labelled proposed policy ceilings and unavailable without host enforcement, so they should not be presented as measured capacity.
