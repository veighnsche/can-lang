# Lifecycle concurrency and reuse review

Read-only review of [the lifecycle draft](../../native-can-test-lifecycle-2026-09-30.md). The root's planned edits to reserve whole-case peak scarce demand, permit declared extra contexts and validate source-input completeness/no rejection-result cache address those points; the findings below are additional.

1. **A same-key fresh build must bypass single-flight identity.** The draft says one producer owns a key and all same-key consumers join ([reuse states](../../native-can-test-lifecycle-2026-09-30.md#L312)), but `fresh_subject_build` requires distinct production executions and output roots even for identical keys ([opt-out](../../native-can-test-lifecycle-2026-09-30.md#L327)). Define an explicit fresh attempt/generation discriminator outside the content key, and reject cache lookup and same-key joining for that request. Keep the content key unchanged in evidence so Can can compare determinism across genuinely equal inputs. Otherwise a native cache can accidentally satisfy the very repeat-build obligation being tested ([BROWSER-006](../native-can-tests-migration-ledger-2026-09-30/browser.md#L136), [LIFE-023](../native-can-tests-migration-ledger-2026-09-30/lifecycle.md#L614)).

2. **One live run per ownership domain is weaker than a host load cap.** Two independent domains/invocations can each admit one 6 GiB run on the same 16 GiB laptop while believing they are within the table's envelope ([run admission](../../native-can-test-lifecycle-2026-09-30.md#L225), [numeric profile](../../native-can-test-lifecycle-2026-09-30.md#L241)). The old harness explicitly found four simultaneous roughly 2 GiB heavy tests caused swap and stalls ([harness_test.go](../../../../tests/integration/harness_test.go#L64)). Either the supported host profile needs one host-wide live-suite admission lease/capacity authority, or it must describe cross-domain concurrency as an unproven limit and refuse a strong laptop-load guarantee. This is separate from not deleting foreign runs: their ownership stays distinct while admission can still share a host-level counter.

3. **The wall-time table needs a whole-phase feasibility rule and verification ceiling.** `quick` reserves 60 seconds for final cleanup within 10 minutes; `bounded-job` reserves 180 seconds within 45 minutes, but preparation/root verification has no aggregate phase ceiling or explicit admission calculation ([profile](../../native-can-test-lifecycle-2026-09-30.md#L241), [deadline composition](../../native-can-test-lifecycle-2026-09-30.md#L270)). Initial runs execute *all* offline roots before live cases; the existing supervisor gives each root a 5-second default, and browser projects can have hundreds of roots ([architecture](../../native-can-test-architecture-2026-09-30.md#L160), [supervise.go](../../../../compiler/internal/driver/supervise.go#L20), [BROWSER-013](../native-can-tests-migration-ledger-2026-09-30/browser.md#L319)). Say exactly whether “build/preparation producer” includes R suite emission, **all-root verification**, candidate builds or only one invocation; then require each phase/case admission to fit its declared body **plus** case cleanup and the untouched final reserve within remaining run time. If it cannot fit, block before starting the unit and leave it selected/unexecuted. These policy numbers are not a claim that a 45-minute job can contain a 30-minute case after arbitrary verification work.

4. **Defaults need per-family overrides before they can be used as executable profiles.** The 120-second `bounded-job` default case body can be consumed by a single local browser launch whose current driver allows 120 seconds, before page actions start ([profile](../../native-can-test-lifecycle-2026-09-30.md#L245), [firefox-remote.mjs](../../../../tests/integration/browser/firefox-remote.mjs#L14)). The 60-second `quick` default is even narrower. The draft correctly permits named finite case profiles, but should require explicit declared browser/lifecycle case deadlines when default cannot cover their mandated actions, and list which coverage families the initial `quick` selection intentionally excludes. A timeout caused by an undersized policy remains incomplete execution, never an expected subject timeout or a silent skip ([lifecycle profile](../../native-can-test-lifecycle-2026-09-30.md#L278)).

Potential efficiency refinement, not a correctness blocker: distinguish the immutable candidate artifact's content/build key from its validation/verification receipt. The draft currently puts the required validation recipe into the reuse key ([key](../../native-can-test-lifecycle-2026-09-30.md#L294)); this is safe but may force a second identical production build solely to obtain a stronger receipt. If the product build supports validating the same sealed artifact without rebuilding, attach a separately keyed receipt; never upgrade a weaker receipt by assertion alone. The first implementation may retain the simpler conservative key until this is demonstrated.
