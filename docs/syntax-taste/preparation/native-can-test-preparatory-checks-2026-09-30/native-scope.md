## PM-N1: handle transport before an explicit action

**One question.** Does a same-realm handle protocol carry a getter-backed `then` object across one request/response and observation cycle without reading that getter or assimilating the object?

**Minimal setup.** A single short-lived Bun child owns a map of at most four values. A small, closed host protocol accepts `make_then_getter`, `alias`, `observe`, `get_then`, and `close`; replies contain only numeric handles and fixed primitive facts. Construct one object whose `then` getter increments a private counter and throws. Return two handles to that one object. Never return the object from an async function, Promise, worker message, or report field. The parent controls an external deadline and remains alive if the child exits. This is temporary mechanics scaffolding, not a retained N interface or Can scenario API.

**Independent observation and acceptance.** The parent fixes the expected action sequence and counts before launch. In the child realm, a counter snapshot immediately after construction and after two `observe` operations must be zero; `Object.is` on the two retrieved handles must be true; the first explicit `get_then` must produce exactly one getter call and the declared thrown marker. Return only tagged counter/identity/error facts. The parent checks the entire action log through a terminal seal and fails on a missing action, extra call, early access, false alias comparison, or missing seal. The observation code must not obtain these facts by asking the candidate adapter or by serializing the hostile object.

**Negative control.** In a disposable variant, deliberately pass the retrieved object to `Promise.resolve` before `observe` and consume the expected rejection. The same zero-before-action assertion must fail and attribute the call to that control. The normal variant must remain untouched.

**Limits and cleanup owner.** At most one child at a time, four handles, eight requests and 8 KiB of tagged replies per leg, and 30 seconds for both legs inclusive of at least 10 seconds cleanup. The [common plan](../../native-can-test-preparatory-checks-2026-09-30.md) names Python parent T and fixes process/RSS/scratch/I/O limits. Register cleanup before allocating the exclusively owned directory or any child/pipe. On success, protocol error, timeout, or handled interruption, send `close` if possible, kill/reap the child if needed, remove only that owned directory, and record the cleanup outcome. Recovery requires the common lock/identity/owner-and-subject inactivity checks; a dead parent alone is insufficient. Never clean shared caches. If T dies before cleanup, the job has no successful receipt and must be reconciled before further admission.

**Remaining N1 work.** This does not establish exact `-0` bits, unsafe integer lexeme preservation, throwing thenable behavior, revoked Proxy handling, arbitrary action catalogues, Can-authored expectations, or protection after a killed parent. Those need separate bounded questions and controls before integrated N1 credit.

## PM-N2: candidate source-module ingress

**One question.** When a hostile getter-backed array enters the existing candidate codec module in the same Bun realm, does its exported `encodeJSON` reject it as a type error before the getter runs?

**Concrete seam.** [`runtime/codec/json.ts`](../../../../runtime/codec/json.ts) exports `encodeJSON(schema, input, bytes)`. Its array branch calls `dataProperty`/`dataArray` from [`runtime/data.ts`](../../../../runtime/data.ts); `dataProperty` examines own descriptors and rejects accessors. [`runtime/reflect.ts`](../../../../runtime/reflect.ts) supplies the Bun `isHostProxy` predicate. The production factory `createCodec` in `runtime/codec/json.ts` delegates its `encode` method to `encodeJSON`; [`compiler/internal/emit/program_state.go`](../../../../compiler/internal/emit/program_state.go) imports that factory into emitted state, and the catalogue declares `codec::encode_json<T>` with `T: wire`. The smallest source-module check imports `encodeJSON` directly and uses an inline schema with root `a`, an array node `a` whose element is primitive `int`, and the primitive `int` node. It avoids copying the schema generator, full runtime harness, emitted state, or compiler output.

**Minimal setup and observation.** After PM-N1 has shown inert delivery, use one short-lived Bun subject realm and a finite typed command: `encode_array_int` with one handle. The inline schema is `{root:"a",nodes:[{identity:"a",kind:"array",name:"array",element:"int"},{identity:"int",kind:"primitive",name:"int"}]}`. First encode ordinary `[1n]` with this same schema and require byte hex `5b315d` (`[1]`), read through the existing `runtime/bytes.ts::copyBytes` with a fixed probe origin. This setup witness prevents a broken schema/import from masquerading as a successful hostile-value rejection. Then the same realm constructs a one-element array with an own index `0` getter that increments a private counter and throws a unique marker, and passes that exact array to `encodeJSON`. A small subject-side wrapper catches only the local `CodecIssue` and returns inert `{reason, path, getterCalls, invoked}` facts after the call. `invoked` records the wrapper's direct call to the imported named export; it is not a compiler artifact witness. The external parent independently compares these facts against fixed expected `reason: "type"`, `path: ""`, and `getterCalls: 0`, plus a complete terminal seal. The wrapper must not use `get`, spread, stringify, or Promise assimilation on the array before the call.

**Negative control.** In a separate disposable variant, make the wrapper read index `0`, catch the deliberately thrown marker, then call the same `encodeJSON`. The counter must increase and the zero-access acceptance must fail; the control cannot be reported as a successful adapter case. A wrong export/signature should also fail at setup rather than silently falling back to raw Bun behavior.

**Limits and cleanup owner.** One subject child at a time, one hostile value per variant, at most four operations and 8 KiB of inert facts per leg, and 30 seconds for setup witness and both variants inclusive of at least 10 seconds cleanup. The common plan fixes aggregate limits. Use the same T-owned directory/PID registration and success/failure/interruption cleanup procedure as PM-N1. No private runtime module swap, dynamic import chosen by a case, compiler build, general evaluator, persistent bundle, or schema mirror is in scope. Source import paths, their complete selected transitive closure and file hashes are pinned at admission; changed hashes invalidate this result. A setup failure remains visible; there is no fallback to an unrelated raw-native probe.

**What PM-N2 cannot claim.** Directly invoking a candidate runtime module is **not** hostile ingress into a C-compiled ordinary Can fixture. It does not prove `createCodec` was instantiated by emitted C state, a generated `codec::encode_json` call occurred, any Can type/effect signature was admitted, the C artifact identity, R import integrity, or an R verdict. Registered N2 still requires a reviewed same-realm binding to an identified generated subject, an independent invocation witness, a separate identity-preserving case, and its listed fault/authentication controls. If that binding cannot be built, mark N2's integrated leg blocked while retaining this narrower source-module observation.
