## What the current compiler actually does

The current [project loader](../../../compiler/internal/project/graph.go) makes a dependency's **global key** its ID (`can.project.dependency/<key>`), rejects that key resolving to different directories, rejects two keys for one real directory, and keeps a graph-wide map keyed by short package name. A second `model` package fails before a file alias can disambiguate it. The [parser](../../../compiler/internal/syntax/declarations.go) accepts a bare package and optional alias in `uses`; the [resolver](../../../compiler/internal/resolve/symbols.go) looks that bare name up globally, then checks direct dependency and `internal` visibility. The [lock](../../../compiler/internal/project/lock.go) pins root-relative path and manifest/source/fixture digests by global dependency key. Application source currently writes `error <integer> name...`, with the number repeated in a project registry; graph/checker/runtime reject even a foreign retired-number overlap. [Nominal error matching](../../../compiler/internal/check/errors.go) and assertion comparison already use concrete type identity, while the [terminal reporter](../../../runtime/entry.ts) also emits a naked numeric `id`. None of the planned syntax or instance rules below currently compiles.

## Canonical ownership, instances and lock

Every project manifest, including the root, declares two canonical lowercase UUIDs: `project_id`, a persistent owner namespace, and `instance_id`, an independently minted instance **lineage** within that owner. Both use standard hyphenated UUID text; the owner mints them once and the loader rejects malformed spellings. The pair, called `ProjectInstance`, is the resolved project's canonical ID. A package ID is `(ProjectInstance, package_name)`; a declaration ID adds its declaration name. These IDs do not contain a dependency key, file-local alias, absolute directory, build order or source digest. Source paths remain logical paths relative to the owner for source maps. The catalogue retains its separate reserved namespace. The manifest replaces `error_registry` with `error_retirements`, a confined relative path to retirement-only JSON such as `{"retired":["model::obsolete"]}`; no active error list is authored twice.

`project_id` stays with one owner through its ordinary updates. `instance_id` stays with one logical dependency slot across compatible updates, so a source-only edit need not rename all its errors. To link two divergent revisions of that owner **at the same time**, the owner gives one a distinct `instance_id`; the two packages and errors are then nominally distinct. The same pair may be represented by different pinned snapshots in two archived builds, but one checked build may contain only one snapshot for that pair. Copying one project manifest unchanged into two divergent dependencies without changing an instance ID is an identity conflict, not a merge. A project can mint IDs without any cross-author name or numeric-error registry.

The planned root lock is a canonical graph snapshot with a root `ProjectInstance`, a table indexed by `ProjectInstance`, and each node's verified manifest/source/fixture/retirement digests, **source-derived active error names**, and direct edges. An edge records **its owner's** dependency key, its confined owner-relative path and the target `ProjectInstance`. The active names are a checked snapshot for update/retirement comparison, not a second authored allocation registry. The loader resolves paths with the existing symlink/confinement checks, reads the target's declared IDs, verifies all digests and target edges, and rejects missing, extra or stale pins. Multiple paths to the same `(project_id, instance_id)` must have identical checked node content and resolved target-edge table within that build; they intern to one graph node and one emitted module set. If the IDs match but bytes or edges differ, loading fails with both owner-relative paths. The same physical directory appearing under multiple direct keys may refer to one instance if all pins agree. Distinct instance IDs never merge merely because package names or contents match. Project dependency cycles remain invalid; source-package import cycles remain legal.

The graph table and emitted paths sort by canonical IDs and logical source paths. A lock-generated `buildId` is a SHA-256 digest of the canonical, sorted checked graph snapshot, with domain prefix `can-locked-build-v2\0`; its framed fields include the root, edges, owner-relative paths and content digests, but no absolute checkout path. The lock schema has a root instance ID and an `instances` table keyed by canonical pair; each node row has checked digests, derived active error names and a direct-edge table keyed by local dependency names. Moving a checkout with the same relative graph gives the same IDs and build ID. Renaming a dependency key while preserving its target keeps nominal package/error IDs but changes the edge table and may change `buildId`. Adding an unrelated node similarly may change `buildId` but cannot change existing declaration IDs. An instance edit may change the build ID and digest while preserving the lineage ID; the lock must be regenerated and checked. Every report names the exact build ID, and the archived lock/snapshot for that ID remains available to interpret its history. P8 must freeze exact JSON keys and field framing before implementing the parser and lock writer; these are semantic requirements rather than a claim that current `can.lock.json` already has such a table.

## Import resolution and visibility

The selected source form is:

```can
package app
    provides []
    uses [billing::model as bill_model, crm::model as crm_model]
```

For `dependency_key::package_name`, resolve `dependency_key` **only** in the manifest table of the importing file's owning project, then find `package_name` in that exact target `ProjectInstance`. The key must be a direct dependency; no recursive search, root-alias inheritance or graph-wide short-name fallback is allowed. Inside `billing`, its own `uses` resolves against `billing`'s dependency table. A bare `uses [model]` addresses a package in the current project; a bare reserved catalogue package addresses that catalogue package. It never searches dependencies. The optional `as` name is file-local and is the only qualifier subsequently used in types/expressions (`bill_model::invoice`); no three-part expression name is introduced. Two imports that would have the same local alias must be explicitly disambiguated. Duplicate import entries and alias collisions with local declarations or reserved names diagnose at their source spans.

The loader still rejects a project package that claims a catalogue-reserved name. A **dependency** import may not use a catalogue-reserved alias; a genuine catalogue import keeps its own reserved name. The resolver still requires `provides` for imported declarations and applies the `internal` directory rule using canonical resolved paths, not an alias. A direct dependency edge does not make that dependency's private symbols or its own dependencies visible to the importer. Unknown key, absent package, transitive-only package, reserved name, private declaration, forbidden `internal` package and mismatched lock target receive distinct located diagnostics identifying the written edge and resolved owner when known.

## Application error identity and reporting

An application declaration omits a number, for example `error payment_declined(str reason)`. Its exact qualified declaration key is `can.error.v2/<project_id>/<instance_id>/<package_name>/<declaration_name>`; UUIDs are normalized lowercase and package/declaration segments obey Can's identifier grammar, so `/` cannot occur inside a segment. A concrete error additionally includes the fully checked generic arguments. A concrete `failed<int>` and `failed<str>` share the declaration key but have distinct concrete `typeIdentity` values. Can's existing type graph already frames type constructors and arguments and hashes the framed value; P8 must version that framing with the new declaration IDs and keep collision detection. Checked matching, `emits` bounds, assertion equality, runtime admission and native adapter bindings use the concrete nominal identity, never a short name or report-only code.

An application `can.runtime-failure` report uses `schemaVersion: 2` and carries `buildId` (64 lowercase hex digits), explicit `errorKey`, concrete `typeIdentity`, `typeArguments` (ordered concrete identity strings), occurrence and diagnostic frames. `errorKey` is the full canonical declaration tuple, not the file-local `bill_model` spelling. Payload stays `<redacted>` and native causes are not exposed. The old naked application `id` field is removed; no compact number is planned. Catalogue-owned numeric metadata may remain for native adapters and can be reported only as separately identified catalogue metadata. The emitted error plan and runtime declaration table key application errors by qualified identity, verify unique declarations and concrete shapes, and no longer enforce global application integer uniqueness. This replaces, rather than maintains, numbered application source and the duplicated active allocation registry.

Each owner lineage maintains a sorted, unique **retired qualified declaration-name** ledger, scoped to `(project_id, instance_id)` and containing `package_name::declaration_name` entries in the manifest's `error_retirements` JSON file. The source's active errors are derived from declarations and cannot overlap its retired entries. A removed published declaration is added to this ledger; changing its name creates a new key and retires the old one. Foreign lineages' retired names never reserve a local name, even when they use the same short package/declaration. A separate lineage of the same publisher may use the short name because its full key differs. Owner metadata and each lock snapshot pin the retired set; updating a lineage from a known predecessor checks that the retired set only grows and that removed declarations are retired. Historical reports continue to point to their archived build/lock.

**First-release history decision:** validate active-versus-retired disjointness in the current checked snapshot and validate monotone retirement against every supplied predecessor lock in that lineage's archived chain. Archive each released lock/build artifact so its old reports remain interpretable. If a build is made from a checkout with discarded history, it can validate only the current snapshot and any predecessor artifacts actually supplied; it makes no claim about lost releases. No external owner registry or universal historical proof is required for the first release. A current `retired` array alone is never described as proof of all past non-reuse.

## Native JavaScript/Bun lowering

Import resolution is compile-time. The generated TypeScript imports checked exports from the target's deterministic instance-derived output module using native relative ESM `import` specifiers; local Can aliases become generated binding names. No runtime dependency-name resolver or duplicated package runtime is needed. The current [module emitter](../../../compiler/internal/emit/modules.go) already renders structured edges as relative ESM paths; the graph/emitter must supply distinct instance-derived paths and preserve one module per interned node. Source maps tie emitted modules to owner-relative source paths and the locked instance, never to a globally unique short name. Error creation/propagation uses the existing native JS call/exception or completion operations plus the minimal metadata adapters required for Can's nominal matching, provenance and redaction contracts; no application-wide integer allocator or custom import engine is emitted.

## Executable acceptance matrix for implementation planning

Use two independently authored libraries, each with `package model`, exported `failed<T>` and distinct `project_id`/`instance_id`, plus a root with direct `billing` and `crm` keys. Migrate their error declarations once to the new unnumbered grammar; **do not rewrite either library's package name or source merely to resolve the collision**. Build 1 pins root, both libraries and their edge tables. Build 2 starts from the same owner lineages, adds unrelated direct dependency `analytics`, and separately tests an alias edit and relocated checkout. Archive both lock snapshots and actual emitted report lines. A third fixture includes two simultaneously loaded lineages of one publisher.

| Case | Required positive or negative result |
| --- | --- |
| Duplicate short package names | Build 1 accepts both unchanged `model` packages; root `uses [billing::model as bill_model, crm::model as crm_model]` resolves two distinct symbols and emits two distinct native ESM targets. Editing only a file-local alias preserves both nominal IDs. |
| Direct versus transitive | `billing` may import its own direct `catalog::model`; root without a direct `catalog` key fails `uses [catalog::model]` with a located undeclared-direct-dependency diagnostic. Adding a real direct edge permits only its exported/public packages. |
| Local and catalogue namespaces | Bare local `uses [model]` resolves only root-local `model`; absent local package diagnoses rather than selecting a dependency. A project package claiming a reserved catalogue name, or a dependency import alias claiming one, fails. Genuine catalogue imports retain their reserved identity. |
| Visibility | Root importing an unprovided symbol or a forbidden `internal` package fails even when the direct dependency and lock are valid. A private package cannot be reached through another file-local alias. |
| Shared transitive instance | Two dependency paths to the same pinned `(project_id, instance_id)` and identical node/edge snapshot coalesce to one module and one nominal identity. The same pair with different bytes/edges in one graph fails and names both paths; distinct lineages with equal package names remain separate. |
| Lock and path integrity | Stale content digest, missing/extra node, mismatched edge target, dependency cycle, path traversal or escaping symlink fails before checking source imports. Relocation with identical relative graph reproduces the build ID and emitted paths. |
| Two build identities | Build 2's unrelated `analytics` edge, a dependency-key rename targeting the same instance, and a file-local alias edit leave `billing`/`crm` error keys and concrete identities unchanged. The graph/edge changes may alter build ID; each old/new report resolves through its archived lock. |
| Same publisher, two lineages | Two independently pinned revisions of one `project_id` with different `instance_id` values may coexist with `model::failed`; matching and report keys remain distinct. Giving divergent revisions the same instance ID in one graph fails instead of silently selecting one. |
| Independent errors and tombstones | Both libraries declare `failed<T>`; one retires `model::old`. Their identical short names and foreign retirement do not collide. Active/retired overlap inside one lineage fails; an update from a known predecessor that deletes a tombstone or removes an error without retiring it fails. |
| Generic exactness | Trigger `billing::model::failed<int>`, `billing::model::failed<str>` and `crm::model::failed<int>` (using resolved aliases in actual source). Reports have distinct concrete type identities; the first two share only their declaration key. Match, bound and assertion checks never merge them. |
| Rename and report archive | Rename `billing`'s `failed` declaration to `rejected`, retire `model::failed`, rebuild, then trigger `rejected`. Its key differs. Build 1's saved `failed` report still resolves under archived build 1 metadata, with redacted payload; reintroducing `failed` in that lineage diagnoses. |
| Error migration and runtime | Numbered application declarations and active-number registry entries fail under the new grammar/schema. The emitted application plan has no required numeric ID; runtime accepts two distinct owner-qualified errors regardless of old equal numeric allocations. Actual terminal JSON has explicit qualified `errorKey`, `buildId`, concrete identity and redacted payload. |

The matrix needs parser/resolver/graph/lock/checker/emitter/runtime/CLI and integration tests, including actual two-build report decoding. It is not satisfied by the current source inspection or by Jev agreement. Agent creation/refactor/repair cost, including total tokens per successful task, remains to be measured under the [evaluation protocol](evaluation-protocol.md).
