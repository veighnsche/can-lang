## Attached assertions, lexical fixtures, and cross-package ownership

An attached function assertion gets a root of `{package ID, declaration ID, assertion name}` and checks an actual invocation against its expected whole completion. A `when` table belongs to a checked lexical call site; its rows use assertion-name selectors. See [checker roots and tables](../../../compiler/internal/check/assertions.go#L13) and [emitted per-root modules](../../../compiler/internal/emit/program_entry.go#L12). The [selected assertion spelling](../decisions.md#assertions) retains named rows, exact positional arguments, and call-site `when` rather than a detached assertion registry.

At runtime, [fixture selection](../../../runtime/assert/fixtures.ts#L20) compares each row's selector to `contextReport(context).root.name`. With no selected row it runs the real call. With a row it checks actual arguments and either supplies the completion or, for a raw row, runs the target adapter and checks its result. The [P3 queue contract](../platform-testing-spec.md#p3-assertion-execution-model) uses one FIFO queue per root identity and lexical table, reservation paths for recursion/participants/callables, exact argument checking, and missing/unused/ambiguous diagnostics. The implementation has [root-local queue state](../../../runtime/assert/context.ts#L87), [path and participant identities](../../../runtime/assert/identity.ts#L67), and [no argument-search allocation](../../../runtime/assert/queue.ts#L66). A root's short name selects rows, but queue isolation uses its full identity; these are different roles.

The historical [original cross-package project](../evidence/2026-09-24/clean-room-full-review/cases/fixture-original/src/app/main.can) has `app::read_customer` assertion `customer`; [helper source](../evidence/2026-09-24/clean-room-full-review/cases/fixture-original/src/helper/main.can) has both `unit` and `customer` rows at `text::from_int(7)`. Renaming only the caller assertion to `renamed` in the [second project](../evidence/2026-09-24/clean-room-full-review/cases/fixture-renamed-root/src/app/main.can) leaves the helper unchanged. Both projects checked; [saved results](../evidence/2026-09-24/clean-room-full-review/probe-summary.json) show all three original roots pass, while the renamed caller root fails with outcome mismatch and the helper's own `unit` root still passes. The [review](../clean-room-language-review-2026-09-24.md#5-give-test-scenarios-explicit-ownership-across-calls) records the causal observation: the helper falls through to real `text::from_int(7)`, yielding `"7"` instead of fixture-supplied `"fixture"`. This is a refactoring-sensitive selector link, not a concurrent queue collision.

The current reusable [P3.1 template contract](../platform-testing-spec.md#p31-typed-fixture-reuse-with-local-ownership) defines inert, exact-target fixture content and in-place expansion at a lexical `when`. The implementation [substitutes definition rows under the use-site selector](../../../compiler/internal/check/templates.go#L194) and [retains the lexical table identity](../../../compiler/internal/check/assertions.go#L107). Thus a template reduces repeated fixture content but still needs a local selector; it does not give the caller explicit ownership of a helper's scenario. The [LD26–28 dispositions](../../implementation/language-design-dispositions-2026-09-22.md#assertions-resources-and-platform-contracts) retain attached roots, checked arguments and lexical identity, implement templates, and defer root-owned overrides pending evidence. The cross-package rename probe supplies the new evidence for a bounded re-evaluation. A whole-helper `when` stub is an existing unit-test idiom, but it bypasses the helper body on that path; compare this coverage loss with a lexical template before proposing new linkage.

## What assertions currently observe

The [assertion checker](../../../compiler/internal/check/assertions.go#L38) requires bare `ok` for excluded opaque or callable success results. The [runner](../../../runtime/assert/runner.ts#L120) accepts an opaque actual value against bare `ok` by completion kind and token presence; it does not compare response status, headers, HTML, resource contents, or downstream browser behavior. Plain records and errors use typed/nominal completion comparison. [P4 evidence labels](../platform-testing-spec.md#p4-real-execution-supplied-completions-and-provider-fixtures) separate `real-can`, `supplied-completion`, `raw-provider-fixture`, `policy-fixture`, `bun-conformance`, and `live-quality`; a supplied consumer result cannot claim adapter or target coverage.

The maintained [account-search rendering source](../../../examples/account-search/src/render/render.can#L6) uses bare `ok` for `html::safe` returns. Its [web handler](../../../examples/account-search/src/web/web.can#L20) has bare `ok` route assertions and returns a 503 feedback fragment for a down loader. The [SaaS review](../saas-language-review-2026-09-24.md#6-i-would-recommend-can-if-assertions-described-observable-product-behavior-more-naturally) identifies that default HTMX policy does not swap 503 responses; that is a source-verified policy interaction, not a new browser test. It is a useful acceptance case for observing status/body/headers and the actual target swap at the appropriate protocol/browser layer. Stronger observation should retain attached assertion gating and keep raw-provider and target conformance labels separate.

## Interfaces to other preparation topics

- **Package-controlled immutable values:** any owner boundary must specify how imports, public constructors, generic decoding, equality, matching, `with`, and assertion fixtures address owner identity. Current transparent records and catalogue-owned opaque tokens do not settle an application-owned value mechanism. [Gate 2](../can-recommendation-program-2026-09-24.md#gate-2--let-libraries-keep-their-promises).
- **Generic errors and diagnostics:** any scoped numeric/reporting identity must still bind source declarations, registry/lock snapshots, runtime failure plans, concrete specializations, and emitted diagnostics. Generic specializations currently share a declaration ID. [C9](../technical-spec.md#c9).
- **Product and browser evidence:** opaque success, raw adapter behavior, HTTP response bytes, and HTMX/browser mutation are distinct observations. The protocol/browser task should specify which layer owns each assertion and what a failed swap reports. [Gate 3](../can-recommendation-program-2026-09-24.md#gate-3--finish-one-server-driven-product-flow).
- **Tooling/build:** qualified imports and scenario links need resolver diagnostics/navigation, formatting, exact source spans, dependency lock digests, and assertion-gated publication; emitted root identities and source-map IDs currently include project-qualified IDs. [P15.1](../platform-testing-spec.md#p151-verified-build-and-publication).

## Open technical questions for the task list

1. What authored import reference unambiguously names one package in one direct dependency while retaining a short file-local alias and reserved catalogue identity? How are package names inside a dependency interpreted when two dependency subgraphs contain the same short name?
2. Which identity is canonical for an application error, which numeric value is stable for diagnostics, and which values belong in source, registry, lock, emitted plan, and external reports? What exactly happens when independent dependencies reuse a number or retire one?
3. How can a caller deliberately activate a helper's scenario across a call boundary without relying on equality of two unrelated assertion labels? Specify refactoring, nesting, recursion, concurrent participants, multiple helper invocations, collisions, and unused-link diagnostics while preserving exact arguments and FIFO queues.
4. What observation surface can assert HTTP/HTML details and browser-visible swaps from a Can-authored scenario while respecting opaque value admission and the separate evidence labels? What is the current best external protocol/browser check against which to measure it?
5. For each proposed change, what do two independent libraries and one caller actually require in authored files, changed files after a rename, diagnostics, and total tokens per successful agent task? Compare with the existing alias, lexical template, and whole-helper-stub idioms before selecting syntax.
