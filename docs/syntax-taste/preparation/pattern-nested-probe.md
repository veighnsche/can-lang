# Current-source nested pattern probe for DI-01

24 September 2026. This is a bounded observation of current Can, not a compiler
change or syntax decision. The executable cases are generated by
[run.py](probes/pattern-nested/run.py). They use compiler HEAD
`02a549d28fd5fc5c3996160e65a97de332390d30` and a fresh bundle built from
that source with the repository's pinned Bun archive. Projects, generated
TypeScript, and result JSON stay under `/private/tmp/can-pattern-nested-cases`;
the bundle stays under `/private/tmp/can-pattern-nested-bundle`.

To reproduce from the repository root:

```sh
go run ./tools/distbuild --archive .local-deps/bun-darwin-aarch64.zip --out /private/tmp/can-pattern-nested-bundle --version pattern-nested-probe
python3 docs/syntax-taste/preparation/probes/pattern-nested/run.py /private/tmp/can-pattern-nested-bundle/can-pattern-nested-probe-bun-1.4.2-darwin-arm64-v1/bin/canlc
```

The script writes each complete `main.can`, project manifest and empty error
registry to its own temporary project, then runs `canlc parse`, `build`, and
`assert`. All 13 cases parse. `build` verifies assertions, so a failed build can
mean a correct checker rejection **or** an assertion outcome mismatch; the
table distinguishes those. `assert` reports the same semantic failure or the
per-row results. No compiler tests or source were edited.

The current [parser](../../../compiler/internal/syntax/matches.go#L150) admits
name, constructor, array, wildcard, literal, range and alternative patterns,
including nested patterns and the rest binder. The
[checker](../../../compiler/internal/check/patterns.go#L57) tries an admitted
leaf at **each** name-pattern node when the expected type is a variant or
error. An unresolved unqualified bare name falls through to an `any` pattern
with a binding. A constructor pattern instead resolves a nominal declaration
and validates its fields. The [coverage check](../../../compiler/internal/check/completion_matches.go#L454)
then works from those interpreted patterns; it cannot infer that `paidd` was
intended as `paid`. The record and array cases show that an expected field or
element type can change the meaning of identical identifier text. This is the
nested boundary identified in the [core evidence](core-evidence.md#pattern-and-variant-identity)
and the [DI-01 comparison](core-alternatives.md#di-01--pattern-intent-and-typo-diagnostics).

The three alternatives in the fresh [Jev findings](jev-pattern/findings.md)
are **hypothetical**. This run did not implement or execute them:

| Semantic alternative | Consequence for these cases if implemented as stated |
| --- | --- |
| Explicit binding everywhere | Bare `paid`/`declined` remain resolved leaf tests at every depth, and `decliend`/`paidd` become errors, including final arms and nested fields/elements. The integer `paid` binder and `first` in `[first, ...rest]` require an explicit binding construct. An expected-type edit cannot turn a bare leaf test into a binder. The treatment of the already visibly marked `...rest` needs a precise rule. |
| Contextual variant rule | Unknown bare names fail at expected variant positions, including inside `payment[]` and `box`'s `payment` field. An explicit whole-value capture and `_` still provide intentional coverage. Bare names at nonvariant positions remain binders, preserving `[first, ...rest]` and the integer `paid` examples. Editing `box.item` or an array element between `payment` and `int` can still change a bare known leaf test into a binder; the reverse edit would make an unknown former binder an error. |
| Explicit both intents | Nominal leaf tests require constructor intent, and captures require separate explicit intent. The plain `paid`, `declined`, `decliend`, and `paidd` forms at variant positions would no longer serve as case tests or fallback binders. Constructor-shaped `decliend()` still fails; correctly named zero-field constructors would test leaves. Current scalar captures, including `first`, need explicit capture intent under the consultation's rule. `_` remains a discard/default pattern. |

All three would reject the final typo and nested variant typo while permitting
deliberate whole-value capture. They differ in refactor stability and how much
current source would have to change. These are semantic predictions from the
consulted contracts, not observed compiler diagnostics. The consultation's
three rankings disagreed and were diffuse; it did not run this probe. Current
Can has no authored explicit binding node to execute here, so this probe cannot
claim that any alternative's proposed capture or coverage behavior is already
parseable. It also does not measure agent repair, total-task tokens, generic
specializations, opaque leaves, or a held-out refactor trial under the
[evaluation protocol](evaluation-protocol.md). No syntax was selected.
