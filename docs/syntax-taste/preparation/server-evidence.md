This is preparation evidence for [Gate 3](../can-recommendation-program-2026-09-24.md#gate-3--finish-one-server-driven-product-flow), not a syntax choice or an implementation amendment. ## Authorization, tenant data and edit feasibility

No tenant, invoice, webhook or outbox application appears in the inspected `examples/` and `tests/integration/` Can sources. The [account-search example](../../../examples/account-search/src/web/web.can#L25-L62) shows query extraction, a SQL loader and response mapping, but it has no actor context or tenant predicate. The [cookie example](../../../examples/cookies/src/main.can#L108-L131) demonstrates token verification but does not resolve a principal or check resource ownership. This is a bounded inventory finding, not proof that no such code exists anywhere in the repository.

A representative invoice edit is feasible in current Can with a query-string resource key, shallow string/repeated form fields, explicit parsing/validation, named SQL descriptors and `with_transaction`. The transaction callback can check actor membership and invoice ownership at the protected operation, then update with tenant and invoice predicates and classify zero affected rows. The source does not prove that a separate pre-read stays valid during a concurrent update; the experiment must specify locking, optimistic revision or a predicate inside the write, and distinguish forbidden from missing according to the product's disclosure policy. Current `execute` cannot return the committed row in one `RETURNING` statement, so a read-after-write or a known-value response must be measured. A public nominal tenant ID or factory-created value cannot by itself prove a live actor has access to this invoice; the operation must recheck an authorization fact from server-controlled context.

The current form decoder discards wire details only after producing a typed record. Its output is still raw text, so a validation branch can retain those strings for re-rendering. This does not imply that the present signup example already retains invalid input: its 422 renderer returns a message fragment, not the original form ([signup handler](../../../examples/form-validation/src/web/web.can#L30-L47)). For invoice rows, the trial must define field paths and how repeated row columns stay aligned before conversion to domain values. Statuses for success, invalid form, conflict, forbidden and unavailable can be constructed with `http::make_body_status` and response builders per [P10](../platform-testing-spec.md#p10-http-request-response-routing-and-server-catalogue); their display under HTMX remains a separate contract.

## Signed webhook and outbox boundary

The available pieces are immutable bounded request bytes ([HTTP ingress](../../../runtime/platform/http.ts#L151-L204)), request headers/body ([P10](../platform-testing-spec.md#p10-http-request-response-routing-and-server-catalogue)), HMAC-SHA256 and Ed25519 verification ([crypto runtime](../../../runtime/platform/crypto/primitives.ts#L73-L102), [verify](../../../runtime/platform/crypto/primitives.ts#L210-L233)), static SQL descriptors and scoped transactions. The catalogue inventory contains byte encoding/decoding operations but no named constant-time byte comparison operation ([catalogue](../../../runtime/catalogue.ts#L4998-L5248)); this matters for an HMAC-header scheme and should be checked in a real provider adapter. Provider signature framing, timestamp tolerance, key rotation and replay identity are provider-specific contracts, not established by the primitives alone.

The flow needs a durable unique delivery/event identity, one transaction that records receipt and business mutation plus an outbox entry, and explicit handling of a repeated delivery. An outbox makes retries durable; it does not make external delivery exactly once. The controlled fault is external success followed by process failure before outbox acknowledgement. The receiver's idempotency contract, or a reconciliation/duplicate policy if absent, determines the promised business effect. `commit_unknown` identifies precisely the ambiguity that requires lookup by durable delivery identity before retrying ([transaction runtime](../../../runtime/platform/sql/transaction.ts#L231-L253)). These are experiment obligations; no current source test demonstrates them together.

## Bounded experiments for the final design task list

1. **Current-Can invoice baseline.** Use a real database and one actor with access to tenant A but not tenant B. Open an invoice, submit numeric seats, optional details and repeated line fields, then observe success, invalid input with retained values/field messages, stale revision conflict, forbidden cross-tenant identifier, and database unavailable. Record exact Can/manifest/renderer files touched and agent task tokens including diagnostics and repair. Keep the authorization check inside the protected read/write path, and inspect persisted rows after every response.
2. **Route, form and target drift.** Rename the route, one field and one fragment target separately. Record compile diagnostics, runtime test failures, and whether the same-typed or still-safe string silently reaches a different behavior. Compare a query-string baseline with a typed-capture resource URL trial; specify endpoint identity, path decoding, safe URL builder, form/action binding and response cases as one interface. A route builder must not claim target existence unless the renderer checks it.
3. **HTML and observable feedback.** Compare named helper components built with today's safe constructors against a checked declarative prototype using the same invoice page. Inject hostile text and 422/409/403/503 responses; assert status, headers, escaping, target swap/no-swap, focus and retained values. Decide UI behavior from observed DOM, not opaque response assertions. Do not infer a new syntax from helper call count alone.
4. **Transaction and signed-webhook faults.** Replay delivery IDs, inject failure before write, after ledger/outbox write, after native commit decision, after provider accepts an outbox attempt and before acknowledgement. Inspect unique ledger rows, invoice business effects, outbox state and provider requests. State whether the provider deduplicates by a stable key. Include one measured mutation that currently needs a read-after-write before considering bounded `RETURNING`; separately test wrong projection against a live versioned schema if compile-time database agreement is proposed.
5. **Domain library boundary.** Keep exact minor-unit arithmetic and half-even ratio rounding ([P14](../platform-testing-spec.md#p14-capability-reconciliation-matrix), [catalogue](../../../runtime/catalogue.ts#L4961-L4997)) plus zoned civil-time resolution ([runtime](../../../runtime/platform/datetime.ts#L216-L249)) as available primitives. A billing library/example must choose renewal, short-month, leap-year, DST, tax and refund policies. The invoice edit and webhook evidence does not select those product policies or justify language keywords.

## Cross-topic interfaces and remaining uncertainty

The browser/shared-contract work needs the server action's route identity, wire fields, response variants and authorization behavior; a future Can browser target cannot trust a client-held tenant ID. The core validated-value work needs explicit raw-form-to-domain conversion and package-owned construction, but must leave current authorization tied to operation and lifetime. Assertion/fixture work needs inspectable HTTP and DOM outcomes plus reusable provider/database scenarios; a source-level opaque `ok` cannot stand in for them. The SQL work needs to distinguish parser/cardinality checks, runtime row validation, and any separately versioned schema snapshot. The service-qualification work needs the same invoice and webhook slices under a named Linux distribution and host shutdown policy; the current target is Darwin ARM64 Bun ([distribution target](../../../distribution/target.json#L1-L12)).

Unverified here: no current invoice/webhook implementation, no 503 account-search browser reproduction, no end-to-end signed-provider replay/outbox test, no schema-snapshot comparison, and no agent token measurement for the proposed flow. The default Go cache path was sandbox-inaccessible; no product source or runtime file was changed.
