# Supporting capability alternatives

24 September 2026 · P4 candidate contracts for DI-17–23 · preparation, not an adopted design

This packet uses the [decision inventory](decision-inventory.md), [AI support](ai-support-evidence.md), [lifetime and deployment](lifetime-deployment-evidence.md), [core](core-evidence.md), [evaluation protocol](evaluation-protocol.md), and [constraints](constraints.md). It records no new probe, Jev consultation, syntax selection, or accept/retain/reject/defer disposition. Current decisions and the September 22 dispositions remain authoritative. The candidates below are bounded comparisons for later trials. There are no external users or compatibility duty for old syntax or generated layouts; accepted behavior and deliberate tests still need a reasoned revision.

Use the same creation, controlled edit, failure diagnosis, and repair task for the strongest present idiom and each candidate. Pre-register fixtures, model settings, repeats, and success thresholds. Correctness, explicit contracts, and safety are gates. Measure complete tokens per **successful agent task**, including instructions, source, diagnostics, tool output, and retries; human visual preference and source length alone do not decide. Compile operations to equivalent native JavaScript/Bun facilities where possible, adding only the adapters needed for Can contracts, resource ownership, and immutability. The platform target must be named and qualified separately.

## DI-17 — Native AI composition

### DI-17a: wrapper recovery provenance

**Strongest present idiom.** Keep `llm` typed generation and use a named ordinary wrapper with explicit `emits` and match/forward arms for each failure. Fetch/judge `wrap` already distinguishes `handles native` from `handles emitted`; an ordinary LLM wrapper cannot distinguish authored from decoder-origin failures of the same nominal kind. The [native AI example](../../../examples/native-ai/src/oracles/oracles.can) demonstrates ordinary forwarding, not a measured failure.

**Bounded alternatives.** (1) Share named ordinary forwarding/recovery helpers where provenance is unnecessary; retain explicit branches when it matters. This changes library code, not error identity. (2) Extend the existing native `wrap` policy specifically to LLM calls, carrying private origin metadata into the wrapper while preserving the public finite error bound. Define whether request, decode, validation, and authored handler failures are eligible for each recovery arm, and forbid recovery from a failure outside the declared policy. Do not infer public errors or merge LLM and judge kinds.

**Discriminator and lowering.** In one generated-record workflow, inject an authored and a decoder failure with the same nominal kind. Assert which recovery runs, the outward error bound, one intended request per attempt, and no replay of a completed external effect. Give agents a recovery-policy edit and measure wrong recovery, compile/repair turns, and complete task tokens. Native LLM calls remain the current Bun-backed request path; the extension needs a small origin-tag/policy adapter at that boundary, not a Can-level LLM engine. No syntax choice is needed to test ordinary wrappers; an LLM `wrap` extension would require a later syntax and contract choice. Retain ordinary wrappers if the workflow remains correct and cheap to edit; defer the extension until provenance causes a reproducible error or material agent cost.

### DI-17b: judge batch handler effects

**Strongest present idiom.** One judge batch prepares registrations, makes one request, validates every response, runs handlers in source order, then constructs the returned result and continues. Put any required atomic writes inside an explicit transaction or outbox. A later handler failure does not undo an earlier external effect ([A7 contract](../ai-io-spec.md#a7-judge-execution-phases-and-the-batch-boundary)).

**Bounded alternatives.** (1) Make the phase and partial-effect rule precise in documentation, diagnostics, and a controlled example, without changing semantics. (2) Use a transaction around compatible database effects, with explicit handling for rollback and uncertain commit; external provider calls remain outside that atomic claim. (3) Stage effect intentions in an outbox and apply them with idempotency after the validated batch, stating delivery and replay semantics. These are workflow choices, not automatic rollback of arbitrary handlers.

**Discriminator and lowering.** Make handler one write to a controlled ledger and handler two fail. Verify one batched native request, full answer validation before any handler, ordering, exact ledger state, explicit error propagation, and no implicit replay. Then inject rollback, duplicate delivery, and uncertain commit in the transaction/outbox candidates. Keep the existing native batch and validation adapters; transactions use native database transaction operations, and outbox dispatch uses admitted native I/O. No new language syntax is required for these alternatives. Retain current batching if explicit transaction/outbox code meets the product contract and agents understand the phase rule; reopen semantics only for a demonstrated workflow that cannot be expressed safely.

### DI-17c: grouped-state callable composition

**Strongest present idiom.** Named functions adapt direct judge/LLM grouped inputs to ordinary callable references. Group boundaries and explicit state disclosure survive; the [callable gate](../../../compiler/internal/check/callables.go#L13) currently excludes direct judge/LLM references and judge wrappers with grouped state. Adapter repetition in one example is evidence of work, not yet evidence of material task cost.

**Bounded alternatives.** (1) Use a named adapter per state contract, optionally taking an explicit context record so dynamic fan-out sees an ordinary callable with a written error bound. (2) Introduce a narrowly typed reference to a grouped-state native declaration, preserving group identity and explicit connection identity through reference creation, capture, invocation, fixtures, and diagnostics. No flattened state record, merged native kind, inferred errors, or general higher-order effect system follows.

**Discriminator and lowering.** Fan out over several judges with two state groups, including one-field and multiple-field groups; rename a group field and a connection, and inject a domain failure. Check disclosed fields, request count, capture-once behavior, fixture selection, error bounds, and agent repair. Named adapters call the existing native judge/LLM path. A direct reference would lower to a closure over the same path plus a checked group/connection descriptor; it must not copy state into a broad ambient object. A new callable spelling and type rule require later syntax selection. Retain adapters if they pass the fan-out and edit trial; keep direct grouped callables deferred under LD06 until a reproducible cost remains.

## DI-18 — Scoped results and race fault visibility

### DI-18a: a result containing an expired scoped resource

**Strongest present idiom.** Return durable data from a scoped operation and use the scoped transaction or reader only within its live owner. A returned own token is rejected at use by the runtime before native work; returning an enclosing live pool can be valid. Runtime ownership/leases remain the safety boundary ([lifetime evidence](lifetime-deployment-evidence.md#scoped-resources-and-transactions)).

**Bounded alternatives.** (1) Improve the runtime `resource_state` diagnostic with creation/close/use context while retaining the existing guard. (2) Add a narrow checker diagnostic for a syntactically obvious escape of the scope's own handle through a direct return or a known record/variant field. It must distinguish an enclosing-owned resource and avoid claiming to prove arbitrary captures or aliases. A general borrow checker or a blanket resource-valued result ban is outside this trial.

**Discriminator and lowering.** Return the own handle directly, inside an aggregate, and through a closure; separately return an enclosing live pool. Assert checker behavior, the pre-native runtime guard, legitimate pool use, and agent repair from each diagnostic. Runtime checks stay at the native-resource adapter and owner lease boundary. A static check changes no generated operation; a better diagnostic only carries provenance metadata. No syntax choice is needed. Retain runtime enforcement if it diagnoses and repairs the practical cases; defer static analysis unless the bounded rule catches useful escapes without rejecting legitimate returns or promising unsound coverage.

### DI-18b / DI-15c: first-success race fault observation

**Strongest present idiom.** Use first-success `race` for intentional fallback, with native `Promise.any` winner selection. Pre-winner failures are consumed; late standard failures are diagnosed. If every failure matters, explicitly observe each candidate or choose a different coordination shape. Dynamic empty and pending cases retain their selected semantics ([coordination evidence](lifetime-deployment-evidence.md#races-fault-observation-and-drain)). This is one design question shared with DI-15c.

**Bounded alternatives.** (1) Add service-level observation around each participant, recording a classified failure before letting the original race settle; keep reporting policy in application code. (2) Add an opt-in race observation policy that reports consumed failures to a diagnostic sink while preserving winner, pending, lease, and error semantics. Specify whether domain failures and standard failures are included, diagnostic identity, order, timing, redaction, and sink failure behavior. Neither option cancels losers or changes `Promise.any` selection.

**Discriminator and lowering.** In a replica/fallback service, test zero, one, and many dynamic participants; early winner; expected and accidental pre-winner failures; late standard failure; pending loser; and close deadline. Count useful diagnoses versus routine noise and verify no duplicate/missing fault, no altered winner, and unchanged root drain. A policy adapter can attach handlers to native participant promises and emit diagnostics; it must not consume work that previously held a lease or make a pending promise settle. Application observation needs no syntax; an opt-in language policy would require a later surface choice. Retain current behavior when explicit service observation suffices, and defer a general mode until the controlled fallback shows a material diagnostic gain.

## DI-19 — Controlled catalogue and external SDKs

**Strongest present idiom.** Integrate a concrete payment, email, or queue provider through admitted typed HTTP, crypto, codecs, and process operations. Keep authentication, idempotency, pagination, timeouts, signature verification, immutable results, finite errors, and deterministic raw fixtures in a named package. No reviewed required SDK has yet been shown impossible through this path ([AI support evidence](ai-support-evidence.md#closed-catalogue-and-sdk-integration-di-19)). Arbitrary JavaScript/Bun imports remain outside the source contract.

**Bounded alternatives.** (1) Keep the protocol package and improve only missing typed catalogue primitives, if a specific primitive is demonstrated absent. (2) Admit a narrow distribution-owned provider adapter with reviewed signatures, codecs, fixtures, errors, ownership, abort behavior, and redacted diagnostics. (3) Revisit a third-party binding manifest only after a named SDK feature is materially impractical through the first two paths; require the same admission and deterministic test contract, rather than general npm access.

**Discriminator and lowering.** Build the smallest useful provider operation for the invoice/webhook flow and test successful/failed authentication, duplicate idempotency keys or events, malformed payloads, provider drift, timeouts, redaction, immutable output, resource cleanup, and fixture determinism. Compare agent integration and provider-change repair against the HTTP baseline. Lower HTTP to native `fetch`/Bun facilities, crypto to native crypto, process work to admitted native process operations, and an admitted SDK call to the actual native SDK with only contract adapters. There is no syntax choice for a protocol package or catalogue addition; a manifest would need its own later syntax and authority decision. Retain the closed boundary unless a reproduced integration shortfall remains; defer manifests until that evidence names the operation and its costs.

## DI-20 — Bulk immutable collection construction

**Strongest present idiom.** Fold with immutable `collections::map` insert/replace and set add. Each update clones a native collection, so mostly unique map insertion has a quadratic copying implication; throughput has not been measured. Existing opaque values remain immutable to Can callers ([AI support evidence](ai-support-evidence.md#bulk-immutable-collections-di-20)).

**Bounded alternatives.** (1) Add specific bulk grouping/aggregation operations that build a native `Map`/`Set` once, then publish one immutable Can value. Define duplicate key rule, key equality, first insertion order, callback evaluation order, callback failures, and whether intermediate groups are observable. (2) If those operations cannot express the measured workload, trial an internal scoped builder whose mutable native value never escapes, is invalid after publication, and has a single immutable output. Avoid general mutable aliases and a bespoke persistent map engine in this comparison.

**Discriminator and lowering.** Benchmark duplicate-heavy and mostly-unique realistic sizes, including a word count, callback domain failure at a middle element, duplicate insertion order, alias attempts, and a failed build. Check exact results and error timing before comparing time/allocation and successful agent-task tokens. Native bulk construction should use `Map`/`Set` and array iteration once; the wrapper must freeze or encapsulate the published value so native mutators cannot leak. A scoped builder likewise uses native mutation internally with owner-like invalidation. A new bulk API needs signature design but need not add grammar; a builder may need an API or bounded scope form selected later. Retain folds while the workload is small or the speedup unproven; defer additions until actual Gate 3/4 data volumes and a measured benefit justify them.

## DI-21 — Billing, calendar, and domain-library boundary

**Strongest present idiom.** Represent money in exact minor-unit `int`; use `number::round_ratio_half_even` and `time::resolve_zoned_time` with explicit civil-time and DST policy. Implement renewal, tax, proration, refund, and provider-event idempotency in an ordinary domain package. Current primitives exist, but no maintained end-to-end subscription example qualifies them ([AI support evidence](ai-support-evidence.md#billing-and-calendar-library-versus-language-di-21)).

**Bounded alternatives.** (1) Build and maintain a policy-explicit billing/calendar library on existing primitives, with nominal domain types and finite errors where useful. (2) If the library reveals a missing exact arithmetic or civil-time primitive, add that one operation to the controlled native catalogue with a precise contract and fixtures. (3) Where provider protocol handling dominates, keep it in the DI-19 integration package, separating provider event interpretation from tax or proration policy. These options do not imply billing, queue, or auth keywords.

**Discriminator and lowering.** Test short months and leap years; DST gaps and overlaps under stated policy; zero-, two-, and three-decimal currencies; half-even boundaries; taxes; partial refunds; duplicate provider events; and uncertain commit in the invoice/webhook scenario. Assert exact minor units, chosen instants, idempotent ledger state, and agent repair after a policy edit. Use native `BigInt`/number and `Date`/time facilities only where they preserve the declared exactness and zone contract; retain the existing catalogue adapters for rounding and zoned resolution. Library work needs no syntax choice. A missing primitive needs a catalogue contract, not grammar by default. Retain the language boundary if the domain library passes; defer any platform addition until a specific primitive gap is reproduced.

## DI-22 — Named-field construction and reorder safety

**Strongest present idiom.** Positional record construction follows declaration order; use strongly distinct domain types where semantics warrant them, named factory functions for frequently edited records, and `with` for named replacement. Adjacent `int total` and `int recent` in the [native AI example](../../../examples/native-ai/src/records/records.can) illustrate a same-typed reorder hazard, but no controlled production misbinding has been executed ([core evidence](core-evidence.md#captures-and-construction)).

**Bounded alternatives.** (1) Keep positional construction and strengthen domain types or factories in the invoice/report slice; a factory that merely forwards two same-typed inputs does not itself remove the hazard. (2) Add a named-field construction form checked against the nominal record declaration, with exact duplicate/missing/unknown-field diagnostics and a stated evaluation order. Decide separately whether partial construction/defaults are allowed; they are not implied by names. (3) A tooling-only option can diagnose suspicious same-typed reorder diffs or offer a checked constructor rewrite, but must be measured for false positives and missed edits.

**Discriminator and lowering.** Reorder same-typed fields and uses across a realistic project, then add and rename a field. Require correct record values or a precise diagnostic, preserve evaluation order and immutable nominal identity, and count silent behavior changes and agent repair tokens. Named construction can lower to the existing native frozen record operation after compile-time field ordering; no runtime name lookup or generic object spread is needed. The language form requires later exact syntax selection; stronger types, factories, and tooling do not. Retain positional construction if the agent trial shows reliable edits with baseline measures; reopen a named form only for a reproducible correctness or material repair benefit.

## DI-23 — Agent authoring surface

### DI-23a: multiline layout, formatter, and diagnostics

**Strongest present idiom.** Keep one physical line for calls, constructors, and assertion rows; factor long expressions into named functions or records, and use the existing parser renderer and diagnostics. The review's 154 example lines over 120 characters and 336-character maximum describe presentation, not agent failure. Precise diagnostic spans and a comment-preserving canonical formatter are already accepted work under LD44–LD45; multiline forms remain deferred under LD46 ([AI support evidence](ai-support-evidence.md#authoring-surface-retained-for-agent-measurement-di-23ab)).

**Bounded alternatives.** (1) Complete formatter and diagnostic improvements, plus builder/refactor helpers, while retaining current grammar. (2) If repair still fails on long forms, allow continuation only inside explicit delimiters, retaining block indentation and attached assertion-row semantics. Specify where newline is whitespace versus a row terminator, comments, trailing separators, nested forms, formatter idempotence, and error recovery. A broad indentation rewrite is outside this trial.

**Discriminator and lowering.** Give agents long calls, constructors, and assertions for creation and controlled edits after formatter/diagnostic work. Test parse/format/parse stability with comments; exact spans for missing delimiters and swapped arguments; assertion attachment; first-pass validity; repair turns; and complete task tokens. Layout is erased by parsing and should not change native lowering. Formatter/tooling needs no grammar selection; delimiter continuation needs a later consistent syntax choice. Retain one-line forms if improved tools meet the agent task threshold; defer multiline grammar while measured pressure is absent or ambiguous.

### DI-23b: unnecessary-local validity rule

**Strongest present idiom.** Inline a narrowly defined immediately forwarded local to satisfy today's checker, or introduce a named helper where a domain step is reused. The checker rejects some semantically meaningful names such as `permitted`; no agent failure cost has been measured ([local checker](../../../compiler/internal/check/locals.go#L41)).

**Bounded alternatives.** (1) Retain the rejection but improve its diagnostic and safe automated inline fix, including source-span precision. (2) Allow the local and report an advisory lint/formatter suggestion, with an option to keep meaningful intermediate names. (3) Limit hard rejection to a demonstrated semantic ambiguity, if one exists, while treating pure style cases as advice; this requires an exact rule and negative examples, not a blanket exemption.

**Discriminator and lowering.** Compare agents adding and refactoring a meaningful `permitted` step, an accidental redundant alias, and a local used for later debugging or branching. Verify unchanged runtime result and error behavior, valid build and repair counts, and complete task tokens. An allowed local can lower to the ordinary generated TypeScript `const` or be safely optimized without changing evaluation count; lint has no runtime effect. No new syntax is needed, but validity and diagnostic policy need a later decision. Retain the hard rule if it prevents measured agent mistakes; move it to advice only if semantic tests remain stable and agent completion improves.

## Shared disposition boundary

DI-17 depends on stable error and package identity, fixture ownership, and native AI state contracts. DI-18 shares service qualification with DI-15. DI-19/21 should use the same concrete invoice/webhook provider and database failure fixtures. DI-20 needs observed collection volumes. DI-22/23 should be evaluated on the same controlled agent edits as the product flow. Each topic eventually needs a recorded accept, retain, reject, or defer reason and a reopening condition; this packet supplies alternatives and acceptance discriminators, not those dispositions. Difficult design choices then receive the three fresh, fully reworded Jev consultations required by `AGENTS.md`, with saved requests/responses and disagreement review, before a final choice is treated as supported.
