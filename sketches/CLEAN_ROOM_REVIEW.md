# Clean-Room Review: can-lang sketches (01–05 + README)

> Status note: design-input record, not a live spec — do not edit the
> review below. Its cuts (`reach`, spec layer, flat error numbers) were
> adopted; the v0.5 plan (`docs/a/a05-expressiveness.md`) and the a06–a09
> builds answer the gaps it left open. Line citations refer to the 01–05
> sketches as read.

## Summary

The sketches propose a coherent bet: **an AI-first language where every function is a self-describing, compile-time-tested, exhaustively-handled unit** — stable error numbers (`E1042`), strict `domain__verb__vN` naming, `mod ... provides/uses/emits` headers, inline `tests` + `reach` coverage markers, `extern` stubs with exhaustive `on`/`match` arms, and a plain-text Given-When-Then `spec` layer for retrieval, all tree-shaken by `ai build --prod`.

Progression across files is legible: 01 (outside `expect` blocks, Zig-style) → 02 (tests moved into signature + `reach` routing) → 03 (externals + stubs, intentionally uncompilable) → 04 (pure-expression `match`-only rewrite, fixed) → 05 (text `spec` layer on top). The direction is consistent and each step fixes the prior file's stated gap.

But the design as sketched does not scale. Demonstrated on a 30-line pure function with 3–5 branches, it already exhibits ~1:1 test-to-code bloat (05: ~28 lines of spec + ~30 lines of tests + ~25 lines of body for trivial login logic). Extrapolated to real code with loops, time, retries, and dozens of externals, the ceremony collapses under its own weight. Three of the core mechanisms (`reach` routing, spec↔tests 1:1 linkage, global stable error numbers) are the highest-risk parts and should be cut or radically simplified before v0.1.

## Strengths

1. **Stable error numbers + `emits` unions are the best idea here.** `error E1042 auth.login_failed` (01:9, README:8) plus `emits E1042, E1043` on both module (01:7) and function (01:23) gives grep-stable, rename-proof error identity. This is genuinely AI-friendly: an agent can search `E1043` instead of guessing string variants. Protobuf analogy in README:8 is apt.
2. **Exhaustive externals handling is sound.** 03:84-91 rules — every `call db__get_user__v1` must handle all declared emits with `on` branches, no catch-all; stubs can't invent outcomes — is the correct answer to "how do you test IO at compile time." The 03→04 fix (adding the missing `locked` stub, 04:43-48) demonstrates the mechanism catching a real gap.
3. **Functional match-only bodies (04) are a real improvement over 01–03's statements.** 04:90-97 comment is right: errors-as-values + syntactic exhaustiveness (3 DB arms × 2 locked arms × 2 pw arms) makes missing paths a parse error rather than a coverage subtlety. No early `return`/`raise` hiding paths.
4. **`mod` self-description header is cheap and useful.** `mod auth provides [...] uses [...] emits [...]` (e.g. 05:6) gives a dependency/error manifest parseable without reading the body. Low ceremony, high retrieval value.
5. **Compile-time execution + prod stripping is the right lifecycle.** Zig/D-style `expect` (README:10, 01:38-51) run at build, fail the build, strip to zero bytes in prod. Correct default: tests as build gates, not shipped artifacts.

## Risks

1. **`reach` markers don't scale and contradict exhaustiveness.** 02's rules (02:47-52) require each case to hit *exactly its own* marker and every marker to be hit. 04/05 then claim exhaustiveness is *syntactic* (04:94-95: "Delete one [arm] and it doesn't compile") — if match is already exhaustive, `reach` is redundant bookkeeping. Worse, it conflates two different things: *which arm ran* (control flow) with *which test case ran* (input identity). Real functions have N×M path combinations (03 already needs `locked × db_ok` vs `locked × db_down` ordering decisions the sketches never discuss). Requiring one named marker per arm forces a combinatorial naming burden and brittle 1:1 test↔arm coupling. A single refactor (splitting an arm) breaks every test name.
2. **Global stable error numbers will merge-conflict and ossify.** "Never reused" (README:8) with a flat `E####` namespace means every new error needs a globally unique number. No sketch shows who allocates numbers, what happens on collision, or how two agents working in parallel avoid picking `E1044`. Protobuf solves this with per-file ranges and a registry; can-lang has neither. Expect number-squatting, renumber churn, and `emits` lists rotting out of sync with bodies (nothing checks `mod emits` ⊇ union of `fn emits` — compare 03:6 vs 03:31).
3. **Spec↔tests 1:1 linkage guarantees spec drift, not prevents it.** 05:121-122 requires every `spec case` to have exactly one `tests` entry and vice versa. But the spec is free text ("max 1 line each", 05:122) with no executable content, while tests carry args/externals/expected values (05:60-91). Any behavior change now requires three synchronized edits (spec text, test table, body arm) or the build fails. In practice the text rots first — note 05's own spec already diverges: `bad_pw` spec (05:37-40) omits `failed_attempts: 0`, which is load-bearing in the test (05:70). The compiler cannot catch that omission because the text is "indexed, not executed" (05:124). Triple-maintenance for zero execution benefit.
4. **Context-blowup claim is inverted.** 05's retrieval contract (05:125-127: "agent may stop reading after spec") assumes the spec suffices for relevance judgments. But 05's spec is ~26 lines and the test table it abstracts is ~30 lines — savings are nil on small files and negative on large ones (spec + tests + body ≈ 3× the logic). The "first 40 lines hold types + spec only" (05:125) is already false in 05 itself: `mod` at line 6, spec ends line 56, function body starts 58 — an agent stopping at line 40 sees half a spec and no signature. The layout contract is asserted, not demonstrated.
5. **Human cruelty vs AI benefit is unpriced.** Strict `Auth__User__v1` / `auth__login__v6` naming (README:9), per-arm `reach` lines, per-test `externals` maps repeating identical stubs (05:63-65 vs 05:69-71 — same stub twice), and version-suffixed everything (`__v1`…`__v6` across five files for one function) are all justified as "AI-friendly" but every one is written and maintained by humans (or by agents making human-reviewable diffs). Version-bump semantics are entirely undefined: when does `v5`→`v6` happen, and must all callers update? The sketches show six versions of one function with no migration story.
6. **Determinism of externals is hand-waved.** 03:87-89 says "the real extern never runs, each test replays only its declared map." Fine for a single-call function. Unspecified: multiple calls to the same extern with different args in one execution, repeated calls with the same args (sequences vs single stub), stateful externals (counter, clock), and what `call` does outside tests (blocking? async? effectful?). The "next sketches" (README:30-31, ratelimit with time mocks) name exactly the case that breaks the single-stub-map model.
7. **Versioning + naming grammar will fight the type system.** `type Auth__User__v1` shared identically across 01–05 while functions rev `v2`→`v6` implies types version independently — but no rule says when a type must rev, whether `v1` and `v2` types interoperate, or what `uses [db__get_user__v1]` means when the DB revs to `v2`. Strict naming without a version-resolution rule is just mandatory renaming.

## Gaps (what blocks v0.1)

1. **Grammar ambiguities.** `tests { name: { ... } => Expected, ... }` trailing-comma rules, `Ok {...}` vs `E1042 {...}` value syntax, `match X { Pat var => ... }` binding form (04:72 `Ok user =>` vs 04:64 `E2001 _ =>`), `=` after signature starting an expression body (04:62, 05:92) vs `{ }` statement bodies (01:24, 03:58), `let x = call f(a) on E => {...}` chaining (03:59-67) — none has a grammar. `given/when/then/and` line limits ("max 1 line each", 05:122) and allowed content (quoted literals? E-codes only?) are prose, not productions.
2. **Undefined `match` semantics.** Is match on (value, error) pairs or a Result type? What does a non-exhaustive match do — 04 claims compile error but 02/03 implement coverage via `reach`, a different mechanism. Are boolean matches (`match user.failed_attempts >= 3 { true => ... }`, 04:72) the only condition form? No guards, no nested patterns, no wildcard arm shown. Operator set (`>=`, `==`, `!=`) and short-circuiting undefined.
3. **Undefined `reach` semantics.** Is `reach` a statement (02:36, 03:61) or an expression-prefix (04:65)? Does it affect runtime (no — stripped, 02:51) — so how does the compiler observe "execution must hit exactly its own marker" (02:49)? Via interpretation, symbolic execution, or instrumented test run? What is "exactly" for arms hit twice, loops, early exits? What error is reported on mismatch?
4. **Undefined test-execution model.** "Pure sandbox during build" (01:35), "executed at compile time" (02:48) — with what evaluator? What subset of the language is allowed in tests (`mock`, `call ... =>`, struct literals)? Are tests hermetic (no extern calls except stubbed)? Timeouts, nondeterminism, floating point, ordering of cases — all unspecified. `mock user = ...` (01:39) vs inline `user: {...}` (02:25) are two syntaxes for the same thing with no stated equivalence.
5. **Undefined externals semantics.** What is `extern fn` at runtime — FFI, RPC, capability? Who implements `db__get_user__v1`, in what language, and how is its real `emits` set checked against the declaration? Can externs take callbacks, return iterators, raise undeclared errors? Multi-call/sequential-stub behavior unspecified (see Risk 6). No story for effect ordering when body calls two different externs.
6. **Undefined `spec` semantics.** 05:121-128 gives four "compiler rules" but only rule 1 is checkable (name-set equality). Rules 2–3 (indexing, "first 40 lines", `ai grep-spec`) describe tooling that doesn't exist. No rule links spec *content* to test *content*, so the layer is unverifiable prose by construction.
7. **Effect system gaps.** No `mut`/ownership story (`failed_attempts` increment, the actual point of a login counter, never appears — sketches only *read* it). No async, no iteration, no error-payload typing beyond inline struct literals, no story for `mod uses` transitivity (if `auth` uses `db`, must callers of `auth` declare it?). `mod emits` vs `fn emits` relationship unchecked.
8. **Prod-strip semantics undefined.** "Strips them to 0 bytes" (01:36), "removes tests/externals/reach" (03:91, 05:128) — is stripping textual or IR-level? Do stripped `reach` lines leave empty blocks (04:64-67 arms would be `{ E1042 {...} }` — fine) vs statement positions (02:36 `reach locked` before `raise` — leaves a hole)? Is stripped output still verifiable against the same `emits` contract?

## Recommendations (cut or simplify)

1. **Cut `reach` markers entirely; keep exhaustive `match` + result-asserting tests.** 04 already proves `reach` is unnecessary: if every arm is syntactically required (04:94-95), then tests asserting input→output pairs per case give full branch coverage without naming arms. Deleting `reach` removes ~1 line per arm, the whole "exactly its own marker" semantics hole (Gap 3), and the test↔arm rename brittleness (Risk 1). Coverage, if wanted later, belongs in tooling output (`ai cover`), not in the language.
2. **Cut the Given-When-Then `spec` layer from v0.1; keep `mod` header + test names as the retrieval surface.** The spec duplicates the test table in unverifiable prose at ~1:1 cost (05:31-56 vs 05:60-91) with a false 1:1 sync guarantee that triples edit burden (Risk 3). For v0.1, index what's already formal: `mod` line, `fn` signature + `emits`, and test-case names. Revisit a text layer only when there's a demonstrated retrieval failure that names-alone can't fix — the sketches assert this failure but never show it.
3. **Cut global flat error numbers; scope them per module or derive them.** Replace `error E1042 auth.login_failed` + "never reused" registry with either `error auth.login_failed` (compiler assigns a stable hash/number at build, recorded in a lockfile) or per-module ranges (`auth` owns E1000–E1999). This keeps the grep-stability win (Strength 1) while eliminating the parallel-allocation collision problem (Risk 2) and the "who owns E1044" process hole. A v0.1 without a number registry is implementable; a v0.1 with a global never-reuse namespace and no registry is not.
