# X-R07-1: owner-value factory experiment

Task B02. Source: R07, F-R07-01/03, LD29 closed gate; contract C-B;
acceptance W3-owner. Same environment and harness as X-R06-1.
No invoice-owned file was touched: the extraction uses its own
`ids`/`handler` packages, so no lane-C patch exists.

## Question

Can the private fixture-factory pattern (F-R07-02) carry a real
handler→helper extraction over owner values with minimal setup
plumbing and retained useful tests — or is factory cost/failure
excessive enough to reopen LD29 for setup-region syntax (Q4)?

## The extraction

Baseline (`f41fba6b`, 8 roots green): `handle_tier` parses raw scores
and maps tiers inline, leaking `ids::invalid` in its bound.

End-state (`99012e88`, 14 roots green): the tier mapping is extracted
into `tier_for(ids::user_id) emits []`; the handler parses once and
relays; `fixture_id` feeds owner values to rows. Extraction delta in
`handler.can`: +48/−9 lines.

Setup plumbing per factory, measured: `fixture_id` 9 code lines
(signature, self-row, match, trap arm, forward arm). The two trap
specification probes (14 code lines) prove the idiom once; they are
not per-factory marginal cost after this experiment. Per distinct
owner input shape the marginal setup is one factory plus one self-row.

## Evidence chain (no forged values, no bypassed assertions)

- Owner package keeps literal roots (`parse` good/bad, `value` good).
- Factory self-row executes the success path
  (`unit: 1 => ok call fixture_id(1)`).
- Consumer projection roots verify through the helper
  (`tier_for` gold/silver/bronze via `call fixture_id(n)`).
- `provides` excludes the factory and probes; a foreign package
  calling `handler::fixture_id` rejects at check with
  `handler::fixture_id is private` (`TestFactoryPrivateToPackage`).
- A row forging `ids::user_id(7)` rejects at check with
  `owner record ids::user_id can only be constructed in its declaring
  package` (`TestOwnerForgeRejected`).

## Failure-path evidence

- Kind/message probes (positive roots): unexpected rejection surfaces
  as `kind == "arithmetic"`,
  `message == "arithmetic: integer division by zero"` — the fixed
  template, not an smuggled reason string.
- Tainted row (`call fixture_id(0)` as a consumer input, separate
  negative project): suite fails closed, exit 1; only the tainted root
  fails; frames locate the trap span (`handler/handler.can`, trap
  line, `binary` operation) plus the tainted input site (`call`).
  All 14 other roots pass, proving containment
  (`TestOwnerNegativeFailsClosed`).

## Repair evidence (constructor evolution)

Surgery adds `ids::retired` for raw scores above 100 (full diff
reproducible via `CONV_DUMP_SURGERY`, `owner-repair` entry):

- Without the factory arm the check fails guided:
  `missing completion arm for ids::retired;
  can.project.root/ids::parse requires an arm for each bound member`.
- With it: 16 roots green. Owner package +8/−3 lines (decl, bound,
  rule, root); handler +4/−1 (factory arm, handler bound/arm/root).
- The extracted `tier_for` is byte-identical before and after
  (`TestFactoryRepairGuided`): constructor change touches the factory
  (+1 arm line) and the handler contract, never the helper or its
  rows. The extraction pays off exactly where it should.

## Limitations

- The trap line reads poorly (`relay call fixture_id(1 / 0)`); its
  meaning lives in the doc comment plus these probes, not the syntax.
  A clearer test-setup failure primitive would be a small catalogue
  addition, not grammar — out of scope for conventions, noted for B05.
- The factory self-row compares against itself; its value is execution
  coverage, and the record states this plainly. Verification comes
  from the owner literals plus consumer projections.
- One owner shape exercised (`user_id` over int). Multi-field owners
  and multi-error constructors follow the same arm-per-error pattern;
  the second error is measured here (`retired`), the fifth is not.

## W3-owner verdict

Passes: handler helper extracted with factory fixtures; all 8
pre-extraction roots retained and green alongside 6 new ones; setup
plumbing 9 lines per factory; unexpected rejection fails closed with
a located standard fault of pinned kind and message; no forged values
(compiler-rejected); repair compiler-guided and helper-local.

## Q4 assessment (for gated B04): inactive

Factory cost is small, explicit, and one-directional: 9 lines per
input shape, one arm line per constructor error, zero helper churn on
constructor evolution, and every failure mode either compiler-guided
or fail-closed with located diagnostics. Nothing measured here is
excessive, and nothing failed: the LD29 gate stays closed and no
setup-region syntax is proposed. The genuine wart is the trap line's
readability, which a catalogue-level failure primitive could address
without touching assertion grammar — a possible B05 follow-up, not a
Q4 trigger.

Trip conditions (reopen only on new evidence): factories multiply
past readability on a real multi-owner handler (held-out extraction
trial); a setup need appears that factories cannot express (not
merely spell awkwardly); or repair trials measure factory repair
above an alternative on equivalent tasks. Qualitative judgment, no
numeric cutoff: the record above is the evidence.
