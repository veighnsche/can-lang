# Application performance scope

`apps.py` follows `../PROTOCOL.md`. All fixture emission and browser bundling happen in `prepare`; runs never invoke the compiler. All generated artifacts remain under `--work-dir`. Browser capability and every workload child write their full JSON result to a newly named work-dir file; Python reads it only after successful child exit and validates the envelope. Raw observations therefore do not depend on large stdout writes. Malformed/missing child results fail, and failed children cannot reuse stale result files. A child launcher supplies the runtime's private empty environment snapshot on descriptor 3 without changing supervisor descriptors.

Browser preparation records available and unavailable Chromium, Firefox and WebKit launch results in `apps-manifest.json`. By default runs execute every available engine. Each case records the actual engine version in its comparison parameters. Set `CAN_PERF_BROWSER_ENGINES=chromium,firefox,webkit` to request exact coverage; any unavailable requested engine blocks preparation/run. The fixture imports real production browser modules with the maintained seven-module browser overlay and exercises four flows: immutable native input/property snapshots with state updates, a three-character native keyboard suffix, button-triggered state/reset/property updates, and exact live caret/value roundtrips. Text input size scales with `--size`; the keyboard suffix stays at three characters to keep automation bounded. Each keyboard interaction retains its three individual handler observations. Handler timing begins inside the callback and ends after the awaited property/state/DOM operations; keyboard interactions sum three handler times. Selection timing measures the in-page set/read completion endpoint. It excludes automation, event queue delay, layout and paint. Actual paint and INP are explicitly unavailable. Readiness, every final DOM value, no page errors and exact selection, old-state preservation and reset values are checked.

Server runs launch a separate local Bun listener process and a generator process. The listener uses real runtime `snapshotRequest`, `ownedResponse`, `nativeResponse` and request revocation; it does not represent the complete `createServer` resource lifecycle. Both GET text responses and POST JSON body/response conversions scale with `--size`. POST uses bounded production request snapshots, fatal native UTF8/JSON decoding and `ownedJsonResponse` with owned bytes; every response includes its request ID and exact message/length. Closed-loop bounded clients and independent scheduled arrivals are distinct cases. Each trial retains request send/completion times, latency, status, correctness, errors, scheduled arrival and dropped work, achieved load and configured population/cap. The same-host Bun fetch generator and fixed concurrency cap can limit delivered load. No remote capacity, TLS, router, or percentile-from-average claim is made.

I/O compares real `createFileReads.readText` against a separate labeled native stream implementation with the same byte bound, copied chunks, ownership copies and fatal UTF8 decoding. Timed work includes open/read/materialization/decode; initial write is excluded. Inputs end in a multibyte scalar. Cache state is OS-managed/warm. Additional runtime/native pairs measure copied binary overwrite → bounded stream read → outbound copy and expected byte-cap rejection including cancellation. Binary output is checked byte-for-byte, source bytes remain unchanged, and runtime rejection must identify `files::limit_exceeded` with the exact bound. This is not a cold-storage or fsync/durability benchmark.

Journeys emit the maintained apps Can fixture through `compiler/perfemit`, identify the checked emitted `gallery::doubled`, `gallery::make_invoice_line` and `gallery::summarize_invoice` exports by source origin, and initialize the emitted program outside samples. The actual application path decodes a serialized batch request, calls the emitted Can function, then serializes and consumes the response. The invoice journey is inspired by `examples/invoice` line records: decode serialized input, construct real emitted Can records, map line validation/totals, fold the accepted/total/invalid-count summary, and serialize the exact response. Separate valid and zero-quantity invalid-line cases check immutable input records and summary, and unchanged source request after the timer stops. The timed adapter retains input/result references in one minimal observation object; full harness scans/snapshots are outside timing. This representative model excludes the real application’s database, authentication, concurrency and render paths; it does not claim a complete browser product or remote network journey.

Quick and standard profiles both permit caller-controlled scaling through `--size`. Standard server cases use 200 requests, 16 clients and 500 scheduled requests/second; quick uses 20 requests, 4 clients and 100 scheduled requests/second. `--iterations` is the number of workload operations per batch/sample, and `--warmups` is the number of discarded warmup batches. Quick records three measured batches and standard records seven. Each reported sample is the mean operation/event/trial duration in its batch. Individual operation, event and HTTP request observations are retained; no request percentile is derived from batch averages. The shared supervisor owns independent process trials and the audit lock.

Coverage expansion relative to the initial application drivers:

| Slice | Initial scenarios | Expanded scenarios | Remaining limits |
| --- | --- | --- | --- |
| browser | One input/DOM flow per engine | Four C02 property/snapshot, keyboard, state/reset and caret flows per engine | No paint/INP, multiselect/upload or whole-product navigation |
| server | GET under two load models | GET and POST body/response conversion under both models | No full createServer lifecycle, router, TLS, remote capacity or sustained soak |
| io | Runtime/native text read pair | Text pair, binary write/read pair, expected bound-rejection pair | OS-managed cache; no fsync/durability/network storage |
| journeys | Emitted doubled request | Doubled plus valid/invalid emitted invoice record validation/map/fold | Representative business model; no invoice auth/database/browser integration |
